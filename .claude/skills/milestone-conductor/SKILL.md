# マイルストーンの進行

マイルストーンの残り Issue を見渡し、dev 環境の空きに合わせて対応の子セッションを起動し、全件が終わったら `release` スキルへ渡す。この役 (進行役) を 1 つのセッションに置く。人が各子セッションへ降りて判断できるよう、進行役は采配に徹し、個々の Issue の設計判断は持たない。

`release` スキルが受け持つのはマイルストーン完了後からリリースまで。本スキルは、その手前のマイルストーンの途中を受け持つ。

## 鉄則

- 子セッションの起動は、**毎回、人の承認を得てから**行う。
- 報告を受けたら、判断の前に **GitHub で事実を確かめる** (Issue の状態、PR、デプロイの結果)。報告が来る前に状況が進んでいることがある。
- 状況は HTML の Artifact (ボード) にまとめ、変化のたびに更新する。
- 出力は日本語。

## 1. 進める順序

- 基盤 (libs や共通インフラを触るもの) → 複数サービスにまたがるもの → サービス単体、の順に流す。
- 1 Issue に 1 セッション。同じサービスの Issue はまとめず、同じサービスの中では 1 本ずつ流す。
- 探索的テストやコード共通化調査のように、新しい Issue を大量に生むものは後回しにしてよい。扱いは人が決める。

## 2. 並行させてよい条件

- dev へデプロイするものどうしを並べるのは、片方が dev に何も出さない (docs だけなど) か、デプロイ先のサービスが重ならない場合だけ。
- libs を触る対応どうしは、dev での動作確認の有無に関係なく 1 本ずつ。libs を触ると全サービスへデプロイされる。
- コードが重なるなら、デプロイ先が違っても待つ。
- 反映確認だけの対応は、ほかの対応を待たせる理由にならない。

## 3. 子セッションの起動

起動は `create_session` で行い、起点を `source_url` / `source_revision` の API パラメータとして渡す (未指定だとリポジトリが clone されない)。

### 起点ブランチ

Issue の integration ブランチがあればそこ、無ければ `develop`。

### 起動プロンプトに入れるもの

- **スコープの境界**: 同じサービスのほかの Issue、同じ画面に関わる隣の Issue は変えない。
- **並行している対応と、その前提**: デプロイ先が重ならないこと。
- **人に確認すること**: integration を切るか、dev で確かめるものがあるか、libs を触るか (触ると並行の前提が崩れる)、Issue ごとの論点。
- **方針の確認の出し方**: 人に方針を尋ねる前に、HTML の Artifact で方針をまとめてリンクを添える。載せるのは、何を直すか、直し方、PR の分け方、ブランチとデプロイ先、dev で確かめるもの、人に決めてほしいこと (選択肢と推奨)。
- **確認の考え方**: 「4. 確認の考え方」の内容。

### 進行役への報告

子セッションが進行役へ報告するのは、次の 3 つだけ。送る前に人の許可を取る。

1. 方針が決まったとき (ブランチ、デプロイ先、dev で確かめるものとその理由)。
2. ブランチ・デプロイ先・dev で確かめるもの・期間のどれかが途中で変わったとき。実装や設計の方針転換は報告不要。
3. develop に入り、反映確認 (と、要る場合は動作確認) を終えてクローズしたとき (解放)。

PR を作った時点の報告は求めない。人は PR を直接見るため、報告の許可待ちが事後報告になるだけで役に立たない。

## 4. 確認の考え方

- **反映確認**: マージ後に、デプロイが成功し、資材が dev に載って各サービスが応答すること。全件必須。
- **動作確認**: 環境に依存しないもの (見た目、クライアント側の挙動など) は手元で確かめる。dev で確かめるのは、dev の環境に依存するもの (実際の認証、AWS のリソース、インフラ、外部との連携など) だけで、その間は dev を押さえる。
- **人に頼むもの**: dev でしか確かめられず、Claude が触れないものだけ。頼むときは、手元で確かめられない理由を添える。

## 5. 報告を受けたら

1. GitHub で事実を確かめる。Issue の状態、PR、デプロイの結果を見て、報告との差を把握してから判断する。
2. 方針の報告を受けた時点で、デプロイ先の重なりから「PR をいつマージしてよいか」を決め、ボードの「マージしてよい時機」に書く。
3. 解放の報告を受けたら、ボードの区間を空きに戻し、待ち行列から次の起動候補を人に提案する。

## 6. 進行ボード

[`templates/board.html`](./templates/board.html) から始め、変化のたびに同じファイルを再 publish して、同じ URL で更新する。上から 判断 → 区間 → 進行中 → 待ち行列 の順に並べる。

| 区画 | 意味 |
|---|---|
| ヘッダー | 更新時刻 (JST)、Issue の残 / 全、進行中の件数 |
| 次にやること | 人の対応待ち、起動候補、後回し |
| dev 環境の区間 | デプロイ先ごとの占有状況。信号 (空き / 占有 / 待ち)、占有している対応、dev に載っている資材、マージしてよい時機、待ち Issue。先頭は基盤 (libs / infra/common) |
| 進行中 | 対応ごとのカード。ブランチ、デプロイ先、dev で確かめるもの、進捗 (方針 → 実装 → マージ → 反映確認 → 解放) |
| 待ち行列 | 残りの Issue を 基盤 → 複数サービス → サービス単体 の順で並べたもの |
| 本番で気を付けること、判断ルール | release スキルへ渡すメモと、並行の判断ルールの要約 |

## 7. パッチリリースの割り込み

緊急のパッチリリースが割り込んだときは、dev への適用と新しい起動を止め、人の許可が出てから再開する。止めた事実と再開待ちであることをボードに書く。

## 8. release への引き渡し

マイルストーンの Issue がすべてクローズしたら、[`release` スキル](../release/SKILL.md)へ渡す。

- 進行中に見つかった、本番リリースで気を付けること (段階的な反映、本番の状態の事前確認など) を書き留めておき、渡すときに添える。
- 本番の状態の確認は、時間で変わるもの (動いているジョブなど) をマージ直前に行う。

## やらないこと (MUST NOT)

- 人の承認なしの子セッションの起動
- Draft → Ready の切替、PR のマージ
- ラベル・マイルストーン・Assignee の付与・変更
- `develop` / `master` への直接 push
- `release` スキルの手順の代行 (リリースブランチ作成以降は `release` スキルで進める)
