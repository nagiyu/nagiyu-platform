# マイルストーンの進行

マイルストーンの残り Issue を見渡し、dev 環境の空きに合わせて対応の子セッションを起動し、全件が終わったら `release` スキルへ渡す。この役 (進行役) を 1 つのセッションに置く。

`release` スキルが受け持つのはマイルストーン完了後からリリースまで。本スキルは、その手前のマイルストーンの途中を受け持つ。

## 1. 着手時

マイルストーンの残り Issue を洗い出し、Issue ごとにデプロイ先と libs を触るかを見立てて、待ち行列を組む。

## 2. 進める順序

- 基盤 (libs や共通インフラを触るもの) → 複数サービスにまたがるもの → サービス単体、の順に流す。
- 1 Issue に 1 セッション。同じサービスの Issue はまとめず、同じサービスの中では 1 本ずつ流す。
- 探索的テストやコード共通化調査のように、新しい Issue を大量に生むものは後回しにしてよい。扱いは人が決める。

## 3. 並行させてよい条件

- dev へデプロイするものどうしを並べるのは、片方が dev に何も出さない (docs だけなど) か、デプロイ先のサービスが重ならない場合だけ。
- libs を触る対応どうしは、dev での動作確認の有無に関係なく 1 本ずつ。libs を触ると全サービスへデプロイされる。
- コードが重なるなら、デプロイ先が違っても待つ。
- 反映確認だけの対応は、ほかの対応を待たせる理由にならない。

反映確認・動作確認の意味は `CLAUDE.md` の Issue のクローズ条件のとおり。dev で動作確認をする間は、その対応が dev を押さえる。

## 4. 子セッションの起動

起動は毎回、人の承認を得てから行う。起点ブランチは、Issue の integration ブランチがあればそこ、無ければ `develop`。

### 起動プロンプトに入れるもの

子は本スキルを読まないため、次の項目は起動プロンプトに書き写す。

- **スコープの境界**: 同じサービスのほかの Issue、同じ画面に関わる隣の Issue は変えない。
- **並行している対応と、その前提**: デプロイ先が重ならないこと。
- **人に確認すること**: integration を切るか、dev で確かめるものがあるか、libs を触るか (触ると並行の前提が崩れる)、Issue ごとの論点。
- **方針の確認の出し方**: 人に方針を尋ねる前に、HTML の Artifact で方針をまとめてリンクを添える。載せるのは、何を直すか、直し方、PR の分け方、ブランチとデプロイ先、dev で確かめるもの、人に決めてほしいこと (選択肢と推奨)。
- **dev の押さえ方**: dev で確かめる間は dev を押さえる。
- **進行役への報告**: 下記の 3 つだけであること。宛先として進行役の session_id を書き、`send_message` で送るよう伝える。

### 進行役への報告

子セッションが進行役へ報告するのは、次の 3 つだけ。送る前に人の許可を取る。

1. 方針が決まったとき (ブランチ、デプロイ先、dev で確かめるものとその理由)。
2. ブランチ・デプロイ先・dev で確かめるもの・期間のどれかが途中で変わったとき。実装や設計の方針転換は報告不要。
3. develop に入り、反映確認 (と、要る場合は動作確認) を終えてクローズしたとき (解放)。

PR を作った時点の報告は求めない。人は PR を直接見るため、報告の許可待ちが事後報告になるだけで役に立たない。

## 5. 報告を受けたら

- 判断の前に、GitHub で事実 (Issue の状態、PR、デプロイの結果) を確かめる。報告が来る前に状況が進んでいることがある。
- 方針の報告を受けた時点で、デプロイ先の重なりから「PR をいつマージしてよいか」を決め、ボードに書く。
- 解放の報告を受けたら、空いた区間に入れる起動候補を人に出す。

## 6. 進行ボード

マイルストーンの状況 (残り・進行中・dev の区間ごとの占有・待ち行列) を HTML の Artifact にまとめ、変化のたびに更新する。[`templates/board.html`](./templates/board.html) を scratchpad にコピーして使い (リポジトリ内の型は書き換えない)、コピーしたファイルを更新して同じ URL へ publish し直す。

## 7. パッチリリースの割り込み

緊急のパッチリリースが割り込んだときは、dev への適用と新しい起動を止め、人の許可が出てから再開する。

## 8. release への引き渡し

- 進行中に見つかった、本番リリースで気を付けること (段階的な反映、本番の状態の事前確認など) を書き留めておき、[`release` スキル](../release/SKILL.md)に渡す。
- 本番の状態の確認は、時間で変わるもの (動いているジョブなど) をマージ直前に行う。
- マイルストーンの Issue がすべてクローズしたら、人の合意を得てから `release` スキルに移る。
