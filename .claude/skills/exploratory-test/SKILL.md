# 探索的テスト

サービスをローカルで `next dev` として起動し、探索担当のサブエージェントに実際のブラウザで触らせて、バグや違和感を拾う。拾った候補は、重要度の高いものから人に見せて、起票するかを判断してもらう。本手順書は、探索の Issue を担当するオーケストレーターが読む。

結果がブレることは許容されている。網羅は目的ではなく、人が見落としやすいものを安く拾うのが目的。

## 1. 準備

リポジトリルートで、上から順に実行する。

```bash
npm ci                                                    # 約 60 秒
npm run build:libs                                        # 共通ライブラリ
.claude/skills/playwright-setup/scripts/install.sh        # chromium。約 34 秒
```

担当サービスの core など、同じサービス内のパッケージも `npm run build --workspace <名前>` でビルドする (サービスごとの名前は `references/services.md`)。しないと API が `Module not found` で 500 になる。

## 2. 起動の 3 段階

サービスごとの起動手順と勘所は `references/services.md` にある。

| 段階 | サービス | 必要なこと |
|---|---|---|
| A | tools / share-together / stock-tracker / niconico-mylist-assistant / portal | `.env.test` のまま動く。core のビルドだけ |
| B | auth / livetalk / admin | `.env.test` に環境変数を足す (`USE_IN_MEMORY_DB=true` など)。admin はさらに偽の DynamoDB が要る |
| C | codec-converter / quick-clip | インメモリ DB の仕組みが無い。偽の AWS サーバーに `AWS_ENDPOINT_URL*` で向ける |

### AWS の扱い

- コンテナの環境変数にある鍵 (`nagiyu-claude-key`) は AssumeRole の権限しか持たず、ローカルのサーバーから AWS を呼んでも、読み取りも書き込みも拒否される。安全なので、鍵を外して起動する必要はない。
- `--profile nagiyu-dev` などを付けて起動しない (`AWS_PROFILE` も同じ)。ロール経由で、dev の一部の Lambda を実行できてしまう。
- AWS が要る画面は、偽のサーバー (`scripts/fake-aws/`) か `page.route` のモックで代用する。偽のサーバーに向けるときは、`AWS_ACCESS_KEY_ID` と `AWS_SECRET_ACCESS_KEY` にダミーの値を入れる。

### 偽の AWS サーバー (`scripts/fake-aws/`)

| ファイル | 用途 |
|---|---|
| `admin-fake-ddb.js` と `admin-seed.js` | admin 用の最小の DynamoDB と、エラー履歴の投入 |
| `codec-converter-fake-aws.js` | codec-converter 用の DynamoDB / S3 / Batch |
| `quick-clip-fake-aws.js` | quick-clip 用の DynamoDB / S3 (マルチパート) / Batch / Lambda |

各ファイルの先頭に、起動方法、対応する API、管理用エンドポイントを書いてある。`localhost` ではなく `127.0.0.1` で向ける (S3 が path-style になる)。

## 3. 探索担当の回し方

探索担当は、サブエージェント (Opus) を **1 サービス 1 体**で走らせる。実測では 1 サービスあたり 9〜19 分、15〜25 万トークンかかる。

- **並列数**: CPU 4 コアで 3〜4 体ずつが限度。それ以上は `next dev` のコンパイルが詰まり、通信の中断による誤観測が増える。10 サービスなら 3〜4 回に分ける。
- **ポート**: web は 3201 から順に、偽の AWS は 43201 から順に、担当ごとに別の番号を割り当てる。3000 と 3001 は使わない。
- **渡す指示**: `references/explorer-instructions.md` の本文に、`<...>` の部分 (リポジトリルート、作業ディレクトリ、サービス名、ポート) を埋めて貼る。続けて `references/services.md` の担当サービスの節を貼る。サブエージェントは親の会話を読めないので、渡したものがすべてになる。
- **作業ディレクトリ**: 担当ごとに、セッションの一時ディレクトリの下へ別々に切る。リポジトリ内には作らせない。
- **起動の担当**: 起動、ウォームアップ、停止は探索担当自身にやらせる (指示に手順がある)。偽の AWS サーバーが要るサービスは、オーケストレーターが先に起動してポートを渡すと、担当の手戻りが減る。
- **戻り値**: 探索担当の最終メッセージが報告になる。発見事項は、分類、重要度、再現手順、証拠、原因の当たり、確度つきで返る。

探索担当は走り出すと人が介入できない。判断が要る場面を作らないよう、禁止事項 (リポジトリの変更、GitHub への書き込み、外部への書き込み) を指示に含めたままにする。

## 4. 後片付け

探索が終わったら、リポジトリを元に戻す。

- 起動した `next dev` と偽の AWS サーバーを、プロセスグループ単位で止める (`kill -- -<PGID>`)。`npx` 経由で起動すると、止めても子のプロセスが残る。パターンで広く殺す `pkill -f` は使わない。
- `next dev` が書き換えた `next-env.d.ts` を戻す。`git status --short` で変更が出ていれば `git checkout -- <パス>` で戻し、コミットしない。
- 大きなテストファイル (マルチパートの確認用など) と、一時ディレクトリの作業ファイルを消す。リポジトリ外 (`/` 直下など) にファイルを作らない。

## 5. 起票の判断の進め方

探索担当の報告は、そのまま起票しない。候補に起こし、人に見せて判断を仰ぐ。

### ルール

- **対象**: バグと、利用者に影響があるもの。リファクタ、テスト、docs、開発環境だけの問題は対象外。
- **単位**: 候補は Issue 1 本の単位にまとめる。重要度の高いものから 1 件ずつ人に見せて判断を仰ぐ。判断の材料は一覧ページにまとめ、判断のたびに更新する。
- **細かいもの**: サービスごとに 1 本に束ね、残すもの (○) と捨てるもの (×) を付けて人に見せる。
- **横断のもの**: 同じ原因が複数サービスにあるもの (長い文字列のはみ出し、404 ページ、不正な JSON など) は、横断の 1 本にまとめるか人に聞く。
- **重複の確認**: 起票前に、必ず既存の Issue と重複を確かめる。重なるものは、既存の Issue へのコメント (追記) にする。
- **裏取り**: 探索担当の報告を鵜呑みにせず、起票前にコードで原因を確かめる。確度の低いものは、dev で確かめるか人に聞く。
- **Issue の書き方**: 現象、再現手順、原因 (該当ファイル) を書き、直し方は書かない。決まっていない仕様の判断は「決まっていないこと」として書く。
- **起票したら**: リンクを人に出す。
- **見送ったもの**: 記録を残さない (Issue にも、他の場所にも)。一覧ページの上でだけ、見送りと分かるようにする。

### 一覧ページ (`scripts/triage/`)

判断の材料を 1 枚にまとめるページを作る。左に検討中の候補 1 件 (提案、再現手順、原因、影響範囲、証拠)、右に全候補のキューと進捗が出る。

1. `scripts/triage/` を一時ディレクトリへコピーする (`img/` を含む。リポジトリ内で生成物を作らない)。
2. コピーした `data.py` を、探索の報告から起こした候補で書き換える。雛形に、候補 1 件と、その詳細 1 件の形が入っている。証拠のスクリーンショットは `img/` に置く。
3. `python3 <コピー先>/build.py` で、隣に `triage.html` が出る。Artifact として公開し、人に見せる。
4. 判断が出るたびに、`data.py` の `STATUS` に結果 (起票は Issue 番号、見送りは理由) を足し、`CURRENT` を次の候補へ進めて、同じ Artifact を更新する。

`data.py` の形と `build.py` の使い方は、`build.py` の先頭に書いてある。
