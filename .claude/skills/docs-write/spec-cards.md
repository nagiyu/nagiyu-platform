# 仕様カードの作成・作り直し

仕様カードは `docs/specs/` にある、**今のコードがどう動くか**の要約である。正本はコードで、「なぜ」は ADR・docs が持つ。カードの文面だけを単独で直さず、コードを変える PR の中で、コードを読んでこの手順に沿って作り直す。仕様・配置・frontmatter・本文の型は [docs/specs/README.md](../../../docs/specs/README.md) を正とし、ここには手順と書き方の要点だけを置く。

## 使うとき

- 変更したファイルが、いずれかのカードの `sources` に含まれる
    - 探し方: `grep -rl "<変更したファイルのパス>" docs/specs`
- 新しいバッチ・通知経路・画面・API・用語を足した
- `node .github/workflows/scripts/spec-cards.mjs check` が落ちた

## 手順

1. **コードを読む**: 今の挙動はコードから取る。ADR は「なぜ」の参照先としてだけ使い、挙動の根拠にしない。ADR や既存のカードとコードが食い違ったら、コードを正とし、食い違いを PR で報告する
2. **型に沿って書く**: 種別 (batch / flow / term / screen / api) ごとの見出しは README の「本文の型」に従う。既存のカードを見本にする
3. **用語カードを確かめる**: 本文で使う用語に term カードがなければ作る。`terms` に id を書き、本文からもリンクする
4. **sources を決める**: そのカードの挙動を決めるファイルだけを、リポジトリルートからのパスで列挙する (glob は不可)。挙動に関係しないファイルを入れると、無関係な変更でカードの確認が要る
5. **ハッシュを計算する**: `node .github/workflows/scripts/spec-cards.mjs update <card の id かパス>`
6. **確かめる**: `node .github/workflows/scripts/spec-cards.mjs check` と `python3 .github/workflows/scripts/check-doc-links.py`
7. **索引に足す**: 新しいカードは `docs/specs/README.md` のカード一覧に足す (`check` が漏れを検出する)

## 画面カードのスクリーンショット

画面 (screen) カードの「画面の見た目」に載せる画像は、手で撮らず撮影スクリプトで撮る。画面カードを作り直すときは、画像も撮り直して同じ PR に含める。

```bash
npm run build:libs                                        # 共通ライブラリ (dist/) が無いとき
npm run build -w @nagiyu/stock-tracker-core               # サービスの core が無いとき
npm run capture:specs -w @nagiyu/docs-site -- stock-tracker                 # 全画面
npm run capture:specs -w @nagiyu/docs-site -- stock-tracker --screen tickers  # 1 画面だけ
```

- サービスは E2E と同じ設定 (`.env.test` のインメモリ DB、認証スキップ) で起動される。外部への通信 (チャートの価格など) と API のエラーは、撮影の中で通信を差し替えて再現する
- どの画面でどの状態を撮るかは、サービスごとの撮影シナリオ (`docs-site/capture/<service>.ts`) に書く。端末の幅もそこで決める。状態を足したら、カードの「画面の見た目」にも同じ名前で足す
- 画像は `docs/images/specs/<service>/screen/` に出力される。撮り直して差分が出たら、画面が変わったかを画像で確かめる (見た目が変わっていないのに差分が出るなら、撮影が不安定なので原因を直す)
- Playwright のブラウザが要求の版で入っていない環境では、`CAPTURE_CHROMIUM_PATH` に Chromium の実行ファイルを渡す (`/opt/pw-browsers/chromium` など)。日本語のフォントなど、環境によって描画が変わるため、画像を撮り直すのは同じ環境で行う
- 新しいサービスに足すときは、`docs-site/capture/<service>.ts` に設定とシナリオを書き、`docs-site/capture/run.ts` の `SERVICES` に登録する

## 既存のカードの作り直し (check が落ちたとき)

**ハッシュだけを更新しない。** `update` はカードの本文が正しいかを確かめない。通すためだけに更新すると、カードが嘘をつく。

1. `check` が示したカードの `sources` を読み、今のコードの挙動を確かめる (変えたファイルの差分から読み始めてよい)
2. カードの本文を 1 行ずつ今のコードと突き合わせる。数値・条件・順序・失敗時の扱いが、いまも合っているか
3. 食い違いがあれば本文を直す。食い違いがなければ本文はそのままにする
4. そのうえで `update` を実行する

## 書き方の要点

- **今の挙動だけを書く**。経緯・理由・検討した他の案は書かず、`related_adr` で ADR に任せる
- **数値は定数の値を書く**。定数名は、コードと突き合わせる必要があるときだけ書く
- **表と箇条書きを中心にする**。短く、1 枚 1 テーマにする
- **batch の節は、必須と任意を分ける**。必須は概要・起点・処理・失敗したとき・つながり。「対象から外れる条件」と「上限」は、そのバッチが持つときだけ書く。起点は、スケジュールか、利用者の操作などの起動のきっかけ
- **「上限」には、処理を止める仕組みとしての上限 (回数・件数の上限など) だけを書く**。対象になる条件 (最低発話数・見る期間など) は「対象から外れる条件」へ、処理のパラメータ (候補の上位件数・保持件数・文字数など) は処理の表・箇条書きへ書く
- **廃止した用語のカードは作らない**。置き換えの経緯は ADR に、昔の中身は git の履歴にある
- **処理・経路はフロー図 (mermaid) + 表にする**。順番・分岐・止まる条件を図に描き、検索語・時間・期限・上限の値などの細かい条件と数値は図の下の表・箇条書きに置く。末尾の図は `## つながり` として、起点・読み書きするデータ・ほかのバッチや Admin との関係を描く (処理の中身は描かない)
- **図は縦向き (`flowchart TD`) にする**。ノードのラベルを「数字 + ピリオド + 空白」で始めない (Markdown の箇条書きと解釈されて崩れる。番号は ①②③ を使う)。1 枚はノード 10 個程度までを目安にし、超えるなら図を分けるか細部を表に逃がす。ラベル内の改行は `<br/>`
- **用語は term カードにリンクする**。本文で定義し直さない
- **コードを読んで得た事実だけを書く**。推測で補わない。読み取れなかったことは書かず、報告する
- 生成日時のような、作り直すたびに変わる値を入れない
- frontmatter の `sources_hash` を手で書かない。表記は [表記規約](../../../docs/development/writing-style.md) に従う
- Markdown のインデントは 4 スペース

## 品質チェック

- [ ] 本文の数値・条件・順序を、`sources` のコードと突き合わせた
- [ ] 経緯や理由を書いていない (ADR への参照にした)
- [ ] 使う用語の term カードがあり、`terms` に書いてある
- [ ] `sources` が実在するファイルだけで、挙動に関係するものに絞れている
- [ ] `spec-cards.mjs check` と `check-doc-links.py` が通る
- [ ] 新しいカードを README の一覧に足した
- [ ] 画面カードは、撮影スクリプトで撮り直した画像を載せ、状態の名前がシナリオと合っている
