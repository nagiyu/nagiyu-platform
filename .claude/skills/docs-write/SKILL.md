# docs/ 執筆ルール

`docs/` の永続ドキュメントは 2 種類ある。執筆・更新時は、まずどちらを書くかを決める。

| 種類 | 中身 | 鮮度の保ち方 | 書き方 |
|---|---|---|---|
| なぜ (ADR・設計判断) | コードからわからないこと (背景・意思決定・設計判断) | 人が書き、追記していく | この文書 |
| 今の挙動 (仕様カード) | コードからわかること | コードから作り直し、CI で検査する | [spec-cards.md](spec-cards.md) |

今の挙動を書くとき、カードを作り直すときは [spec-cards.md](spec-cards.md) を読む。以降の基本原則・手順・図・移行は「なぜ」の文書の書き方である。

## 基本原則

1. **対象は `docs/` 配下のみ**。コード実装・修正は行わない。
2. **最小限のルール**：必須事項のみ記述する。**コードからわかることを、手で書いて保守しない**（API エンドポイント・コンポーネント分割・型定義の詳細など）。書くなら、鮮度を機械的に検査できる写し（仕様カード）として書く。
3. **単体完結**：ドキュメント単体で理解できる内容にする。
4. **「なぜ」の文書ではコード参照を避ける**：ファイルパス・関数名・実装断片への依存的な説明をしない。手で書いた参照は切れても気づかれない。仕様カードは `sources` でコードを参照し、実在とハッシュを検査されるため、この限りでない。
5. **4スペースインデント**：Markdown のネストは常にスペース 4 つ（タブ・2スペースは使わない）。
6. 出力は日本語。
7. **表記規約に従う**: 記号の半角化、スペース、Markdown の強調は [表記規約](../../../docs/development/writing-style.md) に従う。

## 手順

1. **目的の明確化**：何を・なぜ書く／直すかを先に定める。
2. **整合性の確認**：関連ドキュメントの見出し構造・粒度・用語を把握し、同カテゴリで一貫させる。既存ドキュメント間に矛盾があれば、**編集前に報告し合意を得てから**進める。
3. **執筆**：目的・前提・判断基準・制約を中心に書く。コードを見れば分かる具体説明は削除する。
4. **導線の同期**：目次・README・一覧があれば参照リンクを最小限で更新する。

## 図

図は Claude が直接作り、Markdown から読み込める形式で置く。GUI ツールで作って人が書き出す工程を挟まないためである。

1. **まず Mermaid で書く**: Markdown のコードブロックに書けば GitHub がそのまま描画する。フロー・シーケンス・状態遷移・ER・構成図の多くはこれで足りる。
2. **表示が微妙なら SVG にしてよい**: Mermaid は配置を細かく制御できず、ワイヤーフレームのように見た目そのものが情報になる図は描けない。描画結果を人が見て足りないと判断したら、SVG を直接書いて `docs/images/` に置き、画像として読み込む。
    - 描いたらブラウザで画像化して目で確認する。座標のずれはコードを読んでも気付けない
    - 色は `<style>` 内のクラスで定義し、`prefers-color-scheme: dark` でダーク用の色に切り替える。GitHub のダークテーマでも読めるようにするためである
3. **既存の `.drawio.svg` はそのまま使ってよい**: 置き換えは強制しない。

## tasks/ → docs/ 移行（開発完了後）

`tasks/{feature-name}/design.md` の「docs/ への移行メモ」に従って永続化する。

- `requirements.md` → `docs/services/{service}/requirements.md` に統合
- `external-design.md` → `docs/services/{service}/external-design.md` に統合（UI 変更があった場合）
- `design.md` の重要な設計決定 → `docs/services/{service}/architecture.md` に **ADR** として追記
- 反映が完了したら `tasks/{feature-name}/` を削除する

ADR は「背景・問題 / 決定 / 根拠・トレードオフ」の形式で書く（実装詳細は書かない）。

## 品質チェック

- [ ] `docs/` 配下のみを変更している
- [ ] 最小限のルールに従っている（コードからわかることを、検査されない形で手書きしていない）
- [ ] 「なぜ」の文書がコード参照に依存していない
- [ ] Markdown インデントが 4 スペースで統一されている
- [ ] 表記規約に従っている (記号は半角、強調の `**` が生で表示されない)
- [ ] 関連ドキュメントと用語・方針が整合している
