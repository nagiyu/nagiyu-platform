# docs/ の書き方

分類・配置・frontmatter・理由の書き方は [docs の書き方](../../../docs/platform/rules/docs.md) を正とする。ここには手順と、雛形にない種別の本文の型だけを置く。

## 書く前に決めること

1. **何を書くか**: 要件 (目的・ドメインモデル・ユースケース・機能要件・非機能要件)、仕様、規約のどれか
2. **どこに置くか**: `docs/layout.json` の配置のどれか。`services/<service>/` にあるコードの文書は `docs/services/<service>/`、それ以外は `docs/platform/`
3. **本文の型**: サービスの種別は `docs/services/_template/` の同じ位置のファイルを写して使う。platform にしかない種別は下の「雛形にない種別の型」

一緒に変わるものを 1 つの文書にする。同じ内容をほかの文書に書かず、リンクする。

## 要件を書く

- 出典は持たない (`sources: []`)
- やらないと決めたことは、理由を添えて書く
- 属性・キー・テーブル・画面の中身は書かない (仕様に書く)

## 仕様を書く

1. **コードを読む**: 今の挙動はコードから取る。既存の文書とコードが食い違ったら、コードを正とし、食い違いを PR で報告する
2. **型に沿って書く**: 雛形の見出しに従う。最後に任意の「理由」「手順」の節を置ける。必要なものだけ書く
3. **sources を決める**: その文書の挙動を決めるファイルだけを、リポジトリルートからのパスで列挙する (glob は不可)。挙動に関係しないファイルを入れると、無関係な変更で確認が要る
4. **ハッシュを計算する**: `node .github/workflows/scripts/docs-structure.mjs update <path>`
5. **確かめる**: `node .github/workflows/scripts/docs-structure.mjs check` と `python3 .github/workflows/scripts/check-doc-links.py`

### 実装の前に書く仕様

- frontmatter に `unimplemented: true` を書き、出典は空にしてよい
- integration ブランチの上で進め、実装とともに `sources` を埋め、`unimplemented` を消す
- develop / master 向けの PR では、未実装の文書があると CI が落ちる

## 出典が変わった文書を直す (check が落ちたとき)

**ハッシュだけを更新しない。** `update` は本文が正しいかを確かめない。通すためだけに更新すると、文書が嘘をつく。

1. `check` が示した文書の `sources` を読み、今のコードの挙動を確かめる (変えたファイルの差分から読み始めてよい)
2. 本文を 1 行ずつ今のコードと突き合わせる。数値・条件・順序・失敗時の扱いが、いまも合っているか
3. 食い違いがあれば本文を直す。食い違いがなければ本文はそのままにする
4. そのうえで `update` を実行する

旧配置のカード (`docs/specs/`) が落ちたときは [legacy-cards.md](legacy-cards.md) の手順で直す。

## 書き方の要点

- **今の状態を現在形で書く**。決定が変わったら、追記せず書き換える。時系列の経緯と、置き換えられた決定は書かない
- **理由は説明する対象の文書に書く**。採らない案とその理由、判断の根拠になった実測値を含める
- **数値は定数の値を書く**。定数名は、コードと突き合わせる必要があるときだけ書く
- **表と箇条書きを中心にする**。処理・経路はフロー図 (mermaid) + 表にする
- **コードを読んで得た事実だけを書く**。推測で補わない。読み取れなかったことは書かず、報告する
- **docs/ の外へリンクを張らない**。docs/ の外のファイルはコード表記のパスで書く。`sources` はデータなので対象外
- **Issue / PR 番号・Phase 名を書かない**
- README・目次・ドキュメント一覧を手で書かない (公開サイトが配置から作る)
- 表記は [表記規約](../../../docs/development/writing-style.md) に従う。Markdown のインデントは 4 スペース

## 雛形にない種別の型

| 種別 | 置く場所 | 見出し | 出典 |
|---|---|---|---|
| 規約 | `platform/rules/<name>.md` | 規則 (1 つずつ、理由を添える) | 強制している設定ファイル。なければ空 |
| ライブラリ | `platform/specs/lib/<package>/<name>.md` | 使い方 / 振る舞い (入力・出力・失敗したとき) | その機能のソース。サブパスから import させるなら `package.json` も |
| CI | `platform/specs/ci/<name>.md` | 起点 / 処理 / 失敗したとき | 一緒に変わるワークフローの群と、それが呼ぶスクリプト・composite action・イメージの定義 |

- 概要は見出しを立てず、タイトル (H1) の直後に段落で書く。仕様のほかの種別と同じ形にそろえる
- どの種別も、最後に任意の「理由」「手順」の節を置ける。型にない見出し (イメージの一覧、出し分けの表など) は、独立した節にせず、型の節の下に置く

## 図

図は Claude が直接作り、Markdown から読み込める形式で置く。GUI ツールで作って人が書き出す工程を挟まないためである。

1. **まず Mermaid で書く**: Markdown のコードブロックに書けば GitHub がそのまま描画する。フロー・シーケンス・状態遷移・ER・構成図の多くはこれで足りる。
2. **表示が微妙なら SVG にしてよい**: Mermaid は配置を細かく制御できず、ワイヤーフレームのように見た目そのものが情報になる図は描けない。描画結果を人が見て足りないと判断したら、SVG を直接書いて `docs/images/` に置き、画像として読み込む。
    - 描いたらブラウザで画像化して目で確認する。座標のずれはコードを読んでも気付けない
    - 色は `<style>` 内のクラスで定義し、`prefers-color-scheme: dark` でダーク用の色に切り替える。GitHub のダークテーマでも読めるようにするためである
3. **既存の `.drawio.svg` はそのまま使ってよい**: 置き換えは強制しない。

## 画面のスクリーンショット

画面 (screen) の仕様の「画面の見た目」に載せる画像は、手で撮らず撮影スクリプトで撮る。画面の仕様を作り直すときは、画像も撮り直して同じ PR に含める。

```bash
npm run build:libs                                        # 共通ライブラリ (dist/) が無いとき
npm run build -w @nagiyu/stock-tracker-core               # サービスの core が無いとき
npm run capture:specs -w @nagiyu/docs-site -- stock-tracker                 # 全画面
npm run capture:specs -w @nagiyu/docs-site -- stock-tracker --screen tickers  # 1 画面だけ
```

- サービスは E2E と同じ設定 (`.env.test` のインメモリ DB、認証スキップ) で起動される。外部への通信 (チャートの価格など) と API のエラーは、撮影の中で通信を差し替えて再現する
- どの画面でどの状態を撮るかは、サービスごとの撮影シナリオ (`docs-site/capture/<service>.ts`) に書く。端末の幅もそこで決める。状態を足したら、仕様の「画面の見た目」にも同じ名前で足す
- 画像は `docs/images/specs/<service>/screen/` に出力される。撮り直して差分が出たら、画面が変わったかを画像で確かめる (見た目が変わっていないのに差分が出るなら、撮影が不安定なので原因を直す)
- Playwright のブラウザが要求の版で入っていない環境では、`CAPTURE_CHROMIUM_PATH` に Chromium の実行ファイルを渡す (`/opt/pw-browsers/chromium` など)。日本語のフォントなど、環境によって描画が変わるため、画像を撮り直すのは同じ環境で行う
- 新しいサービスに足すときは、`docs-site/capture/<service>.ts` に設定とシナリオを書き、`docs-site/capture/run.ts` の `SERVICES` に登録する

## 品質チェック

- [ ] `docs/` 配下のみを変更している
- [ ] `docs/layout.json` の配置に置いた
- [ ] 本文の数値・条件・順序を、`sources` のコードと突き合わせた
- [ ] `sources` が実在するファイルだけで、挙動に関係するものに絞れている
- [ ] 同じ内容をほかの文書に書いていない
- [ ] 経緯や置き換えられた決定を書いていない
- [ ] `docs-structure.mjs check` と `check-doc-links.py` が通る
- [ ] 表記規約に従い、Issue / PR 番号・Phase 名を書いていない
