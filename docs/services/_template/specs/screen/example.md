# 画面の名前

必須。画面が何のためにあるかを 1〜2 文で書く。見出しは付けない。画面は 1 画面につき 1 本置く。

> この雛形は `docs/services/<service>/specs/screen/<name>.md` に写して使う。説明の文を消し、本文に置き換える。

## 入口

必須。URL のパスと、どこから来るか。

## 表示の条件

任意。`## 入口` の次に置く。権限・ログインなどで見え方が変わるときに書く。

## 表示するもの

必須。画面に出る項目を表・箇条書きで書く。

## 状態

任意。`## 表示するもの` の次に置く。空・読み込み中・エラーのときの表示が決まっているときに書く。

## 操作

必須。操作 → 結果の表。呼ぶ API の仕様 (`specs/api/`) へリンクする。

## 画面の見た目

任意。`## 操作` の次に置く。スクリーンショットを載せる。撮影の仕組み (`docs-site/capture/`) があるサービスでは必須にする。

- 状態ごとに小見出し (`###`) を付け、その下にスマホと PC の画像を 2 列の表で並べる。端末はサービスごとの設定 (`docs-site/capture/<service>.ts` の `devices`) で決まり、1 端末だけのサービスは 1 列にする
- 画像は `docs/images/specs/<service>/screen/<画面>-<状態>-<端末>.png` に置き、仕様から docs 内の相対リンクで参照する。画像は手で撮らず、撮影スクリプトで作る (手順は docs-write スキルの「画面のスクリーンショット」)
- 状態名は撮影シナリオ (`docs-site/capture/<service>.ts`) のものと同じにする。撮る状態は、通常表示、データが空、ダイアログを開いた状態、入力エラー、API のエラー、ロールによる違いのうち、その画面にあるもの

## つながり

必須。この画面と API・ほかの画面の関係を図 (mermaid) で描く。図の書き方は [経路の雛形](../flow/example.md) の「図の書き方」に従う。

## 理由

任意。この仕様になっている理由を、今の状態として現在形で書く。採らない案とその理由、判断の根拠になった実測値を含める。時系列の経緯と、置き換えられた決定は書かない。

## 手順

任意。この仕様が触る対象を操作する手順 (切り替え、復旧、手動実行など) を書く。手順は独立した文書にせず、対象の仕様に書く。
