# Stock Tracker アーキテクチャ設計書（設計決定記録）

## 1. システム概要

Stock Tracker は、株価のリアルタイム監視と条件ベースのアラート通知を提供するサービスです。TradingView API から株価データを取得し、ユーザーが設定した条件（価格閾値など）を満たした場合に Web Push 通知を送信します。また、保有株式の管理と、日次サマリー・判断軸から算出した確度により、投資判断を支援します。

Next.js アプリケーションをサーバーレスで実行し、アラートチェック・日次サマリー生成・確度の算出を独立したバッチ Lambda で処理する構成です。データはすべて DynamoDB のシングルテーブル設計で管理し、認証には nagiyu プラットフォーム共通の NextAuth 基盤を使用します。

---

## 2. 重要なアーキテクチャ決定

欠番は、AI 解析・AI 予測の採点を撤去したときに役目を終えた判断である (ADR 2.21)。

### 2.1 DynamoDB シングルテーブル設計の採用

**背景・問題**

複数エンティティ（取引所・ティッカー・保有株式・アラート・日次サマリー）を効率的に管理するデータベース設計が必要だった。

**決定**

単一の DynamoDB テーブルで全エンティティを管理するシングルテーブル設計を採用する。

**根拠・トレードオフ**

- アクセスパターンが「ユーザー中心」に集中しており、GSI 設計でほぼ全クエリを網羅できる
- nagiyu プラットフォームの既存サービスと同じパターンで一貫性がある
- RDB に比べ設計の複雑性は高いが、DynamoDB の低レイテンシ・オンデマンドスケールとの親和性を優先した
- 複数テーブル設計はクロステーブルクエリが頻発し、コスト・パフォーマンス上不利

---

### 2.2 Repository Factory パターンによるテスタビリティの確保

**背景・問題**

E2E テストで実際の DynamoDB に接続せずに動作確認したい。一方で、本番環境では DynamoDB リポジトリを使用する必要がある。

**決定**

環境変数 `USE_IN_MEMORY_REPOSITORY` により DynamoDB 実装とインメモリ実装を切り替える Repository Factory パターンを採用する。

**根拠・トレードオフ**

- テスト時は InMemory 実装でデータを分離でき、実行速度と独立性を確保できる
- API エンドポイントはリポジトリのインターフェースに依存するため、実装の変更が容易
- シングルトン管理によりリポジトリのインスタンスを効率的に使い回せる

---

### 2.3 バッチ処理の分離（アラート処理 vs 日次サマリー生成）

**背景・問題**

アラートチェック（1分・1時間・日次）と日次サマリー生成（1時間間隔）は処理目的が異なるが、同じスケジュールで実行されることがある。

**決定**

日次サマリー生成バッチを既存のアラート処理バッチ（hourly）とは独立した別 Lambda・別 EventBridge ルールとして運用する。

**根拠・トレードオフ**

- 一方の処理が失敗しても他方に影響しない障害分離が実現できる
- バッチごとにメモリ・タイムアウト設定を最適化できる
- Lambda 関数が増えるが、責務の明確化と保守性向上を優先した

---

### 2.4 Web Push 通知の採用

**背景・問題**

アラート条件達成時にユーザーへ通知する手段が必要だった。スマートフォン・デスクトップ両方で動作し、追加アプリなしで利用できる方式が求められた。

**決定**

VAPID 認証を用いた Web Push 通知を採用する。通知クリック時は `exchangeId`/`tickerId` パラメータ付きのチャート画面 URL へ遷移する。

**根拠・トレードオフ**

- ブラウザネイティブ機能であり、追加アプリが不要
- Service Worker によりブラウザを閉じた状態でも通知受信が可能
- VAPID 認証により通知送信元の検証が可能
- iOS Safari の対応が限定的であることは既知のトレードオフ

---

### 2.5 TradingView API の採用

**背景・問題**

リアルタイム株価データをブラウザとバッチ処理の両方で取得する手段が必要だった。

**決定**

`@mathieuc/tradingview` パッケージを通じて TradingView API を利用する。

**根拠・トレードオフ**

- 既存の finance リポジトリでの動作実績がある
- WebSocket 接続による効率的なリアルタイム更新（ポーリング不要）
- 複数タイムフレーム・多数の取引所・ティッカーに対応
- 非公式パッケージであり、API 仕様変更のリスクがある

---

### 2.7 日足パターン分析の設計方針

**背景・問題**

株価チャートのパターン分析を提供したいが、ユーザー定義の条件式は複雑度が高い。

**決定**

パターンは固定の定義 (現在は買い 11 種・売り 16 種) をコードで持ち、判定結果を「成立・不成立・判定不能」の3状態で管理する。判定結果は確度の判断軸として使う (ADR 2.26)。

**根拠・トレードオフ**

- ユーザー定義の条件式を持たず、確実に動作するパターンから提供する
- 取得日足が所定本数に満たない場合は「判定不能」として成立判定を行わず、精度を担保する

---

### 2.8 バルク取得メソッドのアイテム単位エラー耐性

**背景・問題**

DynamoDB に格納された一部アラートのサブスクリプションデータが不正な形式で残存しており、バッチがアラートを一括取得する際に個別アイテムのマッピング失敗がバッチ全体を停止させていた。旧形式から新形式へのサブスクリプション移行期に発生したデータ不整合が原因。

**決定**

repository 層のバルク取得メソッドは、個別アイテムのマッピング失敗（エンティティデータ不正エラー）をアイテム単位で吸収し、不正アイテムをスキップして有効アイテムのみを返す。スキップ時は識別情報をワーニングとしてログ出力する。

**根拠・トレードオフ**

- 一部の不正データが全件処理を停止させることを防ぎ、バッチの可用性を高める
- スキップログにより、後続の不正データ修正作業をサポートできる
- ログに個人情報（サブスクリプション endpoint など）を含めないことを原則とする
- マッピング失敗以外の DynamoDB SDK エラーは従来通りエラーとして伝播する

---

### 2.9 ダイアログコンポーネントのトップ画面への流用

**背景・問題**

トップ画面（SCR-001）に保有株式・アラート・サマリーの CRUD 操作を追加するにあたり、各専用画面（SCR-002, SCR-003, SCR-004）で既に利用しているダイアログコンポーネントの再利用が求められた。

**決定**

各専用画面のダイアログコンポーネントをトップ画面からも流用する。

**根拠・トレードオフ**

- コンポーネントの重複実装を避け、専用画面とトップ画面で同一の操作 UI を提供できる
- ダイアログの仕様変更は一箇所の修正で全画面に反映される
- 既存コンポーネントの props インターフェースをそのまま利用するため、既存設計を変えずに再利用できる

---

### 2.10 InvalidEntityDataError 判定のモジュール差異耐性

**背景・問題**

一時アラート失効バッチで、DynamoDB の不正レコード（`SubscriptionEndpoint` 欠損など）をスキップする実装があるにもかかわらず、実行環境差異により `instanceof InvalidEntityDataError` が一致せず、バッチ全体が失敗する事象が発生した。

**決定**

`DynamoDBAlertRepository` の不正データ判定は `instanceof` のみではなく、`error.name === 'InvalidEntityDataError'` とメッセージ内容も併用して判定する。

**根拠・トレードオフ**

- モジュール解決経路が異なる実行環境でも、不正データを安定してスキップできる
- 既存の `instanceof` 判定を維持しつつ後方互換で拡張できる
- `name` 判定のみの過検知を抑えるため、メッセージ先頭（`エンティティデータが無効です`）も併用する
- DynamoDB SDK エラーなど他種別エラーは従来どおり伝播させ、障害検知性を維持する

### 2.11 一時アラート失効バッチの subscription 非依存化と「無効化 + TTL」方式

**背景・問題**

ADR 2.8 / 2.10 でアイテム単位エラースキップ・モジュール差異耐性を入れてもなお、一時アラート失効バッチが `subscription` フィールドの整合性に依存して失敗するケースが残っていた。原因は、削除判定そのものに本来不要な `subscription` データを読み込んでいる構造にある。さらに、物理削除を伴うバッチは失敗時の冪等性が低く、リトライ運用が難しかった。

**決定**

一時アラート失効バッチを、対症療法ではなく構造的に組み替える。

1. **バッチ用の軽量取得経路を独立**: `AlertRepository.getTemporaryCandidatesByFrequency` を新設し、DynamoDB Query の `ProjectionExpression` で失効判定に必要な属性（`AlertID` / `UserID` / `ExchangeID` / `Frequency` / `Enabled` / `Temporary` / `TemporaryExpireDate`）のみを取得する。`subscription` は読み込まない。`FilterExpression` で `Temporary = true AND Enabled = true` のアラートのみに絞る。
2. **物理削除 → 「無効化 + DynamoDB TTL」**: `AlertRepository.markTemporaryAsExpired(userId, alertId, ttlSeconds)` を新設。`Enabled = false` への更新と `TTL` 属性のセットを 1 回の `UpdateItem` で行い、物理削除は DynamoDB TTL に委ねる（猶予 7 日）。DynamoDB テーブル定義は既に `timeToLiveAttribute: 'TTL'` で TTL 有効化済み。
3. **Web 一覧 API の `Enabled` フィルタ**: `GET /api/alerts` のリポジトリ呼び出しに `enabledOnly: true` を渡し、無効化された一時アラートを Web 一覧から即時非表示にする。これにより、TTL 発火を待たずユーザー視点では「期限切れ＝即削除」と同等の UX を維持する。

**根拠・トレードオフ**

- 削除判定に subscription を一切触らない構造により、subscription データの不整合がバッチをブロックしない（ADR 2.8 / 2.10 の補完ではなく、その必要性自体を縮減する）
- バッチが「フラグ更新 + TTL 設定」だけになるため冪等で、リトライしても安全
- TTL 発火は最大 48 時間遅延し得るが、Web 一覧の `Enabled` フィルタにより UX 影響は無い
- バッチ専用の軽量経路を独立させたことで、通知送信側で利用する `getByFrequency` / `mapper.toEntity` の挙動には影響を与えない
- `Subscription` を `Alert` に埋め込んでいる現データモデル自体の見直し（独立エンティティ化、新旧形式撲滅）は別途中期対応として計画する

### 2.18 現在価格取得を市場別データソースに分離した判断（US = Finnhub / 東証 = TradingView）

**背景・問題**

分次バッチ（`batch-minute`）の TradingView API タイムアウトが頻発していた。CloudWatch Logs の実測で、タイムアウトは **100% が US 銘柄（NASDAQ/NYSE/AMEX）に集中し、東証（TSE）はほぼ 0** であった。根本原因は、非公式ライブラリ `@mathieuc/tradingview` の **匿名（ゲスト）WebSocket 接続がスロットリングされ、共有接続が沈黙死**すること（ゲスト優先度は US のリアルタイムデータほど厳しく絞られる）。共有セッション・並列度抑制・jitter・時間予算・fresh-WS リトライ・container kill といった延命策を重ねても根治しなかった。

**決定**

現在価格取得を `QuoteProvider` 抽象でルーティングし、取引所の `PriceSource`（admin 管理データ）で振り分ける。

- **US（NASDAQ/NYSE/AMEX）→ Finnhub 無料 `/quote`**（正規 REST・リアルタイム）
- **東証など → TradingView 継続**
- **candle（OHLCV: チャート表示・日次サマリー）は対象外＝TradingView 継続**

**根拠・トレードオフ**

- **非対称分離が最もコスパが高い**: US はタイムアウトの震源であり、かつ US は無料の正規株価 API（Finnhub 等）が潤沢。逆に東証は無料の代替データソースが実質存在しない（J-Quants 無料は 12 週間遅延、Yahoo/stooq は非公式かつサーバ自動アクセスが困難、証券会社系は Windows アプリ常駐や TSE 有料）。よって「痛い US」を正規 API に逃がし、「代替の無い東証」を比較的安定している TradingView に残す。
- **candle を移さない理由**: `summary` は毎時、chart はオンデマンドで、分次のような新規接続バーストを作らずタイムアウトの震源ではない。加えて Finnhub 無料は candle（`/stock/candle`）が有料専用で提供できない。したがって candle は TradingView 継続が合理的。
- **取引所→データソースをコードにハードコードせず `Exchange.PriceSource`（admin 管理データ）にした**: 取引所の追加・切替をコードデプロイなしで運用でき、段階導入も可能（`PriceSource` 未設定/未知は**安全側で TradingView にフォールバック**するため、切り替えるまで挙動は変わらない）。
- **Finnhub API キーは PLACEHOLDER パターン**: Secrets Manager に PLACEHOLDER で作成し、デプロイ時に Lambda env へ注入する（ランタイムで Secrets を読まず、batch ロールに読み取り権限も付与しない）。キー未投入でもデプロイは失敗せず、投入後は再デプロイで有効化される。
- **認証化は見送り**: 非公式利用である点は匿名/認証を問わず変わらず、TradingView の認証化（cookie もしくは ID/パスワード保管）はアカウント凍結リスク・CAPTCHA・運用負荷から採用しない。
- dev 環境で US 取引所を `finnhub` に切替後、分次バッチの US 銘柄が `errors = 0` / `freshSessionRetries = 0` / タイムアウト 0 で処理されることを確認済み。

### 2.19 祝日マスターを持たず、日足の日付で休場日を扱う判断

**背景・問題**

Stock Tracker は「平日 = 取引日」を前提にしており、祝日を考慮していなかった。予測精度の分析で、この前提が測定の土台を歪めていることがわかった。

- 日次サマリー生成が祝日にも動き、前営業日の足をそのまま当日分として保存していた (休場日のコピー足)
- 採点の評価日を「翌平日」で決め打ちしていたため、翌平日が祝日の予測は終値が見つからず、採点できなかった
- バッチの実行が翌営業日の取引時間中にずれ込むと、翌日の進行中の足を前日分として保存していた

**決定**

祝日マスターは導入せず、**データソースの日足が持つ日付を正**として休場日を扱う。

- 日次サマリーは、対象日と日付が一致する足がある場合だけ作る。一致する足がなければ休場日とみなして作らない。分析には対象日以前の足だけを使う
- 確度の採点で使う「翌営業日」も、足の日付から決める (ADR 2.28)

一時アラートの期限算出など、採点以外の「平日 = 取引日」前提は据え置く。

**根拠・トレードオフ**

- 日足は取引があった日にしか存在しないため、日米どちらの休場日もカレンダーなしで判定でき、毎年の祝日マスター更新が要らない
- 同じ仕組みで、進行中の足の混入も防げる
- 休場日にはサマリーを作らないため、休場日の判定のために毎時の実行で足を取得し直すことになる。取引所内の全銘柄が同時に休場になる性質を使い、先頭の数銘柄が続けて「対象日の足なし」なら、その回は取引所ごと打ち切って呼び出しを抑える。個別銘柄のデータ欠損で誤って止めないよう、1 銘柄ではなく複数銘柄で判定し、上場廃止などで足が止まっている銘柄は判定に数えない
- 一時アラートの期限は「これから来る日」を扱うため、足の日付では判定できない。祝日マスターなしでは正しく直せないので、祝日に期限を迎える（実質 1 取引日短くなる）ことを許容している

---

### 2.21 AI 予測を撤去し、機械的な判断軸を測りながら使う判断

**背景・問題**

日次サマリーには、OpenAI による AI 解析で投資判断シグナル・予測リターン・確信度を出し、自動採点の結果で AI を改善していく計画だった。約 3.5 か月分の予測 (採点済み 7,887 件) を分析したところ、次のことがわかった (詳細は #3831・#3834)。

- AI の翌日予測に予測力はない。予測リターンと実績の符号一致は 50.1% (95% CI 48.1〜52.1%) で、保有期間・閾値・確信度で絞っても、銘柄間の順位付けでもベースラインと変わらなかった
- AI の出力は入力の言い換えだった。予測リターンの分散の約半分は「当日リターン + パターン合致数」で説明でき、Web 検索やチャート画像による上乗せはなかった
- 一方、機械的な指標には手がかりがあった。買いパターンが 2 つ以上同時に合致した銘柄日は翌日の超過リターンが +0.89pt (ただし多重検定の補正後は未確定)、値動きの大きさは直近の値幅や出来高比から予測できた (銘柄の平常比で相関 0.23〜0.29)
- ただし、どの手がかりも局面に依存するか、まだ確定していない。AI を使わない「当日 +3% 以上」のほうが強かった旧「強い BULLISH」のエッジも、8 月には反転した

**決定**

Stock Tracker から AI (OpenAI による解析・Web 検索・AI 予測の採点) を撤去する。代わりに、当日までの OHLCV だけから機械的に算出できる判断軸 (パターン・値動きの大きさ) を持ち、軸ごとの成績を記録し続け、その成績で重みづけした確度を確率で示す。サービスの趣旨 (人がサマリーを見て検討する) は変えない。

**根拠・トレードオフ**

- 予測力のない予測を出し続けることは、判断材料として有害である。判断軸なら、どの軸が点灯し、その軸が過去どれだけ当たっているかを説明できる
- 手がかりを「信じて組み込む」と、局面が変わったときに外れ続ける。成績を溜めて重みを更新し続ける仕組みなら、効かなくなった軸は自然に重みを失い、効き始めた軸は拾える
- OpenAI の費用 (Stock Tracker 分で月 $60 程度。その多くが Web 検索の課金) がなくなる
- サポートレベル・レジスタンスレベルも AI の出力だったため、代替なしで撤去した。既存の AI 解析結果と採点結果は、エクスポートせずに DailySummary から削除する。結論と根拠の数字は Issue に残っている

---

### 2.22 予測の記録を DailySummary から分け、書き換えない判断

**背景・問題**

確度を出すには、銘柄 × 日ごとに軸の値・確率・寄与と、翌営業日の答え合わせを記録する必要がある。旧 AI 予測では、解析結果も採点結果も DailySummary に同居させていた。一方、確度は「当時画面に出した値が当たったか」を検証するためのものであり、重みは日々変わり、軸の定義も後から変わりうるため、後から計算し直しても当時の値は再現できない。

**決定**

- DailySummary は「その日の足 (OHLCV) と、足から決まる判定 (パターン)」の記録にする
- 予測と答え合わせは別のアイテム (銘柄 × 日の Forecast、市場 × 日の MarketForecast) に置く。重み・基準値・中立帯は、算出した市場 × 日ごとのスナップショット (ModelSnapshot) に残す。成績画面の期間集計のために、予測日ごとの採点件数の集計 (PerformanceDaily) も持つ
- 予測時点の値 (軸の値・確率・基準値・中立帯・寄与) は一度だけ書き、書き換えない。条件付き書き込みで作り、再実行しても先に書いた値が残る。答え合わせは別の属性として後から追記する
- 軸の値は軸 ID をキーにした Map で持つ。軸を追加するときは、過去の Forecast に新しい軸の値を追記だけし (既存の値と確率は変えない)、追記した軸であることを記録する方針とする
- 答え合わせの実績は日次サマリーの OHLCV から算出する。答え合わせの期間・閾値・平常の定義を変えた集計も、後から行える

**根拠・トレードオフ**

- DailySummary はパターンの再判定などで丸ごと書き直されうる。性質の違う 2 つを同じアイテムに置くと、予測を書き換えない保証が難しい
- 確度の算出が失敗しても、サマリーの保存と表示は影響を受けない
- 軸の追加でデータの移行は要らない。値がない軸は表示・集計から外れる
- サマリー一覧は、同じ取引所・日付で DailySummary と Forecast をそれぞれ取得して結合することになる

### 2.23 確度の算出を独立したバッチにする判断

**背景・問題**

確度は、日次サマリー (当日の足) が揃ってから、前営業日の採点 → 重みの更新 → 当日の確度の算出、の順に出す必要がある。日次サマリー生成バッチに相乗りさせる案と、独立させる案があった。

**決定**

確度の算出は、日次サマリー生成とは別の Lambda (forecast) にする。毎時起動に加えて、日次サマリー生成の終了時に非同期で起動し、引け後すぐに確度が出るようにする。

- 1 回の実行で、市場ごとに「採点 → 重みの更新 → 確度の算出」を順に行う。どの段も冪等で、途中で落ちても次の実行で続きから進む
- 市場の当日分は、前営業日にサマリーがあった銘柄がすべて揃ったか、引けから 12 時間が過ぎたら処理する。打ち切りで欠けた銘柄は、その日の確度なしで確定する (後から届いても作り直さない)
- 稼働開始時の初期値算出 (既存の DailySummary の履歴からの、確度・採点・重みのさかのぼり) にも、同じコードを過去の日付で 1 日ずつ呼ぶ。さかのぼりで作った確度は、稼働後に作ったものと区別して記録する

**根拠・トレードオフ**

- 確度の算出や採点が失敗しても、日次サマリーの保存と表示は継続する (ADR 2.3 と同じ障害分離)
- 「揃った」を待つ判定と 12 時間の打ち切りで、祝日のカレンダーを持たずに、翌営業日の取引開始より前に確定できる
- 平常の算出に 20 営業日、学習に 30 営業日分の採点済みサンプルが要る。それまでの日付は、軸の値と実績だけを記録し、確率は出さない
- 初期値算出が日次の算出と同じコードを通るため、将来データの混入防止 (ADR 2.28) を二重に実装しなくて済む
- 拡張窓 (ADR 2.24) のため、毎日読む学習データが年々増える。推定そのものは 1 年分でも 1 秒未満の見込みで、読み出しがボトルネックになったら、学習用のデータを別に追記していく方式に切り替える

### 2.24 確度の合成に L2 正則化ロジスティック回帰を選んだ判断

**背景・問題**

軸の多くは同じ OHLCV に由来して互いに似ており、件数の少ない軸は偶然の当たりを拾いやすい。合成方式は、相関を考慮し、件数の少ない軸をゼロに寄せ、内訳 (どの軸が確率を何 pt 動かしたか) を説明できる必要がある。dev の履歴 (2026-03〜09) でウォークフォワード検証し、次の候補を比べた。採用の条件は「日付単位のブートストラップで 90% CI が 0 をまたがない改善」かつ「前半・後半の両方で改善」と、結果を見る前に決めた。

- A: 軸ごとの「点灯時の的中率 − 基準値」を、件数で縮めて対数オッズで足す
- B: L2 正則化ロジスティック回帰
- C: B に指数減衰のサンプル重みを足したもの
- D: 相関の強い軸をまとめてから A で足す

**決定**

- B を採用し、3 つの問いで共用する。モデルは問いごとに 1 つで、JP・US で共通にする
- 学習窓は拡張窓 (利用できる全期間) とし、日次で再推定する
- 縮小の強さは、Q-VOL・Q-MKT で α = 20、Q-DIR で α = 80 とする
- 点灯型の軸は 0/1 のまま、数値型の軸は学習サンプルで標準化する
- 推定はニュートン法で自前実装し、乱数を使わない
- 寄与は、基準値から |係数 × 値| の大きい順に 1 軸ずつ足したときの確率の増分とする
- 点灯型の軸のうち、学習サンプル中の点灯が 30 回未満のものは「件数不足」と表示する

**根拠・トレードオフ**

- 係数を同時に推定するため、似た軸 (複合パターン軸とその構成パターン、直近 5 日の値幅と当日の値幅など) の効きは係数の間で分け合われ、二重に数えない。相関を無視する A は、軸を足すと過信して成績が悪化した (Q-VOL に市場レベルの軸を足すと改善幅が +0.038 → +0.003)
- L2 正則化で、件数の少ない点灯型軸は自然に係数がゼロに寄る。0/1 の軸を標準化すると、希少な軸の係数がかえって膨らむ
- 検証結果 (評価期間 2026-05-19〜09-25、基準値だけを出した場合との log loss の差):
    - Q-VOL: +0.028 (90% CI +0.021〜+0.036)、AUC 0.63、ECE 0.021。前半・後半・JP・US のいずれでも改善した
    - Q-DIR: 差なし。確率はほぼ基準値 ±5pt に収まり、当面は全件「中立」になる
    - Q-MKT: +0.084 だが評価日数が 169 日と少なく、確率としては信用できない。「参考値」と明示して出す (ADR 2.27)
- α は 5〜80 で成績がほぼ変わらず、選び方に結果が左右されにくい。C は Q-VOL で僅かに良かったが、半減期の選び方に根拠が薄く、局面への追従は基準値の追従 (ADR 2.25) で担うことにした
- 直近 60 日の学習窓は Q-DIR で有意に悪化した。市場別のモデルや市場ダミーは改善しなかった。週次更新は日次とほぼ同じ成績で、計算が軽いので日次にした
- 寄与を「その軸だけを外したときの差」で測ると、確率が基準値から離れるほど合計がずれる (確率 − 基準値 = −21.7pt に対して合計 −17.7pt)。1 軸ずつ足す方式なら合計が必ず「確率 − 基準値」に一致し、「基準値から軸を 1 つずつ足すと確率になる」という説明がそのまま画面に載る。代わりに、各軸の pt は足す順序に依存するので、順序を固定している
- 係数は「点灯時の的中率」と直結しないため、内訳では軸の過去成績 (件数・的中率・基準値との差) を別に集計して並べている
- 評価期間は約 4 か月で、局面は「7 月の荒れ」と「8〜9 月の凪」の 2 つしかない。上の数字は、この局面の切り替わりを含んだ値である。成績画面と定期点検 (ADR 2.30) で確かめ続ける前提にしている
- 買いパターン合致数 ≥ 2 は、評価期間の後半に的中 73% (56 件) と再現したが、学習期間 (3〜7 月) では 48% で効いておらず重みが付かなかった。局面で当たり外れが入れ替わる軸を拾う経路は、成績を溜めて重みを更新し続けることしかない

### 2.25 基準値を直近 60 営業日で追従させ、平常を 20 営業日にした判断

**背景・問題**

検証で最も確率の信頼性を損ねていたのは、合成方式の違いではなく、基準値 (どの軸も効いていないときの確率) が局面でずれることだった。荒れる割合は、局面によって 40% から 24〜33% へ動く。全期間の平均を基準値にすると、これに追従しない。

**決定**

- 基準値は、予測日の時点で採点が確定したサンプルのうち、直近 60 営業日の的中率 (JP・US 合算) とする。20 件未満のときは全期間の的中率を使う
- 合成では、基準値の対数オッズをオフセットとして与え、切片を推定しない。学習時も、各サンプル日の時点の基準値をオフセットにする
- 荒れの判定に使う「平常」は、直近 20 営業日 (基準日を含む) の値幅の平均とする。20 日分の履歴がない銘柄は、荒れの確度を出さない

**根拠・トレードオフ**

- 基準値を直近 60 日にするだけで、基準値そのものの確率としての成績が改善した。方式の選択より、この追従のほうが効いた
- 切片を持たないことで「表示する基準値 = どの軸も効いていないときの確率」が厳密に成り立ち、寄与の合計が「確率 − 基準値」に一致する。切片を推定する形と成績は同等だった (切片を持つと、2pt 程度がどの軸にも帰属しない残差になる)
- 平常を 60 日にすると予測力はやや上がる (Q-VOL の AUC 0.67 vs 0.65) が、平常の追従が遅れるぶん確率が実績からずれる (ECE 0.062 vs 0.037)。確率を表示する以上、信頼性を優先した。20 日なら、稼働開始時・銘柄追加時に確度が出るまでの期間も 40 日短い
- 平常に中央値を使うと「平常より荒れる」割合が 46〜48% になり、問いの意味が変わるため、平均にした

### 2.26 判断軸と問いの対応を固定する判断

**背景・問題**

各軸を、どの問い (Q-DIR 方向 / Q-VOL 銘柄の荒れ / Q-MKT 市場の荒れ) に使うかを決める必要があった。全軸をすべての問いで使い、効くかどうかを重みに任せる案もあった。

**決定**

軸の定義に対象の問いを持たせ、対応を固定する。

- Q-DIR: 単一パターン軸と複合パターン軸
- Q-VOL: 値動きの大きさ軸と、その銘柄の市場の市場レベル軸
- Q-MKT: 市場レベル軸と、市場平均値幅の平常比

追加した軸も、定義した問いにだけ使う。

**根拠・トレードオフ**

- 全軸を Q-DIR に使うと、大きさ系の軸がノイズとして確率を動かし、基準値だけを出した場合より有意に悪化した。正則化でも吸収しきれなかった
- Q-VOL に市場レベルの軸を足すと改善した。銘柄が荒れるかどうかは市場全体の荒れ具合にも左右される。同じ市場の全銘柄で同じ値になるため、「今日は市場全体が荒れている」という説明にもなる
- 新しい軸が想定外の問いで効く可能性は拾えなくなる。その場合は、軸の定義で対象の問いを増やす

### 2.27 中立帯を確率帯の有意差で決め、最小差 3pt を設けた判断

**背景・問題**

確率は大半の銘柄で基準値付近に集まる。基準値に近い確率を「強含み」「荒れそう」と表示すると、手がかりがないのに寄りがあるように見える。中立とみなす範囲を、固定幅で決め打ちするか、過去の実績から決めるかを選ぶ必要があった。

**決定**

- 過去の予測を「確率 − 基準値」で 5pt 刻み (Q-MKT は 10pt 刻み) の帯に分け、各帯の実現率を、その帯の基準値と両側二項検定で比べる (Holm 法で多重比較を補正、有意水準 5%)。件数 30 件 (Q-MKT は 10 件) 未満の帯は判定しない
- 基準値を含む帯から上下それぞれ外側へ進み、最初に「有意」「差の向きが合う」「差が 3pt 以上」を満たした帯から外側を寄りありとする。満たす帯がない側は寄りなしとする
- 稼働開始時に必ず判定し、以後は 30 営業日ごとに、それまでの全予測で判定し直す
- Q-MKT は、市場ごとの採点済み日数が 250 営業日 (約 1 年) に満たない間、「参考値」と明示する

**根拠・トレードオフ**

- 固定幅だと、効く問いでは中立が広すぎ、効かない問いでは寄りが出すぎる。実績から決めれば、効かない問い (Q-DIR) やデータの薄い問い (Q-MKT) では帯が閉じず、自動的に「中立」「平常」に倒れる
- 帯を確率そのものではなく「確率 − 基準値」で持つのは、基準値が局面で動く (ADR 2.25) ため
- 件数が溜まると、1〜2pt の差でも有意になり中立帯が実質なくなる。最小差 3pt はそれを防ぎ、表示上の意味を保つ
- 稼働開始時を模した検証 (2026-06-30〜09-24) では、Q-VOL の中立は 38% で、寄りありの帯の実現率は基準値から明確に離れていた (上側 53% vs 基準値 40%、下側 27% vs 41%)。Q-DIR・Q-MKT は有意な帯がなく、全件「中立」「平常」になった
- Q-MKT は 1 日 1 件 (市場ごと) しか採点が溜まらず、1 年分溜まるまでは確率帯の実績も成り立たない

### 2.28 将来データを使わない判定を名目の引け時刻で行う判断

**背景・問題**

重みは「過去の期間で決めて、その後の期間に当てはめる」を日々ずらしながら行う必要がある (ウォークフォワード)。JP と US は引けの時刻が違い、日付だけで切ると、JP の当日の予測に、US の前日分の答え (US の当日の引けで確定する) が混ざる。また、バッチの遅延や再実行で DB に答え合わせが入っているかどうかは変わるため、DB の状態で判定すると、同じ日の予測でも学習データが変わってしまう。

**決定**

- 市場 M の日付 D の予測に使えるサンプルは、「サンプルの翌営業日の名目引け時刻 ≤ D の M の名目引け時刻」を満たすものに限る。名目引け時刻は取引所マスタのタイムゾーンと取引終了時刻から求める (市場には、属する取引所のうち最も遅いものを使う)
- 基準値・中立帯・標準化・確率帯の実績も、同じ規則で選んだサンプルから作る
- 翌営業日は、市場の観測カレンダー (その市場でいずれかの銘柄に日次サマリーがある日付の集合) の次の日付とする。銘柄の次の足がそれと一致しないとき (データ欠落・売買停止をまたぐとき) は、その日の答え合わせを作らない。翌営業日の |リターン| が 20% を超えるもの (株式分割をまたぐ等) も採点から外す
- 市場は取引所マスタの市場属性で決める (初期設定は JP = TSE、US = NASDAQ・NYSE・AMEX)
- 算出の中核は「その時点までのデータ」だけを受け取る純粋関数にし、全期間のデータを渡した場合と確定していないものを切り落とした場合で出力が一致することをテストで確かめる

**根拠・トレードオフ**

- 時刻の比較だけで判定できるため、処理順や遅延によらず同じ入力から同じ結果が出る。LIVE では US の前日分の採点が終わる前に JP の当日分が走ることがあるが、使えるサンプルは時刻で決まるので混入にならない
- 観測カレンダーで翌営業日を決めると、祝日マスターなしで休場日をまたげる (ADR 2.19)。2 営業日以上の値動きを 1 日分として採点することもない
- 初期値算出で過去データを読むときだけ、休場日のコピー足・途中足を除外する。日次サマリーがこれらを作らなくなった日 (2026-09-28) より前の足が対象である

### 2.29 AI 撤去後は dev でも日次サマリーを生成する判断

**背景・問題**

dev では、DailySummary を prod から複製し、日次サマリー生成と AI 採点のバッチを止めていた。AI 解析・採点という高コストな生成を dev で二重に行わないためである。AI を撤去すると、日次サマリー生成に残る外部呼び出しは株価の取得だけになる。

**決定**

dev でも日次サマリー生成を定期実行し、DailySummary の複製を止める。取引所・ティッカーの複製は続ける。確度の算出も dev で動かす。

**根拠・トレードオフ**

- 複製を止める理由だった高コストな生成がなくなった
- dev の確度は dev のバッチが自前で算出する。乱数を使わず同じ入力から同じ結果が出るため、prod との差は入力データの差だけになる
- 複製済みの履歴に dev が作ったサマリーが続くので、確度の初期値算出にもそのまま使える
- 株価の取得が dev のぶんだけ増える (1 日あたり銘柄数程度)

### 2.30 確度の定期点検をシステムに組み込まず、定期 Issue で行う判断

**背景・問題**

確度が当てにならないときに「中立」「参考値」へ倒す安全装置 (中立帯の見直しなど) は、システム側に組み込んである。それでも、その安全装置が働いているか、局面が変わって軸が効かなくなっていないかは、人が定期的に確かめる必要がある。

**決定**

- GitHub Actions の定期実行で、毎月 1 日に点検 Issue を作る。四半期 (1・4・7・10 月) は Q-MKT の点検も含める。軸を追加したときは、期間ではなく点灯回数 (100 件・400 件) で区切って点検する
- 人がその Issue で Claude Code のセッションを開き、Claude が prod の DynamoDB を読み取りのみで集計して判定する。点検用のスクリプトは置かない
- 点検の手順と異常の基準の値は、点検 Issue のテンプレートが持つ

**根拠・トレードオフ**

- 点検は、結果を見て原因を考え、必要なら別の対応を決める作業である。システムに組み込んで自動判定するより、人と Claude が Issue 上で行うほうが向いている
- 点検の数字は成績画面と同じ集計なので、その場で出せる。スクリプトを置くと、成績画面の集計との二重管理になる
- 頻度は件数で決めた。Q-VOL は 1 か月で約 2,700 件溜まり、確率帯ごとの実績が読める。Q-MKT は市場ごとに 1 日 1 件で、月 1 回では 20 件ほどでぶれしか見えない。軸の判断に要る件数は、100 件で的中率の誤差が約 ±10pt、400 件で約 ±5pt である
- 異常の基準は、結果を見る前に決め、結果を見てから動かさない。後から動かすと、異常を見逃す方向に寄せられるため。基準は dev のさかのぼり (2026-05〜09) に当てはめて確かめた。Q-VOL の基準に当たったのは、荒れが減って言いすぎになった 8 月 (実現率 28% に対して予測平均 36%) だけだった
- 基準の考え方:
    - Q-VOL は、全体のずれ (ECE)、件数 100 件以上の帯のずれ、最上位と最下位の帯の実現率の差 (並べ分け)、基準値の動きで見る。件数の少ない帯のぶれを異常と取り違えないよう、帯は件数で絞る。AUC は確率帯の表から出せず、点検が成績画面と同じ数字で完結しなくなるため使わない。中立の割合は中立帯の見直しで自然に大きく動くので、割合の変化は異常に含めない
    - Q-DIR は、予測力がなく全件が中立になる前提なので、数値の基準を置かない。寄りありが出たら、別の期間でも再現するかを確かめる
    - Q-MKT は、「参考値」の間は数値の基準を置かない。少ない件数に基準を置くと、ぶれを異常と取り違える。「参考値」が外れた最初の四半期点検で、人と基準を決める

## 3. データモデル概要

DynamoDB シングルテーブルで以下のエンティティを管理します。

| エンティティ                 | 説明                        | 主要な属性                                             |
| ---------------------------- | --------------------------- | ------------------------------------------------------ |
| Exchange（取引所）           | 株式市場の取引所            | ID、名前、タイムゾーン、取引時間、データソース（PriceSource）、市場（JP / US） |
| Ticker（ティッカー）         | 個別銘柄                    | ID、シンボル、銘柄名、所属取引所                       |
| Holding（保有株式）          | ユーザーの保有情報          | ユーザーID、ティッカー、数量、平均取得価格             |
| Alert（アラート）            | 価格条件通知設定            | ユーザーID、ティッカー、条件タイプ、目標価格、通知頻度 |
| PushSubscription             | Web Push 購読情報           | ユーザーID、エンドポイント                             |
| DailySummary（日次サマリー） | その日の足と、足から決まる判定 | ティッカー、日付、OHLCV、パターン分析 |
| Forecast（確度） | 銘柄 × 日の予測と答え合わせ | ティッカー、日付、軸の値、問いごとの確率・基準値・中立帯・寄与、採点結果 |
| MarketForecast（市場の確度） | 市場 × 日の予測と答え合わせ | 市場、日付、市場レベル軸の値、Q-MKT の確率、採点結果 |
| ModelSnapshot（重みのスナップショット） | その日の算出に使ったモデル | 問い、算出した市場、日付、重み、標準化、基準値、中立帯、確率帯の実績、軸ごとの成績 |
| PerformanceDaily（日次の成績集計） | 予測日ごとの採点件数の集計 | 問い、市場、日付、軸ごと・確率帯ごとの件数と的中数 |

エンティティ関係:

- ユーザーは複数の Holding・Alert・PushSubscription を持つ
- Ticker は1つの Exchange に属する
- DailySummary は1つの Ticker に対して日付ごとに1件生成される
- Forecast は DailySummary と同じ銘柄 × 日に 1 件作られ、翌営業日に採点結果が追記される
- Exchange は市場 (JP / US) に属し、市場ごとに MarketForecast が日付ごとに 1 件作られる

詳細な PK/SK・GSI 設計はコードを参照してください。
