# 確度の整合性

確度が、同じ入力から同じ結果になり、予測時点で知り得ないデータを使わず、外部のサービスに依存しないための水準。あわせて、確度の当たり具合を人が定期的に確かめる必要があることと、それをシステムに組み込まない理由を書く。

## 要求水準

- **再現性**: 同じ入力データからは、同じ軸の値・重み・確度が得られる。乱数を使わない
- **将来データの混入防止**: 重みの算出と、成績の初期値の算出が、予測時点で確定していないデータを使わない。全期間のデータを渡した場合と、確定していないものを切り落とした場合で、算出の出力が一致することを、テストで確かめられる形にする ([確度算出バッチ](../../specs/batch/forecast.md))
- **外部 AI への依存なし**: OpenAI などの外部 AI サービスを呼ばない。理由は[目的](../purpose.md)の「扱わない範囲」を参照
- **軸の追加の容易さ**: 判断軸の追加で、既存のレコードの移行や、データ構造の作り直しを要しない。既存のレコードに新しい軸の値がなくても、表示と集計は壊れない ([確度](../functional/forecast.md))
- **定期点検の必要**: 確度が当てにならないときに「中立」や「参考値」へ倒す安全装置が働いているか、局面が変わって軸が効かなくなっていないかを、人が定期的に確かめられる。確度は局面によって当たり外れが入れ替わるためである。点検は人が定期の Issue で行う ([定期の Issue 起票](../../../../platform/specs/ci/scheduled-issues.md)。頻度と異常の基準の考え方もそこにある)。点検の数字は、成績画面と同じ集計である ([判断軸の成績](../functional/axis-performance.md))

## やらないこと

- **点検の自動判定のシステムへの組み込み**: 点検は、結果を見て原因を考え、必要なら別の対応を決める作業で、人が Issue 上で行うほうが向いているため。点検用のスクリプトを置くと、成績画面の集計との二重管理にもなる
