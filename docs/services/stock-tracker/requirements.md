# Stock Tracker 要件定義書

この文書は、何を満たすべきか (目的・対象利用者・要件・非機能の目標) を書く。今どう動くかは[仕様カード](../../specs/README.md)にあり、各節からリンクする。

## 1. ビジネス要件

### 1.1 背景・目的

**背景**:
- 株式投資において、タイムリーな価格情報と適切なタイミングでの売買判断が重要
- 既存の finance リポジトリで提供していた株価追跡・通知機能を、本プラットフォームで刷新
- モノレポ構成による開発効率向上、共通インフラ活用によるコスト削減を目指す
- 投資判断の材料は、AI による予測ではなく、機械的に算出できる判断軸と、その過去の成績から出す。AI の予測に予測力がなかったためである (`architecture.md` ADR 2.21)

**目的**:
- リアルタイムな株価データの可視化（チャート表示）
- 条件ベースのアラート・通知による売買タイミングの最適化
- 保有株式の管理と目標価格の算出による投資判断支援
- 日次サマリーで、判断軸から算出した確度 (翌営業日についての確率) と、その出どころ (点灯した軸と各軸の過去成績) を示し、人が検討できるようにする

### 1.2 対象ユーザー

**プライマリーユーザー**:
- 個人投資家（株式トレーダー）
- 日々の株価変動をチェックし、売買判断を行うユーザー

**ユーザー特性**:
- 複数の銘柄を監視している
- 価格条件に基づいた通知を受け取りたい
- 保有株式の平均取得価格と目標価格を把握したい
- モバイル/デスクトップの両方から利用する

### 1.3 ビジネスゴール

**実装済み機能**:
1. **株価の可視化**: リアルタイムな株価データをチャートで表示
2. **通知機能**: 価格条件に基づくアラート通知
3. **保有株式管理**: 平均取得価格、目標価格の算出
4. **確度の提示**: 判断材料の出どころをすべて説明できる状態にし、確度が実際にその確率で当たっているかを継続的に確かめられる

**将来の拡張候補**:
- テクニカル指標の追加（移動平均、ボリンジャーバンドなど）
- ポートフォリオ分析機能

## 2. 機能要件

### 2.1 ユースケース

各ユースケースの今の挙動 (画面の要素、操作、API、バッチの処理手順) は、リンク先の仕様カードを参照する。ここには、何を満たすべきかだけを書く。

#### UC-001: 株価チャート表示

**概要**: ユーザーが指定した取引所・ティッカーの株価チャートを、時間枠を選んで表示する

**アクター**: ログインユーザー

**前提条件**: ユーザーがログイン済み。取引所・ティッカーが登録されている

**満たすべきこと**: Web Push 通知から開いたとき、通知元アラートの取引所・ティッカーが選択済みの状態でチャートを表示する

**今の挙動**: [トップ画面](../../specs/stock-tracker/screen/home.md)、[チャート API](../../specs/stock-tracker/api/chart.md)

#### UC-002: アラート設定

**概要**: ユーザーが株価の条件を設定し、条件達成時に通知を受け取る。アラートの作成・修正・削除は、アラート一覧画面（SCR-003）に加えて、トップ画面（SCR-001）のアラートパネルからも行える。

**アクター**: ログインユーザー

**前提条件**: ユーザーがログイン済み。ブラウザで通知許可が有効

**今の挙動**: [アラート一覧画面](../../specs/stock-tracker/screen/alerts.md)、[アラート API](../../specs/stock-tracker/api/alerts.md)、[Push 通知 API](../../specs/stock-tracker/api/push.md)、[アラート通知の経路](../../specs/stock-tracker/flow/alert-notification.md)

#### UC-003: 保有株式管理

**概要**: ユーザーが保有株式を登録し、平均取得価格をもとに売りの目標価格を決められる。保有株式の作成・修正・削除は、保有株式管理画面（SCR-002）に加えて、トップ画面（SCR-001）の保有株式パネルからも行える。

**アクター**: ログインユーザー

**今の挙動**: [保有株式画面](../../specs/stock-tracker/screen/holdings.md)、[保有株式 API](../../specs/stock-tracker/api/holdings.md)

#### UC-004: 日次サマリー閲覧

**概要**: ユーザーが各取引所に登録されたティッカーの直近の日次サマリーを、確度とあわせて一覧形式で確認する

**アクター**: ログインユーザー（`stocks:read` 権限保持者）

**前提条件**: ユーザーがログイン済み。取引所・ティッカーが登録されている

**満たすべきこと**: 確度がない日付や、確度を算出できなかった銘柄でも、ティッカーの行とチャートは表示する

**今の挙動**: [サマリー画面](../../specs/stock-tracker/screen/summaries.md)、[サマリー API](../../specs/stock-tracker/api/summaries.md)

#### UC-005: 日次サマリー自動生成

**概要**: システムが 1 時間間隔の専用バッチを実行し、各取引所の直近の取引日について、全ティッカーの日次サマリーを自動生成して保存する

**アクター**: システム（EventBridge Scheduler）

**満たすべきこと**:
- 対象日の日足が存在しない日 (祝日などの休場日) は、日次サマリーを作らない。バッチの実行が翌営業日の取引時間中にずれ込んでも、進行中の足ではなく対象日の足を使う (判断は `architecture.md` ADR 2.19)
- エラーが発生しても、当該ティッカー・取引所の処理をスキップして他の処理を継続する
- 保存後に確度の算出 (UC-011) が続く
- サマリーデータ項目は OHLCV (始値・高値・安値・終値・出来高) とパターン分析の結果とする
- アラート用の既存 1 時間バッチ（`hourly`）とは独立した別バッチとして運用する

**今の挙動**: [サマリーバッチ](../../specs/stock-tracker/batch/summary.md)

#### UC-006: 確度の詳細閲覧

**概要**: ユーザーが詳細ダイアログで、1 銘柄の確度を、ふだんの割合・同じ確率帯の過去実績・点灯した軸の内訳とあわせて確認する。表示された確率を信じてよいかと、何が確率を動かしたかを判断できるようにする

**アクター**: ログインユーザー（`stocks:read` 権限保持者）

**前提条件**: ユーザーがログイン済み。日次サマリーが生成済み

**満たすべきこと**: 確度がない場合も、理由を示したうえで、チャートとアラート作成は通常どおり使える

**今の挙動**: [サマリー画面](../../specs/stock-tracker/screen/summaries.md)、[トップ画面](../../specs/stock-tracker/screen/home.md)、[確度 API](../../specs/stock-tracker/api/forecasts.md)

#### UC-007: アラート絞り込み

**概要**: ユーザーがアラート一覧画面で、条件を指定してアラートを絞り込む

**アクター**: ログインユーザー

**前提条件**: ユーザーがログイン済み。アラートが 1 件以上登録されている

**スコープ**:
- フィルタ状態は URL パラメータには反映しない（ページリロード時にフィルタ状態は保持されない。URL 同期が必要な場合は後続 Issue で対応する）

**今の挙動**: [アラート一覧画面](../../specs/stock-tracker/screen/alerts.md)

#### UC-008: チャート自動更新

**概要**: ユーザーがチャート画面で自動更新を有効にすると、一定間隔でチャートデータが再取得・再描画される

**アクター**: ログインユーザー

**前提条件**: ユーザーがログイン済み。取引所・ティッカーが選択済み

**今の挙動**: [トップ画面](../../specs/stock-tracker/screen/home.md)

#### UC-011: 確度の算出と採点

**概要**: 日次サマリーが揃った市場について、前営業日の確度を採点し、重みを更新し、当日の確度を算出する

**アクター**: システム (確度算出バッチ Lambda)

**満たすべきこと**:
- 予測日より前に確定した成績だけから、重み・基準値・中立帯を算出する
- 確度は予測時点の値として記録し、後から書き換えない
- 確度の算出や採点に失敗しても、日次サマリーの保存と表示は継続する
- 稼働開始時は、既存の日次サマリーの履歴から、確度・採点・重みをさかのぼって算出する (既存データは読むだけで書き換えない)。判断軸を追加したときも、同じ方法で過去の成績を算出する方針とする (`architecture.md` ADR 2.22)
- 採点から外すもの (データ欠落や売買停止をまたぐ銘柄、株式分割をまたぐ等の極端なリターン) の考え方は `architecture.md` ADR 2.28

**今の挙動**: [確度算出バッチ](../../specs/stock-tracker/batch/forecast.md)、[確度](../../specs/stock-tracker/term/forecast.md)

#### UC-012: 判断軸の成績閲覧

**概要**: ユーザーが判断軸の成績画面で、全軸の成績と、合成した確度の成績 (確率帯ごとの実績) を問いごとに確認する

**アクター**: ログインユーザー（`stocks:read` 権限保持者）

**前提条件**: 既存認証フローでログイン済み

**今の挙動**: [判断軸の成績画面](../../specs/stock-tracker/screen/axis-performance.md)、[判断軸の成績 API](../../specs/stock-tracker/api/axis-performance.md)

#### UC-010: 一時アラート失効処理

**概要**: システムが毎時バッチを実行し、取引終了後に期限切れとなった一時アラートを無効化して、自動削除の対象にする

**アクター**: システム（EventBridge Scheduler）

**前提条件**: DynamoDB に一時アラートが存在する

**満たすべきこと**:
- 不正なサブスクリプションデータを持つアイテムが存在しても、バッチ全体は停止しない。個別アラートの処理に失敗しても、後続のアラートの処理を継続する
- ログに個人情報（サブスクリプションの endpoint 等）を含めない
- 物理削除は DynamoDB TTL に委ねる (判断は `architecture.md` ADR 2.11)

**今の挙動**: [一時通知アラート失効バッチ](../../specs/stock-tracker/batch/temporary-alert-expiry.md)、[一時通知](../../specs/stock-tracker/term/temporary-alert.md)

#### UC-009: チャート画面統合表示

**概要**: ユーザーが取引所・ティッカーを選択すると、チャートに加えてサマリー・保有株式・アラート情報をチャート画面上に表示する。保有株式パネルおよびアラートパネルからは、トップ画面上で直接 CRUD 操作が可能。

**アクター**: ログインユーザー

**前提条件**: ユーザーがログイン済み。取引所・ティッカーが選択済み

**満たすべきこと**: 保有平均価格とアラートのしきい値を、チャートにオーバーレイして見られる

**今の挙動**: [トップ画面](../../specs/stock-tracker/screen/home.md)

### 2.4 確度の問いと採点

#### 問い

確度は次の 3 つの問いに対して、当日の引け後に出す。答え合わせは翌営業日の引け値で行う (保有期間 1 営業日)。当たりの条件と対象は[問い](../../specs/stock-tracker/term/question.md)を参照する。

| 問い | 確度の意味 |
|---|---|
| Q-DIR 方向 | 銘柄が同じ市場の登録銘柄の平均を上回る確率 |
| Q-VOL 荒れ | 銘柄が平常より荒れる確率 |
| Q-MKT 市場の荒れ | 市場全体が平常より荒れる確率 |

- 方向を同市場平均との差で測るのは、相場全体の上げ下げ (局面) の影響を除いて、銘柄固有の上乗せだけを評価するためである。市場全体が −2% の日に −1% なら「上回った」になる
- 市場の単位は `external-design.md` ADR-010、値幅と平常の決め方は `architecture.md` ADR 2.25

#### 判断軸

判断軸は、当日までの OHLCV (とそこから算出した値) だけを使って機械的に算出できる条件または値とする。軸ごとに、どの問いに使うかを定義として持つ (`architecture.md` ADR 2.26)。軸の種類と一覧は[判断軸](../../specs/stock-tracker/term/axis.md)を参照する。

- 単一軸の重みづけの合計だけでは「重なったときにだけ出る効果」を表せないため、複合パターン軸を独立した軸として持つ
- 特定のパターン同士のペアは軸にしない。件数が少なすぎるうえ、偶然の当たりを拾いやすいためである
- 判断軸は後から追加でき、追加した軸にも同じ採点・重みづけが適用される

#### 合成の要件

- 重みは、予測日より前に確定した成績だけで決める (ウォークフォワード)
- 件数の少ない軸の重みはゼロに寄せる
- 軸同士の相関を考慮して合成する (単純な多数決や合計にしない)
- 局面によって当たり外れが反転するため、重みは固定せず、直近の成績を反映して更新し続ける
- 確度と一緒に、どの軸も効いていないときの確率 (基準値。画面上は「ふだん」) を出し、基準値に近い範囲は「中立」として区別する

具体的な方式は `architecture.md` ADR 2.24〜2.28 を参照。

#### 成績の指標

- 軸ごと・問いごと: 件数 (点灯型なら点灯回数)、点灯時の的中率と基準値との差、Q-DIR は点灯時の平均超過リターン
- 合成した確度: 確率帯ごとの件数と実際の的中率 (「60% と出したものが実際に 6 割当たっているか」)

## 3. 非機能要件

### 3.1 パフォーマンス要件

| 項目                   | 要件                                    |
| ---------------------- | --------------------------------------- |
| チャート表示           | 初回ロード 2秒以内                      |
| 株価データ取得         | 1秒以内                                 |
| 通知遅延               | 条件達成から、アラートの通知頻度の間隔以内 (1 分間隔なら 1 分、1 時間間隔なら 1 時間)。1 時間間隔のアラートは毎時 1 回だけ判定する |
| 同時接続数             | 想定 100ユーザー                       |
| アラート設定入力       | 通知テキスト入力時にアラート設定モーダルの不要な再描画が発生しないこと（通知編集は別ダイアログで独立して管理する） |

### 3.2 セキュリティ要件

**認証・認可**:
- Auth サービス（プラットフォーム共通）による JWT 認証
- ロールベースアクセス制御（RBAC）

**権限の方針**:
- 権限は、閲覧 (`stocks:read`)・自分のデータの書き込み (`stocks:write-own`)・マスタ管理 (`stocks:manage-data`) の 3 つに分け、ロールは `stock-viewer` (ゲストユーザー、デフォルト)・`stock-user` (一般ユーザー)・`stock-admin` (管理者) の 3 つとする。上位のロールは下位の権限を含む
- 保有株式とアラートは利用者ごとに分け、ほかの利用者のものは読み書きできない
- 各権限でできること、ロールとの対応は[権限とロール](../../specs/stock-tracker/term/permission.md)を参照する

**データ保護**:
- HTTPS 通信の強制
- DynamoDB のデータは保存時暗号化
- Web Push サブスクリプション情報の暗号化

**セキュリティ対策**:
- XSS 対策: React の自動エスケープ、CSP ヘッダー
- CSRF 対策: SameSite Cookie
- 入力バリデーション: クライアント・サーバー両方で実施
- 機密情報管理: 外部 API キー (Finnhub 等) は Secrets Manager で管理し、実行環境へ安全に注入する

### 3.3 可用性要件

| 項目               | 要件                           |
| ------------------ | ------------------------------ |
| 稼働率             | 99.5%（ベストエフォート）      |
| RTO (復旧目標時間) | 4時間以内                      |
| RPO (復旧目標時点) | 1時間以内（DynamoDB PITR有効） |

**バックアップ戦略**:
- DynamoDB Point-in-Time Recovery (PITR) 有効化
- 保持期間: 35日間

### 3.4 保守性・拡張性要件

**コード品質**:
- TypeScript strict mode 有効
- ESLint による静的解析
- テストカバレッジ 80%以上（ビジネスロジック）

**モジュール化**:
- core パッケージ: ビジネスロジック（フレームワーク非依存）
- web パッケージ: Next.js UI
- batch パッケージ: Lambda 関数（通知バッチ）

**拡張ポイント**:
- 新しい条件タイプの追加（パターン認識など）
- 判断軸の追加 (テクニカル指標など)
- 新しいチャートライブラリへの切り替え
- 複数の株価データソースへの対応

### 3.5 その他の非機能要件

**スケーラビリティ**:
- Lambda 自動スケール（Web）
- DynamoDB オンデマンドキャパシティ
- EventBridge Scheduler による定期実行（バッチ）

**インフラ**:
- **Web**: Lambda (Web Adapter) + CloudFront
- **Batch**: Lambda + EventBridge Scheduler
- **データストア**: DynamoDB
- **認証**: Auth サービス（本プラットフォーム共通）

**モニタリング**:
- CloudWatch Logs による統一ログ管理
- CloudWatch Alarms によるエラー監視

**障害分離**:
- 確度の算出や採点に失敗しても、日次サマリー (OHLCV・パターン判定) の保存と表示は継続する

**確度の算出**:
- 算出タイミング: 確度は日次サマリー生成と同じタイミング (取引所の引け後) で出す
- 再現性: 同じ入力データからは、同じ軸の値・重み・確度が得られる (乱数を使わない)
- 将来データの混入防止: 重みの算出と成績の初期値算出が、予測時点で確定していないデータを使わないことを、テストで検証できる形にする
- 外部 AI への依存なし: OpenAI など外部 AI サービスを呼ばない
- 拡張の容易さ: 判断軸の追加で、既存レコードの移行やデータ構造の作り直しを必要としない。既存レコードに新しい軸の値がなくても、表示・集計が壊れない

## 4. ドメインオブジェクト

| エンティティ | 説明 |
| ----------- | ---- |
| Exchange（取引所） | 株式が取引される市場（例: NYSE, NASDAQ） |
| Ticker（ティッカー） | 個別銘柄を識別するシンボル |
| Holding（保有株式） | ユーザーが保有する銘柄・数量・平均取得価格 |
| Alert（アラート） | 価格条件に基づく通知設定 |
| PushSubscription | Web Push 通知の購読情報 |
| DailySummary (日次サマリー) | ティッカーごとの、その日の足 (OHLCV) と、足から決まる判定 (パターン分析) |
| 問い (Question) | 確度を出す対象。Q-DIR (方向)・Q-VOL (荒れ)・Q-MKT (市場の荒れ) |
| 判断軸 (Axis) | 機械的に算出できる条件または値。単一パターン軸・複合パターン軸・値動きの大きさ軸・市場レベルの軸がある |
| 確度 (Forecast / MarketForecast) | 問いごと・銘柄 (または市場) × 日の確率と基準値、軸の値と寄与。予測時点の値として残し、翌営業日に採点結果を付ける |
| 重み (ModelSnapshot) | 問いごとに、予測日より前の成績から決まる合成時の重みと、基準値・中立帯・軸ごとの成績 |

## 5. スコープ外

- ❌ テクニカル指標 (移動平均、ボリンジャーバンド、RSI など)。判断軸として後から追加できる仕組みだけを持つ
- ❌ 特定のパターン同士のペアを判断軸にすること
- ❌ 予測タイミングの変更 (米国市場の引け後に翌日の東証を予測する等)
- ❌ サポートレベル・レジスタンスレベル (AI の出力だったため撤去した。機械的な代替は持たない)
- ❌ 確度にもとづく通知 (アラート)
- ❌ ポートフォリオ分析機能
- ❌ 複数の株価データソース対応
- ❌ カスタムアラート条件（JavaScript ベースのカスタム条件式）
- ❌ バックテスト機能
- ❌ AI による解析・予測

## 6. 用語集

確度・基準値 (ふだん)・中立帯・平常・点灯型 / 数値型・寄与は、[確度](../../specs/stock-tracker/term/forecast.md)、[問い](../../specs/stock-tracker/term/question.md)、[判断軸](../../specs/stock-tracker/term/axis.md)を参照する。仕様カードに定義がない語だけをここに置く。

| 用語 | 説明 |
| ---- | ---- |
| Exchange | 取引所（例: NYSE, NASDAQ） |
| Ticker | ティッカーシンボル（例: AAPL, NVDA） |
| Holding | 保有株式 |
| Alert | アラート（価格条件に基づく通知設定） |
| Timeframe | 時間枠（例: 5分足、1時間足、日足） |
| VAPID | Voluntary Application Server Identification（Web Push 認証） |
| Single Table Design | DynamoDB の設計パターン（1テーブルで複数エンティティ管理） |
| 市場 | JP (TSE) と US (NASDAQ・NYSE・AMEX)。同市場平均・市場の荒れの単位 |
| 超過リターン | 翌営業日のリターン − 同日・同市場の登録銘柄の平均リターン |
| 値幅 (レンジ) | (高値 − 安値) ÷ 前営業日の終値 |
| ウォークフォワード | 予測日より前のデータだけで重みを決め、予測日を 1 日ずつずらしながら繰り返す手順 |
| キャリブレーション | 予測した確率と、実際に当たった割合が一致しているかの度合い |
