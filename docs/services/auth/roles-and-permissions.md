# ロール・権限定義

今のロールと権限の一覧は[ロールと権限の定義](../../specs/platform/term/role.md)にある。この文書は、ロール・権限を設計した方針と理由を書く。

## 概要

本ドキュメントは、nagiyu プラットフォームにおけるロールベースアクセス制御 (RBAC) の設計思想を定義します。

## 設計方針

### 1. コードベースでの管理

ロール・権限定義は**コードで管理**し、データベースには保存しません：

**利点:**
- バージョン管理が容易（Git で履歴を追跡）
- デプロイ時に自動的に反映
- 権限変更時のマイグレーション不要
- コードレビューで変更を審査可能

**制約:**
- 新しいロールを追加するにはコードデプロイが必要
- 実行時の動的なロール作成は不可

### 2. 最小権限の原則

ユーザーには業務遂行に必要な**最小限の権限**のみを付与します：

- デフォルトでは権限なし（明示的な付与が必要）
- 複数ロールの組み合わせで柔軟に権限を調整
- 管理者ロール (`admin`) はユーザー管理とロール割り当ての権限を持つため、慎重に付与

### 3. 権限の粒度

権限は**リソース単位**と**アクション単位**で `{resource}:{action}` と定義します。

### 4. 拡張性

Phase 2 以降で追加されるサービス（Logs, Tools 等）の権限も同じ体系で管理します。

## ロールの設計

### admin（管理者）

- 強力な権限を持つため、付与は慎重に行う
- 初期セットアップ時にのみ手動で付与する (→ [デプロイ・運用マニュアル](./deployment.md))

### user-manager（ユーザー管理者）

- ユーザー情報の管理のみを行えるロール。ロール割り当て (`roles:assign`) を持たせないのは、権限昇格を防ぐため
- ロール割り当てには `admin` が必要

### 有料ロール

有料ロールは、課金の権利として付けることを想定したロールである。課金の権利は、Stripe の契約、または支援への手動の付与で付き、出どころと有効期限を持つ。ユーザーの有効なロールは、手動ロールと、期限内で取り消されていない課金の権利のロールを合わせたものになる。

有料ロールと契約はサービスごとに持ち、1 サービスに複数の段を持てる。ロール ID は `{service}-{段名}`、権限は `{service}:{段名}` とする。現在の有料ロールは[ロールと権限の定義](../../specs/platform/term/role.md)と[プランの段](../../specs/auth/term/plan-tier.md)を参照する。

- **サービスと段の上下はロールの定義に持つ**: ロール ID の文字列を解析して決めない。段名から上下は読めず、ID の付け方に縛られないようにするため
- **上の段は下の段の権限を含む**: 既存のロール (stock-user が stocks:read を含むなど) と同じ作り。手動の権利と契約が重なっても、サービスは上の権限から順に見れば段が決まる
- **出し分けは各サービスで決める**: どの機能にどの段の権限を求めるかは、各サービスの対応で決める。ここではロールと権限の名前だけを置く
- **ロール ID は Stripe と揃える**: Stripe の価格の lookup_key は、有料ロールの ID と同じ文字列にする。対応表を持たずに、プランと有料ロールの対応を Stripe 側で変えられるようにするため (→ ADR-013)
- **権利として付けられるのは有料ロールだけ**: 課金の権利は、課金で付くロールを手動ロールと分けて扱うための仕組みなので、付けられるロールを有料ロールに絞る。権限の面では、絞らなくても広がらない。課金の権利を付けられるのは `roles:assign` を持つ管理者で、その人はもともと手動ですべてのロールを付けられるため
- **絞るのは付けるときだけ**: 絞り込みは、権利を付けるとき (API の検証と管理画面の選択肢) にだけ行い、読み取りと有効なロールの算出では行わない。絞り込みより前に付けた有料ロール以外の権利も、読めて有効なロールに載り続ける

### サービス用の手動ロール

運営者が自分で使うために、管理画面から手動ロールとして付けるロール (`quick-clip-unlimited`、`billing-tester`)。有料ロールと違い、課金の権利としては付けない。

- **`billing` を持たない**: 有料ロールの印である `billing` を付けないことで、`PAID_ROLES` に入らない。プランの画面、Stripe の価格の lookup_key、課金の権利の選択肢に出ず、契約や支援の付与で付くことがない。売らず、Stripe と結びつけないため
- **上の段として他の権限を含めない**: 有料の段の並び (standard → pro) の外にあり、`quick-clip:standard` や `quick-clip:pro` を含まない。Quick Clip は `quick-clip:unlimited` を先に見て、プランの権限と両方持っていても使い放題として扱う
- **`billing-tester` は課金の入口を開けるテスト用のロール**: 本番以外では、`billing:test` を持たない利用者は申し込みができない。dev のサンドボックスで、テスト用のカードによって無料のまま有料の段が付くのを防ぎつつ、動作確認する人には決済までの流れを通せるようにする。本番では制限をかけないので、このロールは意味を持たない
- **`admin` に含めない**: テスト用の別アカウントに、ユーザー管理やロール割り当てを含む管理者権限を渡さずに付けられるようにするため (→ [アーキテクチャ](./architecture.md) の ADR-014)

## 実装ガイドライン

- ロール・権限定義は `libs/common/src/auth/roles.ts`、権限チェック関数は `libs/common/src/auth/permissions.ts` に置く。ロール ID は kebab-case、権限は `{resource}:{action}` 形式にする
- 権限チェックはサーバーサイド (API Route と Middleware) で必須とする。クライアントサイドは UI の表示制御のみで、セキュリティ目的では使わない
- ロールが複数ある場合は、全ロールの権限を足し合わせてチェックする

## ユーザーへのロール割り当て

### 初回セットアップ（手動）

プラットフォーム初期セットアップ時、最初の管理者ユーザーを手動で DynamoDB に登録します (→ [デプロイ・運用マニュアル](./deployment.md))。

### 管理画面からの割り当て

Admin サービスではなく Auth のユーザー編集画面から割り当てる。必要な権限は `roles:assign`。操作は[ユーザー編集画面](../../specs/auth/screen/user-edit.md)と[ユーザー API](../../specs/auth/api/users.md)を参照する。

### 課金の権利による付与

有料ロールは、手動ロールとしてではなく、課金の権利として付ける。

- **Stripe の契約**: Stripe の契約に合わせて Auth が権利を付け、更新・解約に合わせて期限を更新・取り消す。管理画面からは変更できない (→ [契約がロールになる経路](../../specs/auth/flow/billing-entitlement.md))
- **手動の付与**: Stripe 以外で受けた支援には、管理者がユーザー編集画面から、期限つきで権利を付ける。必要な権限は `roles:assign`

### ロール変更の監査

**Phase 2 で実装予定:**
- ロール変更は CloudWatch Logs に記録
- 変更者、変更対象、変更前後のロール情報を記録

## セキュリティ考慮事項

### 1. 権限昇格の防止

- ユーザーは自分自身のロールを変更できない仕組みを実装する
- API Route でリクエスト元ユーザー ID と変更対象ユーザー ID を比較する

### 2. ロール検証

- DynamoDB から取得したロールが有効なロール ID であることを検証する
- 不正なロール ID は無視し、警告ログを出力する

### 3. JWT へのロール埋め込み

**メリット:**
- 毎回 DynamoDB を参照せずに権限チェックが可能
- ステートレスで高速

**デメリット:**
- ロール変更が即座に反映されない

**対策:**
- JWT 有効期限を短く設定（30日）。その後、Auth がセッションを読むときに一定時間ごとにロールを DB から読み直すようにした。今の挙動は[セッションのロール](../../specs/auth/term/session-roles.md)を参照
- 緊急時の JWT 無効化機能は Phase 3 で検討

### 4. 監査ログ（Phase 2）

すべての権限チェック結果を CloudWatch Logs に記録：
- ユーザー ID
- 要求された権限
- チェック結果（granted / denied）

## Phase 2 以降の拡張

### Phase 2 で追加予定

- `logs:read` / `logs:write` と、CloudWatch Logs を閲覧できる `log-viewer` ロール。Logs サービスの実装時に追加し、admin にも両権限を加える
- `tools:admin`、`settings:write`、`analytics:read` などの権限

### Phase 3 以降で検討される追加ロール

- `tools-admin`: Tools サービスの管理権限
- `analytics-viewer`: プラットフォーム利用統計の閲覧権限

### リソースレベルの権限（将来検討）

現在はリソース種別単位の権限ですが、将来的に特定リソースへのアクセス制御が必要な場合は、特定のリソース ID に対する読み書きを権限として表現する形を検討します。
