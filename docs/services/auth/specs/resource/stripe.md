# Stripe

Auth が定期課金に使う Stripe のアカウントと、Auth がそのアカウントに求める条件。Stripe の画面の中の設定は、リポジトリの外にある。ここには設定値の写しを持たず、Auth のコードが前提にしていることと、その理由、実物を見る方法を書く。

## リソース

dev は Stripe のサンドボックス、prod は本番のアカウントにつなぐ。どちらにも、次の条件を満たす設定が要る。鍵は[シークレット](./secrets.md)にある。

| Stripe の対象 | Auth が求めること |
|---|---|
| 商品と価格 | 有料ロールの段ごとに、`lookup_key` が有料ロールの ID の価格がある |
| 顧客 | Auth が作る。顧客の `metadata.userId` がユーザーの `userId` |
| 契約 | 1 品目 |
| 通知の受け口 | `/api/billing/webhook` を、契約に関わるイベントで登録する |
| Customer Portal の設定 | 段の切り替え (上げ) を開き、段の価格を切り替え先に入れる |
| 契約の予約 (Subscription Schedule) | 下げのとき Auth が作る。メタデータ `createdBy` が `nagiyu-auth` |

## 設定値

実物は、Stripe の管理画面で見る。

### 価格

| 条件 | 内容 |
|---|---|
| `lookup_key` | 有料ロールの ID ([プランの段](../term/plan-tier.md)に一覧がある)。プランの画面の価格の取得も、契約からロールを決めるのも、この値で行う |
| 状態 | 有効 (active) な価格だけを引く。アーカイブした価格は引かない |
| 繰り返し | 繰り返し (recurring) の価格にする。下げの予約は、繰り返しのない価格を行き先にできない。運用では 1 か月ごとにしている |
| 金額 | 税込みの金額で作る。プランの画面が、金額に「(税込)」を付けて出す |
| 商品 | 段ごとに別の商品にする。商品の説明は、段の説明としてプランの画面と決済画面に出る。空なら出ない。プランの画面は改行を反映しないので、1 段落で書く |

- 有料ロールの ID でない `lookup_key` の価格で契約した品目は、無視して警告をログに残す。権利は付かない
- 機能 (Entitlements) は使わない。付くロールは、契約の品目の価格の `lookup_key` だけで決まる
- 売らないサービスの価格が、`lookup_key` つきで残っていると、プランの画面にそのサービスが出る
- 金額はコードにも docs にも持たない。金額を決めた値は、サンドボックスの価格にある

### 顧客と契約

- 顧客は、Auth が初めての申し込みで作り、`email`・`name`・`metadata.userId` を入れる。Stripe の画面で作った顧客では、同期が対応するユーザーを見つけられない
- 通知を受けたら、顧客の `metadata.userId` が指すユーザーの `StripeCustomerId` が、その顧客と一致するときだけ同期する ([ユーザーテーブル](../data/users.md))。メールアドレスは紐づけに使わないので、変わっても契約は切れない
- 権利を付けるのは、状態が `active`、`trialing`、`past_due` の契約だけ
- 契約は 1 品目にする。上げを送る Customer Portal の確認画面は、品目が 1 つの契約しか扱えず、下げの予約も先頭の品目だけを見る

### 通知の受け口

| 項目 | 内容 |
|---|---|
| URL | dev は `https://auth.dev.nagiyu.com/api/billing/webhook`、prod は `https://auth.nagiyu.com/api/billing/webhook` ([デプロイ先](../deploy.md)のホスト名) |
| 署名鍵 | 受け口を作ると出る署名シークレット。`nagiyu-auth-stripe-{env}` の `webhookSecret` に入れる |

- 受け口は、イベントの種類を見ない。通知の対象に顧客があれば、その顧客の契約を Stripe から取り直して権利に反映する。顧客がないイベントは何もせず成功を返す ([Stripe 通知 API](../api/billing-webhook.md))
- 契約の状態が変わるときに届く、次のイベントを登録する
    - `checkout.session.completed`
    - `customer.subscription.created`、`customer.subscription.updated`、`customer.subscription.deleted`
    - `subscription_schedule.created`、`subscription_schedule.updated`、`subscription_schedule.released`、`subscription_schedule.canceled`、`subscription_schedule.completed` (Auth が作る下げの予約に関わるもの)

### Customer Portal

Auth は、設定を指定せずに Portal の画面を作る。そのため、Stripe の既定の Portal の設定が使われる。

| 条件 | 理由 |
|---|---|
| 解約・支払い方法の変更・請求の履歴を開く | 「契約を管理」から行う操作 |
| プランの切り替えを開き、切り替えの対象に段の商品と価格を入れる | Auth が上げを送る確認画面は、ここに入っている価格にしか切り替えられない |
| 比例配分をオンにして、即時に請求する | 上げは、差額を日割りで即時に請求する。日割りの扱いは Portal の設定で決まり、Auth は指定しない |
| 解約は期間の終わりに効かせる | プランの画面と特定商取引法に基づく表記が、解約しても期間の終わりまで使えると案内している |
| 下げ (費用のみが減少する変更) は、請求期間の終了時に適用する | 利用者は「契約を管理」から Portal の一般の切り替えでも下げられる。すぐに適用にすると、日割りのクレジットが出て、下げは期末から・返金なしという案内と食い違う |
| 顧客情報は名前とメールアドレスだけを更新できるようにする | 領収書の宛名と届け先を本人が直せるようにする。住所と電話番号はデジタルのサービスで使わないので、預からない |

## 理由

- 価格の `lookup_key` を有料ロールの ID にそろえる。対応表を持たずに済み、プランと有料ロールの対応を Stripe の管理画面で変えられる。価格を Stripe に持つのは、価格と説明の文言が Stripe の 1 か所になり、表示が Stripe と食い違わないため ([プランの段](../term/plan-tier.md))
- 通知の中身は合図としてだけ使い、毎回 Stripe から取り直して権利を上書きする。通知は順序が保証されず、重複して届くことがあり、失敗すると最大 3 日間再送される。届いた順に適用すると、Stripe の状態と食い違う。取り直せば、重複・順序の入れ替わり・再送のいずれでも、最終的に Stripe の状態と一致する ([契約がロールになる経路](../flow/billing-entitlement.md))
- 下げは Auth が予約し、Portal の下げの設定に任せない。Portal が下げを期末に効かせられるのは、同じ商品の価格どうし (実質は月払いと年払いの間) に限られる。段ごとに商品を分けているので、別の商品の間の下げは、すぐ効いて日割りのクレジットが出る。それでも Portal の下げの設定を期末にするのは、利用者が「契約を管理」から Portal の一般の切り替えで下げることもあるため。ただし、別の商品の間の下げにこの設定が効くかは確かめていない
- 上げを Portal の確認画面に残すのは、即時の請求で起きる支払いの失敗や 3D セキュアを、自作せずに Stripe に扱わせるため。切り替え先を Auth が決めるのは、Portal の一般のプラン変更に任せると、2 つ目のサービスが売り始めたとき、別のサービスの商品へも切り替えられてしまうため
- 予約が付いている間は、Portal で変更も解約もできない (Stripe の仕様)。下げが効いた後も、予約は 1 請求期間付いたまま残る。下の段の段階の終わりを指定しなくても、Stripe が 1 請求期間の終わりを入れるため。Portal から下げたときも同じで、Auth では外さない。サンドボックスのテストクロックで、切り替わった後も契約の `schedule` に予約が残ることを確かめた。残っている間に上げや解約が断られるかは確かめていない
- 返金の仕組みは Auth に持たない。返金は Stripe の管理画面から手で行う (返金の方針は[法務の文書](../../../../platform/specs/lib/ui/legal.md)にある)

## 手順

### 本番の Stripe を有効化する

Stripe の事業者の情報 (公開用の事業者名・サポートの連絡先) は、本番環境を有効化してからでないと設定できない。サンドボックスとは別に、本番の環境で次を用意する。本番の審査では料金が本番のサイトに出ている必要があるため、有効化の申請を出したら、審査を待たずに 1 から 4 まで進めて、プランの画面に価格を出す。

1. **商品と価格**: 上の「価格」の条件で、段ごとに商品を作り、それぞれに 1 か月ごとの価格を付ける。金額は、サンドボックスの各価格を見て同じにする。本番の有効化のときにサンドボックスから商品をコピーできるが、コピーするのは本番で売るサービスの商品だけにし、コピー後に `lookup_key` が付いているかを確かめる
2. **Customer Portal**: 上の「Customer Portal」の条件で設定する
3. **通知の受け口**: 上の「通知の受け口」の URL とイベントで登録する。作ると出る署名シークレットを 4 で使う
4. **鍵**: 本番の秘密鍵と、受け口の署名鍵を `nagiyu-auth-stripe-prod` に入れ、Auth を再デプロイする ([Stripe の鍵を設定する](./secrets.md#stripe-の鍵を設定する))
5. **表記の URL とビジネスのサイト**: 特定商取引法に基づく表記のページ (`https://auth.nagiyu.com/legal/tokushoho`) の URL を Stripe に登録する。本番の審査で確かめられる。申請のビジネスのウェブサイトには、売っているサービスのページを入れる。Portal (技術ブログ) は、サービス・プランの画面・表記のどれにもつながっておらず、審査で売っているものと価格にたどり着けない
6. **新しい購入のメール通知**: Stripe のダッシュボード (本番) で、コミュニケーション設定 (Communication preferences) の「Payment receipts」にある「Successful payment receipt」のメールを有効にする。運営者が新しい購入を知るための設定で、Auth にはこのための仕組みを持たない。顧客への領収書のメール (設定 → 顧客へのメール) とは別の設定で、そちらは顧客に届くものなので、これでは通知されない。更新の支払いの失敗に気づけるよう、「Failed payments」のメールも有効にする。Stripe のメニューの場所は変わりうるため、見つからなければ設定の検索で「Communication preferences」を探す
7. **動作の確認**: 自分のカードで本番の決済を試さない。本物の支払い方法で本番を試すことは Stripe の利用規約で禁じられている ([Stripe のテストの案内](https://docs.stripe.com/testing))。少額の割引で試しても、日本円は 50 円未満だと請求されず、決済を確かめられない。代わりに、100% 割引のクーポンで 0 円の契約を作って、通知からロールが付くまでを確かめる。支払い成功のメールと決済そのものは、最初の本物の購入で確かめる
    1. 確かめに使うアカウントでプランの画面から申し込みを押し、決済画面を閉じる。これで、そのユーザーに紐づいた Stripe の顧客ができる。Auth は顧客に付けたユーザー ID で同期するので、Stripe の画面で顧客を作るのでは確かめられない
    2. 100% 割引・期間 1 回のクーポンを作り、その顧客に段の契約をクーポン付きで作る。支払い方法は請求書の送信にすると、カードが要らない
    3. そのアカウントに段のロールが付き、プランの画面に契約中と出ることを確かめる
    4. 契約を解約し、クーポンを削除する。期間 1 回のクーポンを残したまま契約が続くと、次の更新で正規の金額が請求される

### 価格を変える

Stripe の価格は、一度使われると金額を変えられない。金額を変えるときは、同じ商品に新しい価格を作り、`lookup_key` を古い価格から新しい価格へ移す (API なら、価格を作るときに `transfer_lookup_key` を指定すると移せる)。古い価格はアーカイブしてよい。

- プランの画面と申し込みは、`lookup_key` で価格を引くので、移した時点から新しい金額になる。コードの変更も Auth の再デプロイも要らない
- すでに古い価格で契約している利用者は、古い価格のまま更新され続ける。移すかどうかは別に判断し、移すなら Stripe 側で契約の価格を切り替える
- 金額を変えたら、プランの画面と特定商取引法に基づく表記の案内 (表記は金額を持たず、プランの画面へ案内している) に食い違いが無いかを確かめる

### 下げの予約が残っているとき

段を下げると、下げが効いた後も 1 請求期間、契約に予約が付いたまま残る。その間に利用者が上げや解約をできずに困ったら、Stripe の管理画面で、その契約の予約を解除 (release) する。契約の中身は変わらない。望まない次の期間分が請求されていたら、返金する (→ 「返金する」)。

その間に上げや解約が実際に断られるかは確かめていない。確かめるときは、サンドボックスのテストクロック (管理画面の「シミュレーション」) で顧客と上の段の契約を作り、期間の終わりに下の段へ切り替わる更新をスケジュールしてから、切り替わった後まで時間を進める。契約の `schedule` に予約が残っている状態で、Customer Portal や管理画面から上げ・解約ができるかを見る。

### 返金する

Stripe の管理画面から手で返金する。Auth には返金の仕組みを持たない。

### 契約中のユーザーを削除する・Stripe の顧客を削除する

契約中のユーザーの削除は[ユーザー API](../api/users.md)、Stripe で顧客を削除したあとの対応の取り外しは[ユーザー編集画面](../screen/user-edit.md)にある。
