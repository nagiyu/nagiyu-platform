# Auth サービス 要件定義書

この文書は、何を満たすべきか (目的・対象利用者・要件・非機能の目標) と、その判断の理由を書く。今どう動くか (画面・API・経路・用語) は[仕様カード](../../specs/README.md)にあり、各節からリンクする。

---

## 1. ビジネス要件

### 1.1 背景・目的

nagiyu プラットフォームは複数のサービス (admin, logs, tools 等) で構成されており、各サービスで統一された認証・認可機能が必要です。Auth サービスは、プラットフォーム全体の認証・認可を一元管理し、シームレスなユーザー体験を提供します。

**課題**:
- 各サービスで個別に認証機能を実装するとコストが増大
- 認証情報の一貫性が保てない
- セキュリティポリシーの統一管理が困難

**解決策**:
- Auth サービスで認証・認可を集約
- JWT トークンを用いたステートレス認証
- サブドメイン全体でのシングルサインオン (SSO)

**課金の入口**:

プラットフォームには、運営コストのかかる機能がある (外部の AI の呼び出し、動画の処理など)。一方で、収益の手段はなかった。認可はロール単位で行っているため、Auth サービスは課金を「ロールを付け外しする入口の一つ」として扱う。こうすると各サービスは、権限チェックの作りを変えずに、有料ユーザーの操作範囲を広げられる。各サービスで何を有料にするかは、Auth サービスでは扱わない。

### 1.2 対象ユーザー

#### プライマリーユーザー
- **プラットフォーム管理者**: ユーザー管理、ロール割り当てを行う。支援サービスなど Stripe 以外で受けた支援に、期限つきで有料ロールを付ける
- **エンドユーザー**: Google アカウントでログインし、各サービスを利用。有料プランに申し込む人もいる

#### セカンダリーユーザー
- **開発者**: Auth サービスのAPIを利用して他サービスを実装
- **運用担当者**: デプロイ、監視、障害対応を実施

### 1.3 ビジネスゴール

#### Phase 1 の目標
1. **認証基盤の確立**: Google OAuth による安全な認証機能を提供
2. **SSO 実現**: 一度のログインで全サービスにアクセス可能
3. **ユーザー管理**: プラットフォーム共通のユーザー情報管理
4. **ロール・権限管理**: 管理者とユーザーを区別し、適切なアクセス制御

#### Phase 2 以降の目標
- 複数 OAuth プロバイダー対応 (GitHub 等)
- パスワード認証の追加
- 多要素認証 (MFA) の実装
- 監査ログ機能

#### 課金の目標
1. **運営コストの回収**: 運営コストの一部を、利用者の課金で回収できるようにする
2. **出し分けの土台**: 各サービスが、有料ロールを見るだけで無料と有料の出し分けを作れるようにする
3. **手動の付与**: Stripe との連携とは別に、手動の付与でも有料の運用ができるようにする

## 2. 機能要件

### 2.1 ユースケース

各ユースケースの今の挙動 (画面の要素、操作、API の入出力・エラー、経路の手順) は、リンク先の仕様カードを参照する。ここには、何を満たすべきかと、その理由だけを書く。

#### UC-001: Google アカウントでログイン

- **概要**: ユーザーが Google アカウントを使用してプラットフォームにログインする
- **アクター**: エンドユーザー
- **前提条件**: ユーザーが Google アカウントを所持している
- **満たすべきこと**: Phase 1 では Google OAuth のみ。Google の認証やユーザーの作成に失敗したときは、エラーを示す
- **今の挙動**: [サインイン画面](../../specs/auth/screen/signin.md)、[サインインの経路](../../specs/auth/flow/sign-in.md)、[認証エラー画面](../../specs/auth/screen/auth-error.md)

#### UC-002: 他サービスへのシングルサインオン

- **概要**: Auth サービスでログイン後、他サービスに自動的にログインできる
- **アクター**: エンドユーザー
- **前提条件**: Auth サービスでログイン済み (JWT クッキーが存在)
- **満たすべきこと**: 各サービスは JWT クッキーを検証し、無効なら Auth サービスのログインページへ送る。JWT の有効期限が切れたら再ログインが必要になる
- **今の挙動**: [サインインの経路](../../specs/auth/flow/sign-in.md)、[システム系の API](../../specs/auth/api/system.md)

#### UC-003: ユーザー一覧の閲覧

- **概要**: 管理者がプラットフォームに登録されているユーザー一覧を閲覧する
- **アクター**: 管理者 (`users:read` 権限を持つユーザー)
- **前提条件**: ログイン済み、`users:read` 権限を所持
- **満たすべきこと**: 権限不足の場合、URL を変えずに権限なしの画面を表示する
- **今の挙動**: [ユーザー一覧画面](../../specs/auth/screen/users.md)、[ユーザー API](../../specs/auth/api/users.md)

#### UC-004: ユーザー情報の編集とロール割り当て

- **概要**: 管理者がユーザーのロールを変更する
- **アクター**: 管理者 (`roles:assign` 権限を持つユーザー)
- **前提条件**: ログイン済み、適切な権限を所持
- **満たすべきこと**:
    - 権限不足の場合、URL を変えずに権限なしの画面を表示する
    - 対象のユーザーが存在しない場合、「ユーザーが見つかりません」を表示する
    - 自分自身のロールを変更しようとした場合は、エラーにする
    - 最後の管理者がいなくならないようにする (管理者がいなくなると、復旧は DynamoDB の直接の書き換えだけになる)。ロールを外す操作と、ユーザーの削除の両方に適用する
- **今の挙動**: [ユーザー編集画面](../../specs/auth/screen/user-edit.md)、[ユーザー API](../../specs/auth/api/users.md)

#### UC-005: サインアウト

- **概要**: ユーザーがログアウトする
- **アクター**: エンドユーザー
- **前提条件**: ログイン済み
- **満たすべきこと**:
    - いずれかのサービス (Auth 自身を含む) のヘッダーから、Auth サービスのサインアウト確認画面を経てサインアウトし、ログアウトを始めたサービスに戻る。確認画面でキャンセルすると、サインアウトせずに元のサービスへ戻る
    - 戻り先が nagiyu のサービス以外の URL の場合、その URL へは戻さず Auth サービスへ戻す
    - サインアウトは、クッキーの発行元である Auth サービスに集約する。各サービスは自前でサインアウトを受け付けず、Auth サービスのサインアウトへ遷移させる
- **今の挙動**: [サインアウト確認画面](../../specs/auth/screen/signout.md)、[戻り先](../../specs/auth/term/callback-url.md)

#### UC-006: 有料プランに申し込む

- **概要**: 利用者が自分で有料プランに申し込み、有料ロールを得る
- **アクター**: エンドユーザー (ログイン済み)
- **前提条件**: 申し込むサービスに、有効な契約がない (サービス内の別の段の契約も含む)
- **満たすべきこと**:
    - 決済の入力は Stripe の決済画面 (Checkout) で行う。支払いを終えて戻ったら、Stripe から契約を取り直して課金の権利に反映し、ロールを再取得してから元のサービスへ戻る。この時点で有料ロールが有効になっている
    - 決済画面で中止した場合は、何も変わらずプランの画面に戻る
    - 未ログインの場合は、ログインへ案内する
    - 同じサービスの有効な契約がある場合は、別の段でも新たに申し込ませず、プランの画面の段の切り替えへ案内する
    - 課金が有効になっていない場合は、価格と操作の代わりに準備中と表示する
    - 本番以外では、テスト用のロール (`billing-tester`) を持たない利用者 (未ログインを含む) は申し込めない。画面は導線を出さずにその旨を表示し、申し込みの API も断る (→ ADR-014)。契約の管理は変えない
    - 2 つのタブで決済画面を開き、両方で支払った場合に限り、同じプランの契約が 2 件できる。現実的に起きないものとして許容している
- **今の挙動**: [プラン画面](../../specs/auth/screen/plans.md)、[課金 API](../../specs/auth/api/billing.md)、[契約がロールになる経路](../../specs/auth/flow/billing-entitlement.md)

#### UC-007: 契約を管理する

- **概要**: 契約中の利用者が、解約・支払い方法の変更・請求の確認を自分で行う
- **アクター**: エンドユーザー (ログイン済み・Stripe の顧客を持つ)
- **満たすべきこと**:
    - Stripe の Customer Portal で行う
    - 解約した場合も、支払い済みの期間の終わりまでは有料ロールが有効なままになる
    - Stripe の顧客を持たない利用者には「契約を管理」を表示しない
- **今の挙動**: [プラン画面](../../specs/auth/screen/plans.md)、[課金 API](../../specs/auth/api/billing.md)

#### UC-008: 契約の変化が自動で反映される

- **概要**: 契約・更新・解約・支払い失敗が、利用者の操作なしに課金の権利へ反映される
- **アクター**: システム (Stripe からの通知)
- **満たすべきこと**:
    - 通知の署名を検証し、通知から Stripe の顧客を特定する。署名を検証できない通知は処理しない
    - その顧客の最新の契約を Stripe から取り直し、Stripe 由来の課金の権利を書き換える。次のロール再取得のときに、利用者の有効なロールが変わる
    - 通知の顧客が Auth のユーザーと結びつかない場合は、何もせず成功を返す (再送されても結果は同じため)
    - 通知が遅れる・重複する・順序が入れ替わる・取りこぼされる場合も、最終的には Stripe 上の最新の状態に一致する
    - 書き換えに失敗した場合は失敗を返し、Stripe に再送させる
- **今の挙動**: [Stripe 通知 API](../../specs/auth/api/billing-webhook.md)、[契約がロールになる経路](../../specs/auth/flow/billing-entitlement.md)

#### UC-009: 課金の権利を手動で付ける

- **概要**: 管理者が、Stripe 以外で受けた支援 (pixiv FANBOX など) に対し、期限つきで有料ロールを付ける
- **アクター**: 管理者 (`roles:assign` 権限を持つユーザー)
- **前提条件**: ログイン済み、`roles:assign` 権限を所持
- **満たすべきこと**:
    - 付ける有料ロールと有効期限を指定して、課金の権利を足せる。必要なら、既存の手動の権利の期限を変える、または取り消せる。変更は手動ロールの変更と一緒にまとめて保存される
    - 期限が過ぎた権利は、管理者が何もしなくても無効になる
    - Stripe 由来の権利は表示だけで、変更できない。Stripe 上の契約と食い違わないようにするため
    - 取り消した権利は変更できない。新しい期限が現在より前の場合は、エラーにする
    - 他の更新と競合した場合は、再読み込みを促す
- **今の挙動**: [ユーザー編集画面](../../specs/auth/screen/user-edit.md)、[ユーザー API](../../specs/auth/api/users.md)、[課金の権利](../../specs/auth/term/role-grant.md)

期限の変更は、新しい期限が現在より後なら、延長・短縮・期限切れからの復活のいずれも許す。日付の入れ間違いを直せるようにし、支援を再開した人を同じ権利で扱えるようにするためである。途切れていた期間は記録に残らない。

#### UC-010: Stripe の顧客との対応を外す

- **概要**: Stripe で顧客を削除したとき、管理者がユーザーと Stripe の顧客の対応を外す
- **アクター**: 管理者 (`roles:assign` 権限を持つユーザー)
- **前提条件**: 対象のユーザーが Stripe の顧客と結びついている
- **満たすべきこと**: 対応を外すと同じ書き込みで、Stripe 由来の有効な課金の権利も取り消す。対応がないユーザーの場合は、エラーにする
- **今の挙動**: [ユーザー編集画面](../../specs/auth/screen/user-edit.md)、[ユーザー API](../../specs/auth/api/users.md)

Stripe で顧客を削除すると、Auth には削除済みの顧客 ID が残り、その利用者の申し込みと契約の管理が失敗し続ける。これを解くための操作である。対応が外れると、この先の通知で権利を書き換えられなくなるため、Stripe 由来の権利も一緒に取り消す。Stripe 上の顧客と契約には触れない。

#### UC-011: 課金に関する公開情報を見る

- **概要**: 誰でも、ログインせずに料金と特定商取引法に基づく表記を確認できる
- **アクター**: エンドユーザー (ログイン不要)
- **満たすべきこと**: プランの内容・価格・支払いと解約の条件を確認できる。課金が有効になっていない間も、特定商取引法に基づく表記は表示する
- **今の挙動**: [プラン画面](../../specs/auth/screen/plans.md)、[特定商取引法画面](../../specs/auth/screen/tokushoho.md)

#### UC-012: 契約の段を切り替える

- **概要**: 契約中の利用者が、同じサービスの別の段に変える
- **アクター**: エンドユーザー (ログイン済み・そのサービスに有効な契約がある)
- **満たすべきこと**:
    - 上げは、Stripe の Customer Portal の確認画面で日割りの金額を確認して確定する。すぐ上の段が有効になり、差額が日割りで即時に請求される
    - 下げは、Auth の画面で切り替わる日を確認して確定する。請求期間の終わりに下の段へ切り替わる予約ができ、返金はない。それまでは今の段のまま使える
    - 確認画面で中止した場合は、何も変わらずプランの画面に戻る
    - 解約予約中、または下げの予約中は、段の切り替えを出さない
    - 支払いを確認できていない契約 (past_due) では、切り替えを断る。上げると未払いの請求に差額が重なり、未払いのまま上の段が付きうるため
    - 支払いの失敗や 3D セキュアは、Stripe の確認画面が扱う
- **今の挙動**: [プラン画面](../../specs/auth/screen/plans.md)、[課金 API](../../specs/auth/api/billing.md)、[プランの段](../../specs/auth/term/plan-tier.md)

#### UC-013: 下げの予約を取り消す

- **概要**: 下げを予約している利用者が、予約を取り消して今の段を続ける
- **アクター**: エンドユーザー (ログイン済み・下げの予約がある)
- **満たすべきこと**: 予約が取り消され、契約は今の段のまま残る。予約が付いている間は Customer Portal で変更も解約もできない (Stripe の仕様) ため、解約や別の変更をしたいときは、先にこの操作で取り消す
- **今の挙動**: [プラン画面](../../specs/auth/screen/plans.md)、[課金 API](../../specs/auth/api/billing.md)

## 3. 非機能要件

### 3.1 パフォーマンス要件

| 項目               | 要件                                    |
| ------------------ | --------------------------------------- |
| 応答時間           | 95パーセンタイルで 2秒以内              |
| OAuth ログイン時間 | 5秒以内 (Google API 依存)               |
| JWT 検証時間       | 100ms 以内 (署名検証のみ)               |
| DynamoDB 応答時間  | 100ms 以内 (オンデマンド課金)           |
| 課金の権利の反映   | 既存のロール再取得と同じ契機で反映される。決済直後は、元のサービスへ戻った時点で反映されている |
| Stripe の通知の処理 | Stripe が応答を待つ時間内に結果を返す  |

### 3.2 セキュリティ要件

#### 認証・認可
- **OAuth プロトコル**: OAuth 2.0 に準拠
- **JWT の保護**: Auth.js の既定の方式で暗号化する。秘密鍵は Secrets Manager で管理する
- **クッキー属性**: HttpOnly, Secure, SameSite=Lax
- **権限チェック**: サーバーサイドで必須実施

#### データ保護
- **DynamoDB 暗号化**: AWS KMS による暗号化 (At Rest)
- **通信暗号化**: HTTPS 通信 (In Transit)
- **シークレット管理**: AWS Secrets Manager で管理

#### セキュリティ対策
- **CSRF 対策**: state パラメータ、SameSite クッキー
- **XSS 対策**: React の自動エスケープ、DOMPurify
- **権限昇格防止**: 自分自身のロールを変更不可。最後の管理者を外す・削除することも不可

#### 課金
- **カード情報**: Auth サービスでは受け取らない。入力は Stripe の決済画面と Customer Portal で行う
- **通知の検証**: Stripe からの通知は署名を検証してから処理する。検証できないものは処理しない
- **手動の変更**: 課金の権利の手動変更と、Stripe の顧客の対応の解除は、roles:assign 権限を持つ管理者に限る
- **鍵の管理**: Stripe の秘密鍵と通知の署名鍵は、既存の秘密情報と同じく Secrets Manager で管理し、リポジトリに置かない
- **本人の分だけ**: 申し込みと契約の管理は、ログイン中の本人の分だけを扱う。戻り先は nagiyu のサービスの URL に限る
- **本人に見せる範囲**: 本人向けのユーザー情報では、課金の権利のメモと、権利を付けた管理者を返さない

### 3.3 可用性要件

| 項目               | 要件                                    |
| ------------------ | --------------------------------------- |
| 稼働率             | 99.9% (AWS SLA に準拠)                  |
| Multi-AZ           | DynamoDB, Lambda は自動的に Multi-AZ    |
| 復旧目標時間 (RTO) | 30分以内                                |
| 復旧目標時点 (RPO) | 5分以内 (DynamoDB Point-in-Time Recovery) |
| Stripe の障害時    | すでに付いている課金の権利と、それに基づく有料ロールは影響を受けない |
| 通知の処理の失敗   | 失敗を返して Stripe に再送させ、最終的に反映される |

### 3.4 保守性・拡張性要件

#### コード品質
- TypeScript strict mode 必須
- テストカバレッジ 80%以上
- ESLint, Prettier による自動チェック

#### モジュール化
- ロール・権限定義はコードで管理 (`libs/common/src/auth/`)
- NextAuth.js を使用し、OAuth プロバイダー追加が容易

#### 拡張ポイント
- OAuth プロバイダーの追加 (GitHub, メールアドレス認証等)
- 新しいロール・権限の追加
- Phase 2 以降での監査ログ機能追加
- 課金の権利の出どころの追加 (Stripe と手動のほか、支援サービスとの連携など)
- 有料ロールと Stripe の商品の対応、価格は、コードを変えずに Stripe 側で変えられる
- 各サービスは、有料かどうかを既存の権限チェックで判定する。課金のための専用の判定をサービスに持たせない

### 3.5 その他の非機能要件

#### スケーラビリティ
- Lambda 同時実行数: 自動スケール (最大1000)
- DynamoDB: オンデマンド課金で自動スケール

#### データ保持
- ユーザーデータ: 無期限 (削除されるまで)
- CloudWatch Logs: 30日 (dev), 90日 (prod)

#### 互換性
- ブラウザ: Chrome, Safari, Firefox の最新版をサポート
- モバイル: iOS Safari, Android Chrome をサポート
- dev 環境は develop の版と integration の版が後勝ちで上書きし合う。どちらの版が動いても、もう一方の版が書いたデータでエラーにならない

#### プライバシー
- ログインせずに見られるページから、運営者の本名・住所・電話番号にたどり着けない。特定商取引法に基づく表記では、これらを「請求があれば遅滞なく開示いたします」とする
- Stripe が送る領収書メールには、正式な事業者名 (個人では本名) とサポート用の住所が必ず載る。払った本人にだけ見える範囲なので、許容している

権限が足りない場合は、URL を変えずにその画面の位置で権限なしの画面を表示する。

### 4.2 画面の設計判断

画面の要素・インタラクション・状態は仕様カードにある。ここには、要件として求めることと、画面を設計した理由だけを書く。

#### サインインページ

- ログイン済みの場合は別ページへリダイレクトする

#### ユーザー一覧ページ

- ロールは ID ではなく名前で表示する。ID は管理者が読んでも意味を取りにくいため。定義に無い ID は表示が消えないよう ID のまま表示する

#### ユーザー編集ページ

- **課金の権利を並べる理由**: 手動ロールの編集と同じ画面に置き、「このユーザーの有効なロールがなぜそうなっているか」を 1 画面で読めるようにする。Stripe 由来の権利は表示だけにする (API でも変更を拒否する)
- **取得に失敗したとき**: 見出しと「ユーザー一覧へ戻る」は表示したままにし、画面の文脈と戻り道を失わせない。対象のユーザーが存在しない場合と、それ以外の取得の失敗は表示を分ける。再試行で直るかどうかが違うため

#### サインアウト確認ページ

- **確認を挟む理由**: 画面を開いただけでサインアウトする形にすると、リンクや埋め込まれた画像から利用者を勝手にサインアウトさせられる。このため、利用者がボタンを押したときだけサインアウトする

#### プランページ

料金を示し、ログイン中の利用者が自分の契約の状態を確かめ、申し込みと契約の管理へ進む画面。

**判断根拠**:
- **Auth に置く**: 申し込みには、Auth のユーザーと Stripe の顧客を結びつける処理が要り、ユーザーを持つのは Auth だけだから
- **料金の画面を兼ねる**: 料金を見る画面と申し込む画面が分かれると、価格の表記が 2 か所になって食い違いやすい
- **価格と説明は Stripe から読む**: 価格と商品の説明は開くたびに Stripe から読み、文言を Stripe の 1 か所で管理する。説明が空なら出さない
- **価格が無い段は出さない**: 有料ロールはコードで定義するが、売るかどうかは Stripe に価格を作るかで決める。サービスを順に課金に載せるため、価格を作るまでは枠を出さない。ただし、その利用者が契約中か手動の権利を持っていれば、状態を確かめられるよう枠を出す。価格の取得に失敗したときは売っているか分からないため、全部の枠を出して取得できなかった旨を示す (Stripe の障害で画面が空にならないようにする)。出す段が無いサービスは、見出しごと出さない
- **サービスごとに見出しを置く**: 契約と更新日がサービス単位で、段はその中の選択肢だから。段を下から並べると、上げ下げの方向が読める
- **段の説明は商品に持つ**: 段ごとに商品を分けるので、商品の説明を段の説明にする。文言を Stripe の 1 か所に置く (ADR-013)
- **上げは Auth が行き先を決めて Portal の確認画面へ送る**: Portal の一般のプラン変更に任せると、別サービスの商品へも切り替えられてしまう。日割りの表示・支払いの失敗・3D セキュアは Stripe が扱う
- **下げの確認は Auth の画面で出す**: 下げは Portal ではなく Auth が予約する (ADR-013) ため、切り替わる日と返金が無いことをこの画面で示してから予約する
- **予約中・解約予約中は切り替えを出さない**: 予約が付いている間は Portal で変更も解約もできない (Stripe の仕様) ため、プランの画面に予約を表示して Auth から取り消せるようにする
- **支払いを確認できていない契約では切り替えを出さない**: 上げると未払いの請求に差額が重なるため
- **契約の管理は 1 つ**: Customer Portal は顧客の単位で開くため、プランごとではなく画面に 1 つだけ置く
- **解約・支払い方法の変更・請求の履歴は自作しない**: Stripe の Customer Portal に任せる。作る量を減らし、カード情報を Auth で扱わないため
- **開いたときにも同期する**: 更新の通知を取りこぼしたときの保険
- **戻り先は nagiyu のサービスに限る**: 各サービスは戻り先を付けてこの画面へ案内する。オープンリダイレクトを防ぐため、戻り先を検証する
- **表記へのリンクは準備中でも出す**: 決済事業者の審査が、表記の URL を確かめるため

#### 特定商取引法に基づく表記ページ

定期課金に必要な表示を載せた公開ページ。中身は `@nagiyu/ui` の共通部品で描画する。

**判断根拠**:
- 定期課金では、申し込みの最終確認の段階で、金額・更新の周期・解約の方法が分かる必要がある (2022 年の特定商取引法の改正)。金額と周期は Stripe の決済画面が出し、解約の方法はプランのページとこの表記で補う
- 置き場所と文面の判断は [アーキテクチャ設計書](./architecture.md) の ADR を参照

## 5. スコープ外

以下は Phase 1 で実装しない機能です:

- ❌ パスワード認証 (Phase 2 以降で検討)
- ❌ GitHub OAuth、その他 OAuth プロバイダー (Phase 2 以降で検討)
- ❌ 多要素認証 (MFA) (Phase 2 以降で検討)
- ❌ パスワードリセット機能 (パスワード認証実装後)
- ❌ アカウント削除のセルフサービス (Phase 2 以降で検討)
- ❌ 監査ログ閲覧 (logs サービスの責務、Phase 2 以降)
- ❌ PWA 対応 (Auth サービスは認証が必須のため、PWA は無効)

課金については、以下を Auth サービスで扱わない:

- ❌ 各サービスでの無料と有料の出し分け (どの機能を有料にするか、回数の上限など)。各サービスで扱う
- ❌ ログインしていない利用者の利用回数の制限
- ❌ 支援サービスとの自動連携 (コード入力・API 連携など)
- ❌ Stripe が送る領収書メールを止めて、自前で通知を送ること
- ❌ 海外の顧客向けの税の処理 (販売代行型の利用を含む)
- ❌ 返金の仕組み (返金は Stripe の管理画面から手で行う)

## 6. 用語集

| 用語          | 定義                                                                 |
| ------------- | -------------------------------------------------------------------- |
| SSO           | Single Sign-On。一度のログインで複数サービスにアクセスできる仕組み |
| JWT           | JSON Web Token。JSON 形式の署名付きトークン                          |
| RBAC          | Role-Based Access Control。ロールベースアクセス制御                  |
| OAuth 2.0     | 認可のためのオープン標準プロトコル                                   |
| DynamoDB      | AWS の NoSQL データベースサービス                                    |
| CloudFront    | AWS のコンテンツ配信ネットワーク (CDN)                               |
| NextAuth.js   | Next.js 用の認証ライブラリ                                           |
| ACM           | AWS Certificate Manager。SSL/TLS 証明書管理サービス                  |
| 手動ロール    | 管理者が管理画面から付けるロール                                     |
| 課金の権利    | 課金によって付くロール。手動ロールとは別に持ち、出どころと有効期限を持つ ([課金の権利](../../specs/auth/term/role-grant.md)) |
| 出どころ      | 課金の権利がどこから来たか (Stripe / 手動)                           |
| 有料ロール    | 課金の権利として付けられるロール ([プランの段](../../specs/auth/term/plan-tier.md)) |
| 有効なロール  | 手動ロールと、期限内で取り消されていない課金の権利のロールを合わせたもの。セッションに載る ([セッションのロール](../../specs/auth/term/session-roles.md)) |
| Checkout      | Stripe が提供する決済画面                                            |
| Customer Portal | Stripe が提供する、契約者自身が解約や支払い方法の変更を行う画面    |
| Subscription Schedule | Stripe の契約の予約。Auth は下げを、請求期間の終わりに効く予約として作る |
