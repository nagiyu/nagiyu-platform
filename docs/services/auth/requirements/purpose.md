# auth

nagiyu プラットフォームのログインを集め、各サービスが認証を作らずに済むようにするサービス。ログインとロールの管理に加えて、有料プランの申し込みを、ロールを付ける入口の一つとして扱う。

## 解決したい課題

各サービスが個別に認証を実装すると、コストが増え、認証の扱いと安全の水準がサービスごとにばらつく。このサービスはログインを Google アカウントで受け付けて集め、一度のログインで全サービスに入れるようにする (SSO)。各サービスはログインを作らず、権限で判定するだけで済む。

プラットフォームには、運営コストのかかる機能 (外部の AI の呼び出し、動画の処理など) がある。このサービスは課金を「ロールを付け外しする入口の一つ」として扱い、次を満たす。

- **運営コストの回収**: 運営コストの一部を、利用者の課金で回収できる
- **出し分けの土台**: 各サービスが、有料ロールの権限を見るだけで、無料と有料の出し分けを作れる。課金のための専用の判定を、各サービスに持たせない
- **手動の付与**: Stripe を通さずに受けた支援にも、管理者が手動で有料ロールを付けられる

## 扱わない範囲

- **各サービスの無料・有料の出し分け**: どの機能を有料にするか、回数の上限をどうするかは、各サービスが権限で判定して決める。このサービスは有料ロールを付けるところまでを受け持つ
- **JWT の検証**: このサービスは暗号化した JWT を発行するだけで、各サービスは Auth へ問い合わせずに、受け取った JWT からロールを読む。そのため、ロールの変更や権利の期限切れが各サービスへ届くのは、利用者が Auth を通るときになる ([セッションのロール](../specs/term/session-roles.md))
- **決済手段・返金・税の扱い**: 課金の機能に閉じる取り決めなので、機能要件の「やらないこと」に書く ([申し込みと管理](functional/subscription.md))

## 利用者

- **管理者**: ユーザーの一覧を見て、ロールを割り当てる。Stripe を通さずに受けた支援には、期限つきで有料ロールを付ける
- **エンドユーザー**: Google アカウントでログインして、各サービスを使う。有料プランに申し込む人もいる
