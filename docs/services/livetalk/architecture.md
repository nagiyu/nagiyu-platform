# リブトーク（LiveTalk）アーキテクチャ設計書（設計決定記録）

この文書は、なぜそう設計したか (決定、根拠、捨てた案) を書く。今どう動くかは[仕様カード](../../specs/README.md)にある。

> 型定義・API スキーマ・コンポーネント設計などコードを読めばわかる実装詳細は記載しない（`services/livetalk/` のソースを参照）。

## 1. システム概要

Live2D アバター（桃瀬ひより）と AI（OpenAI LLM + VOICEVOX TTS）を組み合わせたコンパニオン PWA。「キャラが同じ時間軸で生活している」体験を中核に、会話・記憶・生活サイクル・能動通知を提供する。

- フロント / バックエンド: Next.js（Lambda Web Adapter）を ECS Fargate で稼働
- 音声合成: VOICEVOX を同一 ECS Task のサイドカーコンテナとして同居
- データ: DynamoDB Single Table（1 メッセージ 1 item）
- バッチ: EventBridge Scheduler + Lambda（Topic 集約 / Web 取得 / 通知 / 活動時間学習）
- 配信: CloudFront → サービス専用 ALB → ECS Service
- リージョン: **us-east-1 固定**（CloudFront 連携の制約による）

全体構成・SK パターン・モジュール構成の詳細は `services/livetalk/` / `infra/livetalk/` のコードを参照。

## 2. 重要なアーキテクチャ決定

### 2.1 Live2D はクライアント側でリアルタイム描画する（ADR-001）

**背景・問題**

サーバー側で Live2D を描画して動画として返す案を初期に検討したが、コスト・レイテンシ・帯域の観点で実用性が低い。同領域の既存サービス（Open-LLM-VTuber、Neuro-sama 等）はすべてクライアント描画を採用している。

**決定**

`pixi-live2d-display-lipsyncpatch`（MIT）を使い、ブラウザの WebGL でリアルタイム描画する。サーバーは「テキスト + 音声 + モーション指示」だけを返す。

**根拠・トレードオフ**

- ✅ 1 応答あたりの追加レイテンシがほぼゼロ / サーバー GPU 不要 / 帯域はモーション JSON 数 KB のみ
- ✅ 既存 OSS（Open-LLM-VTuber）を参考にできる
- ⚠️ iOS Safari の WebGL は注意点があるが、Live2D は 2D メッシュなので 3D ほど重くない

### 2.2 DynamoDB Single Table 設計、会話は 1 メッセージ 1 item（ADR-002）

**背景・問題**

「ユーザーごとに 1 レコードで会話を配列保持」が最初の検討案だったが、DynamoDB のアンチパターンであり、400KB 上限・書き込みコスト・並行競合・TTL 非対応の観点で破綻する。

**決定**

PK = `USER#<userId>`、SK = `CHAR#<charId>#MSG#<ulid>` 等で、メッセージは個別 item として保存する。Single Table 設計の標準パターンに従う。

**根拠・トレードオフ**

- ✅ メッセージ数に上限がなくなる / TTL で古いメッセージを自動削除可能（Message は 90 日）
- ✅ 「直近 N 件取得」が効率的（Query + Limit）/ 圧縮要約は別 item（`MEMORY#SUMMARY`）として独立管理
- ⚠️ 全件読み出しは複数 item の Get が必要だが、本サービスでは不要

### 2.3 VOICEVOX はセルフホスト、文単位で逐次パイプライン化（ADR-003）

**背景・問題**

VOICEVOX はストリーミング合成に対応していない。長文を一括生成すると最初の音声まで数秒〜十数秒待たされる。

**決定**

LLM の応答ストリームを文区切り（。！？）で分割し、文単位で VOICEVOX に投げる。生成された音声を逐次クライアントへ送信して順次再生する。

**根拠・トレードオフ**

- ✅ 最初の音声まで短時間 / CPU で十分（GPU 不要）/ ECS Fargate 1 タスクで安価に運用可能
- ⚠️ 文単位なのでアクセント・抑揚が文同士で繋がらない（許容）
- ⚠️ VOICEVOX の synthesis が CPU 律速で直列化しやすく、長い応答では合成待ちがレイテンシ要因になる（運用課題として継続観測）

> **注記（実測との差異）**: 上記のうち 2 点について、実測が当初の前提と食い違っていた（Issue #3761 のコスト調査で判明）。決定当時の記述は履歴として残し、以下を追記する。
>
> - **「起動時のモデルロードに 30〜60 秒かかる」は見積もりであって実測ではなかった。** prod タスクのライフサイクル実測では、起動 81.6 秒の内訳は **イメージ pull 37.5 秒 + ヘルスチェックのポーリング待ち + web 起動**で、支配項は pull である。VOICEVOX エンジンは既定で全話者モデルをロードせず（`--load_all_models` はオプトイン、話者ごとの遅延ロード）、実測メモリのピークが 690MB に収まっていることもこれと整合する。したがって**起動時間の短縮に効くのは `startPeriod` の調整ではなく pull 時間の短縮**（公式イメージの ECR ミラー化・不要話者モデルの削減）である。この誤った前提は「VOICEVOX は常駐コンテナでなければならない」という判断の根拠として使われていたため、実行基盤を再検討する際はこの実測値を出発点にする。
> - **「CPU 律速で直列化しやすい」には、現時点で計測根拠がない。** `ChatMetrics.latency.ttsTotal` は `chat-usecase.ts` で計測されていたが CloudWatch（EMF）へ出力されておらず、合成待ちが実際にユーザーの体感遅延になっているかを判定できない状態だった。加えて実装上、音声は LLM 完走と Moderation 判定の後に emit されるため、**TTS 合計が LLM 合計を下回る限り合成時間はユーザーから見えない**。Issue #3761 で `TTSTotalLatency` / `LLMTotalLatency` を EMF に追加したので、今後はこの 2 値の大小で判定する。ECS タスクの CPU 割当を縮小できるかの判断もこの計測に依存する。

### 2.4 ECS Fargate 1 Task に Next.js + VOICEVOX の 2 コンテナ同居（ADR-004）

**背景・問題**

VOICEVOX を独立サービスとして立てるか、Next.js と一緒に動かすか。

**決定**

MVP〜Phase 5 完了までは「1 ECS Task に 2 コンテナ」構成。Next.js から `localhost:50021` で VOICEVOX を叩く。VOICEVOX クライアントは環境変数 `VOICEVOX_URL` で接続先を差し替え可能とし、将来の共通サービス化に備える。

**根拠・トレードオフ**

- ✅ 単一デプロイ単位で扱える / ローカル・dev・prod の動作差を最小化 / コスト効率がよい
- ⚠️ スケール時に Next.js と VOICEVOX が一緒にスケール（許容、将来分離可）

### 2.5 親密度は上昇のみ、降下しない（ADR-005）

**背景・問題**

Replika が無起動期間で親密度を下げて炎上した教訓を踏まえる。一方で、関係性の表現として上昇は必要。

**決定**

親密度は上昇のみ。長期無起動でも下げない。代わりに「久しぶり！」演出と通知文面の温度感調整で時間経過を表現する。

**根拠・トレードオフ**

- ✅ ダークパターン回避、ユーザーが気持ちよく戻ってこれる / Replika との差別化として明確
- ⚠️ 親密度の意味が「累積接触量」になる（恣意的だが許容）

### 2.6 睡眠状態は応答ゲートではなくスタイル変調（ADR-006）

**背景・問題**

キャラに「就寝中は応答しない」設計だと、夜型ユーザーが使えなくなる。デスクトップメイト的な「常に応答可能」が本サービスの魅力に合う。

**決定**

寝てる時間帯でも応答する。ただし応答スタイルが寝ぼけ口調 + 半目になる。「起きてる / 寝てる」の 2 状態でフレーバーだけを変える。

**根拠・トレードオフ**

- ✅ 夜型ユーザーをカバー / 「寝起きの会話」自体が親密度の演出になる
- ⚠️ LLM のスタイル維持が技術的に難しい（few-shot で誘導）

### 2.7 メモリは階層化 + 信頼度スコア、編集機能は撤去（ADR-007）

> **本 ADR の階層化・信頼度・cooldown は #3696 で撤廃**。知識・記憶は Topic 中心モデル（ADR-2.24）へ置換した。ただし「編集を提供せず訂正は前向き（会話・削除）に流す」という整合方針は 2.24 の決定的忘却に引き継がれている。

**背景・問題**

Ani / Replika で問題化した「誤情報の永続化」「些細な情報を毎回参照」を構造的に解決したい。当初は記憶編集 UI を MVP から提供する方針だった。

**決定（当初）**

メモリを Tier A/B/C/D に階層化し、信頼度スコアと cooldown を持たせる。LLM への注入は関連度フィルタを通したものに限定する。

**決定の修正（編集機能撤去、Issue #3308）**

Phase 3e（#3283）で記憶編集 UI（閲覧 / 編集 / 削除 / ピン留め）を実装し dev で検証したところ、**「記憶を編集・削除してもLLMが古い情報を言い続ける」三層整合性問題**が判明した。

LLM プロンプトは 3 系統で構成される：

| 層              | データ                           | TTL     |
| --------------- | -------------------------------- | ------- |
| ① MemoryEntity  | DynamoDB の個別記憶アイテム      | Tier 別 |
| ② MemorySummary | 日次バッチが生成する会話圧縮要約 | なし    |
| ③ Messages      | 直近の会話履歴                   | 90 日   |

編集 UI は ① しか更新しないため、② ③ に古い情報が残存し、LLM 応答に旧情報が出続けた。

これを受けて **編集機能を撤去**した：

- 撤去: `PATCH /api/memory/:id`、編集 UI / ボタン
- 維持: 一覧閲覧、削除（`DELETE /api/memory/:id`）、ピン留め
- 追加: 削除確認ダイアログに「即時反映されない」注釈、記憶ページに「訂正は会話で」ガイダンス

**根拠・トレードオフ**

- ✅ 編集を廃止すれば三層整合性問題は構造的に発生しない（情報が前向きにのみ流れる）
- ✅ 「友達 / コンパニオン」関係において「キャラを書き換える機械」は世界観と相性が悪い → 会話による訂正（Phase 3d #3282）が正規ルート
- ⚠️ 将来編集機能を復活させる場合は、② ③ の更新（または注釈での許容）を設計に含めること

### 2.8 認可は既存プラットフォーム RBAC に乗る（ADR-008）

**背景・問題**

新規 permission を作るか、独自の認可機構を作るか。

**決定**

既存 `libs/common/src/auth/` の RBAC に新 permission `livetalk:chat` を追加する。`livetalk-user` role を作り、必要なアカウントに付与する。運用者向けには `livetalk:admin` 権限（ステータスページ等のデバッグ機能用）を併設する。

**根拠・トレードオフ**

- ✅ 既存基盤の恩恵を最大限受ける / 他サービスとの統合運用が容易 / role 付与で「自分のみ」も「公開」も制御可能
- ⚠️ プラットフォームの認可方針に縛られる（許容）

### 2.9 セーフティは自前実装する（LLM 任せにしない）（ADR-009）

**背景・問題**

OpenAI / Anthropic の安全機構は不十分。Character.AI / OpenAI の訴訟事例（Adam Raine 事件等）で開発者責任が確立されている。

**決定**

入力時にキーワード辞書で危険発言を検出 → LLM をバイパスして強制テンプレ応答に切替。応答後も OpenAI Moderation API で二段チェック。日本のリソース（いのちの電話、よりそいホットライン、TELL Lifeline）を案内する。検出ログを別領域に保管する。

**根拠・トレードオフ**

- ✅ 法的責任の最小化 / Character.AI のような事故を構造的に回避
- ⚠️ false positive で会話が中断されることがある（許容、安全側に倒す）/ キーワード辞書のメンテが必要

### 2.10 モデルは桃瀬ひより + 音声は冥鳴ひまりで MVP、後で差し替え可能（ADR-010）

**背景・問題**

オリジナルキャラ・声を作るには時間とコスト。すぐ動くものを作りたい。

**決定**

- Live2D: 桃瀬ひより（Live2D 公式サンプル）
- 音声: VOICEVOX 冥鳴ひまり（speaker=14、ライセンス緩い）
- `CharacterDefinition` で抽象化し、将来差し替え可能とする（抽象化の構造・client/server 境界は 2.15 を参照）

**根拠・トレードオフ**

- ✅ MVP がすぐ動く / 法的リスク最小（公式サンプル + 緩いライセンス TTS）
- ⚠️ キャラ性と声が完全一致しない（許容、本格公開時に差し替え）
- ⚠️ 年商 1,000 万円超 or 中・大規模事業者になる前に Live2D 別途契約が必要

### 2.11 通知は指数バックオフ + 時間帯制限 + クリティカル escalation（ADR-011）

> **通知のクリティカル判定とネタ源は #3696 で Topic.care ＋ WEB fact へ移行**。旧 InterestCategory.Weight を escalation 信号に使う設計は撤廃した (ADR-2.24)。頻度制御・時間帯制限の枠組み自体は本 ADR のまま。ただし、重要通知は同じ話題・同じ予定を 1 度だけ送り、最後の発話から 3 日たつと止まる。平常通知は勉強が止まっている間、話題名を入れない文面だけを使う (ADR-2.25 / 2.27)。その後、1 日の上限と間隔の延ばし方も変わった。今の挙動は[通知バッチ](../../specs/livetalk/batch/notify.md)を参照。

**背景・問題**

Push 通知の頻度バランスが難しい。少なすぎると忘れられ、多すぎると鬱陶しい。

**決定**

- 平常通知: 過去 N 回のやり取りの中央値間隔から算出、超過後は倍々で間隔拡大
- 時間帯: 朝・夕方（ユーザー活動時間から学習）
- クリティカル escalation: 新作・期間限定情報は時間帯外でも配信
- 上限: 1 日 2 件まで（平常 1 件 + クリティカル 1 件）

**根拠・トレードオフ**

- ✅ ユーザーの生活リズムに自然に適応 / 「追わない」スタンスが他コンパニオンとの差別化に
- ⚠️ N 件のサンプルが溜まるまでは固定間隔（許容）

### 2.12 「知らない → 勉強しておく」は強制ゲート化（ADR-012）

> **#3696 で知識ゲートの位置を見直し**。ゲートは想起の後段に置き、既に WEB fact を持つ既知 Topic は会話でそのまま回答して勉強予約に倒さない。真に未知 (関連 Topic なし) の話題のみ acquire に予約する。勉強の依頼 (StudyTopic) は、会話で出た未知の話題を積む用途で残る。取得対象は、この依頼・使われた Topic の鮮度確認の依頼・care の順で選ぶ (ADR-2.24 / 2.26)。今の挙動は[勉強の依頼](../../specs/livetalk/term/study-topic.md)と[勉強バッチ](../../specs/livetalk/batch/acquire.md)を参照。取得は利用者単位の 1 日の回数の上限の内側で行う (ADR-2.25)。LLM の良心に頼らずコード側で gating する本 ADR の骨子は維持する。

**背景・問題**

LLM は学習済み知識でホイホイ即答する。プロンプトで「知らないと答えろ」と書いても守らない。

**決定**

知識ベース検索を行い、ヒット無しのトピックは**コード側で強制的に**「勉強しておくね」テンプレに切り替える。LLM の良心に頼らず gating する。該当トピックは STUDY_TOPIC キューに積み、次回の勉強バッチで優先処理する。

**根拠・トレードオフ**

- ✅ 「同じ時間軸で生きてる」感の演出が確定する / プロンプトインジェクション耐性も高い
- ⚠️ 一般常識まで「勉強する」と返してしまうリスクがあるので、分類精度に注意

### 2.13 可観測性は構造化ログ + EMF メトリクス（ADR / Issue #3315）

**背景・問題**

AI に渡すコンテキストは会話の蓄積で増えていく。コンテキストサイズと応答速度を計測できる形にしておく必要がある。アプリ内に計測画面（L3）は作らず、CloudWatch で観測する。

**決定**

構造化ログ（L1）と CloudWatch EMF メトリクス（L2）を組み合わせる。

- Best-effort 計測: 計測コードは try/catch で囲み、例外がチャット応答を止めない
- PII 保護: トークン数・レイテンシ・件数のみ記録（会話本文を含めない）
- EMF: `console.log` でトップレベル `_aws` キーを持つ JSON を直接出力
- Namespace: `LiveTalk/Chat`（PromptTotalTokens / LLMTimeToFirstToken / ChatTotalLatency 等）、`LiveTalk/Batch`（CompressedMessageCount / BatchLatency）
- ディメンション: `Environment` / `CharacterId`
- DynamoDB 消費 RCU も `ReturnConsumedCapacity: 'TOTAL'` で計測

実装は `services/livetalk/core/src/observability/` を参照。

### 2.14 LLM レスポンスの Structured Outputs 化（ADR / Issue #3316）

**背景・問題**

要約・分類・昇格判定で「JSON のみ返せ」とプロンプト指示し `JSON.parse` する実装は、silent failure（パース失敗時に記憶抽出が静かに失われる）・フォーマット揺れ・型保証の欠如という問題があった。

**決定**

OpenAI Responses API の **Structured Outputs**（`responses.parse` + `zodTextFormat`）を採用する。

- `ILLMClient` に `chatStructured<T>` を追加（Provider 抽象化を維持）
- Zod スキーマを `src/llm-client/schemas/` に集約（summarize / correction / confirmation）
- strict モード対応: optional は `nullable()` で表現
- refusal を専用エラーとして throw
- **chat ストリーミング（`chatStream`）は対象外**（会話応答はストリーミングで返すため JSON スキーマが適用できない）。Structured Outputs の対象は分類・要約・昇格判定のみ

**根拠・トレードオフ**

- ✅ silent failure の解消 / デコーダレベルの型保証 / フォーマット揺れの排除
- ⚠️ 会話応答のストリーミングとは両立しない（構造化応答化は将来検討 → roadmap / Discussion Issue）

### 2.15 キャラクター部品はロジックと描画・表示を分離し id で結合する（ADR / Issue #3413）

**背景・問題**

ADR-010 でキャラクターのロジック（性格・声・ライセンス等）は抽象化したが、名称や Live2D モデルの参照が UI に焼き付いており、複数キャラ対応の障害になっていた。また、描画・表示を担う UI 側は、サーバ専用依存（AWS SDK 等）を含むロジック層をそのまま取り込めない（クライアント向けビルドが壊れる）という制約がある。

**決定**

キャラクター部品を「ロジック（誰か）」と「描画・表示（どう見せるか）」に責務分離し、キャラクター ID をキーに結合する。

- ロジックは ADR-010 の `CharacterDefinition`（フレームワーク非依存）に集約する。
- 描画・表示用の情報（表示名・短縮名・Live2D モデルや描画パラメータ）は、ロジック層に依存しない形で UI 側に持つ。
- 両者はキャラクター ID をキーにした静的なレジストリで結合し、UI・API はキャラクター ID から解決する（既定キャラクターへのフォールバックを持つ）。
- ロジック層と UI 側に重複して持つ情報（表示名・既定キャラクター ID）は、テストで一致を担保する。短縮名は UI 専用とする。

**根拠・トレードオフ**

- ✅ 名称・モデル参照の焼き付きを除去 / 複数キャラ追加時の変更箇所を局所化 / 描画・表示側がサーバ専用依存を巻き込まない構造を保証
- ⚠️ 一部情報（表示名・既定キャラクター ID）を二重に持つ（テストで同期を担保）
- ⚠️ Live2D 以外のレンダラ抽象化・キャラクターのデータベース管理・ユーザー作成キャラ（UGC）は対象外（将来 → roadmap）

実装は `services/livetalk/web/src/lib/characters/` を参照。

### 2.16 通知はキャラクター単位の能動アクションにする（ADR / Issue #3491）

> **発火判定の「知識」根拠は #3696 で Topic.care ＋ WEB fact に置き換わった**(ADR-2.24)。キャラクター単位・ユーザー総量上限・クロス汚染防止という本 ADR の枠組みはそのまま。重要通知の止め方と重複抑止は ADR-2.27 を参照。

**背景・問題**

ADR-011 の通知は「ユーザー単位・既定キャラクター前提」で設計されていた。複数キャラクター運用（ADR-010 / ADR-2.15）に移行した結果、通知が既定キャラクター固定でしか生成されず、非既定キャラクターは能動通知を出せない。さらに通知に「どのキャラクターからか」の情報が無いため、起動時に通知元と無関係なキャラクターが第一声を喋る・別キャラクターの知識が会話に混入する、という取り違えが発生した。

**決定**

通知を「キャラクターからの能動アクション」と再定義し、生成→配信→消化をキャラクター ID で一貫させる。

- 生成: ユーザー × 各キャラクターで判定する。発火可否はキャラクター単位の履歴・親密度・知識で判断する。ユーザーへの通知過多を防ぐため、平常通知は 1 回の実行につき 1 キャラクターのみ選抜し（最も長く通知していないキャラクターを優先）、クリティカル通知はキャラクター独立で送る。1 日あたりの上限はユーザー総量で維持する（キャラクター数倍にしない）。
- 配信: 通知にキャラクター ID を載せ、タップ時に通知元キャラクターの画面を開く。プッシュ購読は端末単位のまま（キャラクター単位にしない）。
- 消化: 起動経路で出し分ける。通知タップ起動では通知元キャラクターへ自動で切り替えて第一声を出す。自前起動では現在のキャラクター以外の未消化通知を「○○から連絡が来てるよ」と提示し、切り替えるまで保持する。消化はキャラクター単位で、別キャラクターへ切り替えても他キャラクターの通知は消えない。
- クロス汚染防止: 通知由来の知識文脈は、現在のキャラクターと通知元が一致するときのみ会話へ渡す。
- 検証: 発火条件を介さず任意キャラクターの通知を配信できる管理者限定のテスト送信手段を、恒久のデバッグツールとして持つ。

通知配信履歴にはキャラクター ID を保持する。キャラクター ID を欠く過去データは既定キャラクター扱いで後方互換とする（保持期間内に自然消滅する）。

**根拠・トレードオフ**

- ✅ 各キャラクターが能動的に通知できる / 取り違え・知識のクロス汚染が構造的に起きない / ユーザー総量上限により既存の体感頻度を壊さない
- ⚠️ 生成判定がユーザー × キャラクター数に増える（コストより正確性を優先）
- ⚠️ 複数キャラクターからの通知を一覧・バッジで見せる凝った体験は対象外（将来 → roadmap）

### 2.17 非 Live2D キャラはレイヤー合成の一枚絵を音声駆動で動かす（ADR / Issue #3502）

**背景・問題**

ADR-2.15 でレンダラを抽象化したが、Live2D 以外の描画方式は将来課題（roadmap C）として保留していた。一方、AI 生成イラストのサブキャラ（早瀬アゲハ）は Live2D モデルを持たない。静止画 1 枚では「生きてる感」が乏しく、かといってサブキャラのために Live2D を起こすのは制作コスト・権利の両面で見合わない。

**決定**

非 Live2D キャラ向けに、一枚絵のパーツ（目・口など）を重ね合わせ、音声に連動して瞬きと口パクを行う描画方式を、レンダラ抽象化の 1 種別として追加する。

- 瞬きと口パクは「開き／閉じ」のパーツを排他で切り替える二値表現とする（中間のフェードは行わない）。
- 口パクは発話音声の音量から開閉を判定し、Live2D 経路と同じ Web Audio ベースの解析手段を共用する。
- 動かさないキャラ向けに、完成した静止画 1 枚をそのまま表示する方式（瞬き・口パクなし）も別種別として残し、描画方式はキャラ単位で選べるようにする。

**根拠・トレードオフ**

- ✅ Live2D を持たない AI 生成キャラにも最小コストで「生きてる感」を付与できる（roadmap C「簡易モデル」の最初の実体化）
- ✅ 音声連動の仕組みを Live2D 経路と共用し、描画方式が増えても発話演出の一貫性を保てる
- ✅ 排他切替の二値表現は、連続フェードよりも動きが明確で、重ねた下のパーツが透ける不具合も避けられる
- ⚠️ 表現力は Live2D に劣る（母音ごとの口形や連続的な表情変化はできない）。メインキャラは Live2D を維持し、本方式はサブキャラ位置づけとする
- ⚠️ パーツ画像はリポジトリ管理外（エッジ配信）であり、各環境への事前配置が表示の前提になる

### 2.18 インフラ監視はプラットフォーム共通のアラーム集約基盤に接続する（ADR / Issue #3526）

**背景・問題**

ADR-2.13 はアプリ内計測（構造化ログ + EMF メトリクス）を整備したが、インフラ層の障害検知には穴があった。バッチ DLQ（保持 7 日）にアラームが無く、バッチが落ち続けても証拠が 7 日で消える。ALB の 5xx / ターゲット異常、DynamoDB のスロットリングも検知できない。一方で、障害通知を受ける仕組み（SNS → 永続化 → Web Push）は admin が既に持っている。

**決定**

livetalk のインフラ障害アラームを CloudWatch で定義し、admin のプラットフォーム共通アラーム集約基盤へ接続する。

- 監視対象: バッチ Lambda エラー・バッチ DLQ 滞留（4 バッチ各々）・ALB 5xx・ALB ターゲット異常・DynamoDB スロットリング。その後、バッチは今の 4 本に置き換わり、DLQ の滞留アラームは学習バッチと通知バッチの 2 本にだけ残っている (集約バッチと勉強バッチの分は #4670 で扱う)。
- 通知先は admin の**本流**アラーム集約 SNS Topic（`nagiyu-admin-alarms-{env}`）。同 Topic から `alarm-ingest → error-events → Web Push` の既存経路に乗せ、通知の二重化や独自配信を作らない。admin 自身の障害監視に使う self-monitoring Topic とは用途が異なるため、そちらは使わない。
- アラーム**定義そのものは livetalk 個別**の専用 stack に持つ。admin の self-monitoring アラームと定義パターンは共通だが、共通コンストラクトへの抽出は admin 側のリファクタを伴いスコープが広がるため、今回は見送る（将来課題）。
- アラームのしきい値は「直近の検知漏れを無くす」ことを優先し、保守的に低く置く（誤検知より見逃しを嫌う MVP 段階の判断）。

あわせて、時刻判定に依存するバッチ間で `TZ=Asia/Tokyo` の設定有無が揃っていなかった不整合を解消した（§4.3）。

**根拠・トレードオフ**

- ✅ DLQ 滞留・ALB 異常・スロットリングを即検知でき、証拠の自然消滅を防げる
- ✅ プラットフォーム共通の通知経路に集約され、サービスごとに配信を作り込まない
- ⚠️ アラーム定義が admin と livetalk に重複する（共通化は将来課題）
- ⚠️ 実発火 → Web Push までの E2E は能動的なトリガー（DLQ への投入等）が必要で、定義の正しさは CDK の synth / assertion テストで担保する

### 2.19 ユーザー（Profile）列挙は sparse GSI で行い、全件 Scan を排する（ADR / Issue #3527）

**背景・問題**

毎時バッチ（compress / study / learn-user-activity / notify）が全ユーザーを列挙するために、テーブル全体を Scan + FilterExpression していた。ADR-002 の Single Table 設計では Message 等の大量 item が同居するため、ユーザー数増加に対して Scan のコスト・実行時間が線形に悪化し、Lambda 15 分制限に当たるリスクがあった。列挙ロジックも複数 usecase に重複していた。

**決定**

Profile item のみを索引化する sparse GSI（`GSI1`）を追加し、バッチのユーザー列挙を Query に置き換える。列挙ロジックは core（`ProfileRepository.listAllUserIds`）へ集約する。

- `GSI1PK='PROFILE'` を Profile item にのみ付与する（sparse GSI ＝ 属性を持つ item だけが索引に載る）。他の item 種別には付けないため、索引は Profile だけで構成される。
- `GSI1SK` は生の `UserID`（`USER#` プレフィックスなし）。射影は `KEYS_ONLY`（列挙に必要なのは UserID のみで、属性を複製しない）。
- 索引を参照する他 stack はテーブル名を `getDynamoDBTableName()` 等で独立に組み立て、CDK のクロススタック参照（`Fn::ImportValue`）/ SSM 経由の結合を避ける。export 依存に伴うカスケード再デプロイを防ぐため。

**根拠・トレードオフ**

- ✅ ユーザー列挙が Scan → Query になり、コスト・実行時間がユーザー数に対して線形悪化しない
- ✅ `KEYS_ONLY` 射影で索引ストレージと書き込みコストを最小化し、列挙ロジックを core に集約して重複を解消
- ⚠️ sparse GSI のため属性を持たない既存 Profile は索引に載らない。恒久的な backfill 資材は作らず、ユーザー母集団が廃棄可（dev / prod とも少数のシードのみ）だったため、データをクリアして再 onboarding する運用で対応した（consent フローが GSI 属性付きで Profile を作り直す）
- ⚠️ 一覧系 API のうち無限増加しうる notes / push pending はページング対応とした。memory 一覧は Tier compaction で件数が有界なため対象外（暗黙打ち切りを持たない）

### 2.20 チャット API の保護はアプリ層ガードで行い、状態は Single Table に相乗りする（ADR / Issue #3528）

**背景・問題**

`/api/chat` は認証さえ通れば 1 リクエストごとに LLM（ストリーミング）+ VOICEVOX 合成が走るが、レート制限・二重送信制御・サーバ側タイムアウトが無かった。悪意がなくても PWA の再送やクライアントバグで LLM 課金が走るリスクがある。なお OpenAI 利用額そのものの上限（budget cap）は AWS/CDK では制御できず、本サービスのインフラの管轄外である。

**決定**

レート制限と並行制御をアプリ層に実装し、状態は ADR-002 の Single Table に相乗りさせる（新テーブル・IAM 変更なし。既存の `grantReadWriteData` が必要アクションを網羅）。

- レート制限はユーザー単位の固定ウィンドウ・カウンタ（窓と回数は[チャット API](../../specs/livetalk/api/chat.md)を参照）。`@nagiyu/aws` の上限付きの回数カウンターで、上限未満のときだけ加算する条件付き更新にし、判定と加算を 1 回の操作で行う。超過時は HTTP 429（`Retry-After` は断った窓で決める）。カウンタは TTL で自動掃除する。
- 窓は 1 分 → 1 時間の順に数え、1 時間で断ったときは数えた 1 分を戻す。断った申し込みはどの窓も消費しない。断った分まで数えると、1 分の窓で断られ続けるあいだに 1 時間の窓が埋まり、短い連打だけで 1 時間止まってしまうため。1 分を先に数えるのは、断る理由の大半が 1 分の窓で、そのときは 1 時間に触れず戻しも要らないため。
- 並行制御は in-flight ロック（SK=`CHATLOCK`）。同一ユーザーの並行リクエストは 2 本目以降を **拒否（429）** する（キャンセルではなく拒否。Message 生成が冪等でないため拒否が安全側）。取得は条件付き（`attribute_not_exists OR ExpiresAt < now`）で、失効判定は `ExpiresAt` に基づき、TTL の物理削除遅延（最大 48h）に依存しない。解放は誤削除防止のため `OwnerToken` 一致を条件とする。
- ガード適用順は **ロック取得 → レート加算**。並行で 429 拒否されたリクエストがレート枠を消費しないようにする。
- サーバ側の決定論的タイムアウトは **持たない**。`for await` の外側にデッドラインを置く方式は、ジェネレータが真にハングした場合に発火せず誤解を招くため撤去し、上流クライアントの既存タイムアウト（OpenAI SDK のリクエストタイムアウト / VOICEVOX クライアントの AbortController）に委譲する。
- ロックの `ExpiresAt` 窓は、上流の最大ストリーム時間を上回る長さにする（値は[チャット API](../../specs/livetalk/api/chat.md)を参照）。タイムアウトを撤去した結果「ロック失効 = ストリーム上限」の前提が消えたため、正常な長尺ストリーム中にロックが奪取されないようにする（通常は完了時の `finally` で即時解放され、`ExpiresAt` はクラッシュ／ハング時の粗いフェイルセーフ）。
- ガードの DynamoDB 呼び出しが失敗した場合は **フェイルオープン**（警告ログを残してバイパスし、チャットは通す）。

**根拠・トレードオフ**

- ✅ 新テーブル不要・IAM 変更不要で、条件付きの `UpdateItem` によりアトミックに判定・加算できる。ロック→レート順でレート枠を保護する
- ⚠️ 1 分の戻しに失敗すると、その 1 回を多く数えたままになる (止める側にずれる)。戻しの失敗はエラーイベントに warning で報告する
- ⚠️ route 層に決定論的な上限を持たないため、実効上限は上流クライアントのタイムアウト依存（OpenAI SDK 既定は緩め）。必要なら将来クライアント側のタイムアウトを明示的に絞る
- ⚠️ フェイルオープンのため、DynamoDB 障害時はガードが効かない（コスト保護より可用性を優先する判断）
- ⚠️ クライアントが応答中にアプリを閉じても上流処理は中断されず、その間ロックを保持する（`ExpiresAt` が粗いフェイルセーフ）。閉じた直後の再送が並行ガードで 429 になるのはこの仕様による意図どおりの挙動。上流処理ごと中断するには `AbortSignal` を usecase へ伝播する必要があり、将来課題とする
- ⚠️ OpenAI 利用額の上限ガード（budget alert 等）はインフラ管轄外のため本対応では見送り（OpenAI コンソール側の運用設定領域）

### 2.21 退会・データ削除は即時ハード削除、セーフティログのみ匿名化して残す（ADR / Issue #3532）

**背景・問題**

18 歳同意・プライバシーポリシーは整備済みだが、「忘れてもらう権利」（自分のデータを消してサービスから抜ける導線）が存在しなかった。Message は TTL 90 日で自然消滅するが、**Memory Tier A/B・MemorySummary・Affection は在籍中は無期限保持**で、ユーザーが自発的に消す手段が記憶の個別削除（`DELETE /api/memory/:id`）しかない。公開フェーズ（招待制 → 一般公開）では、退会と一括削除の導線が要件レベルで必要。

**決定**

- **退会 = 即時ハード削除**。`PK=USER#<userId>` 配下の全 item（Profile / Message / Memory / Summary / Affection / Knowledge / Note / Notification / PushSubscription 等）を一括削除する。論理削除＋猶予期間は本サービスの規模に対して過剰なため採らない。
- **例外: SafetyEvent は残す**。自傷・希死念慮の検出ログは、Character.AI / OpenAI の訴訟事例（ADR-009 の動機）を踏まえ、開発者防御の証跡として保持する。ただし退会時に **ユーザー ID 等の個人識別子を切り離した匿名化レコード**へ移し、横断レビュー用領域（ADR-2.22 の GSI 配下）でのみ参照できるようにする。保持期限は検出から 3 年とし（暫定、公開フェーズの法務レビューで確定する）、TTL で自動削除する。匿名化しても期限は引き継ぎ、付け直さない。退会時の案内もこの期限に合わせる。
- **退会のスコープは livetalk サービスのデータのみ**。プラットフォームの Google アカウント自体や他サービスのデータは対象外。RBAC role（`livetalk-user`）の剥奪は運用（人力）で行う。
- **データエクスポート（セルフサービスのポータビリティ）は作らない**。国内法（個人情報保護法）で必須なのは開示請求への対応であり、これは運用（問い合わせ対応での手動開示）で代替する。セルフサービス化は将来検討（roadmap）。

**根拠・トレードオフ**

- ✅ 「忘れてもらう権利」を満たしつつ、セーフティの法的証跡を失わない / 論理削除を持たないぶん実装・整合性がシンプル
- ✅ エクスポートを運用対応に倒すことで、公開前に塞ぐべき削除導線へスコープを集中できる
- ⚠️ ハード削除は不可逆（確認フロー必須）。SafetyEvent の匿名化と保持期限の運用は別途整備が要る

**実装メモ（HOW / Issue #3579）**

上記「別途整備」のうち、退会の実装で確定した設計判断（コードからは読み取れない「なぜ」）を残す。

- **削除は生 item 走査で実装**。`PK=USER#<userId>` を Query で全件取得し、SK が `SAFETY#` 以外を `BatchWriteItem` で削除する。SK 種別を列挙せず走査するため、将来の item 種別追加に自動で追従する。
- **1 PK スコープ・冪等。完全原子性は持たない**。DynamoDB に「PK 一括削除」がないため `BatchWriteItem` ＋ 未処理リトライで進め、リトライ上限後も残存すれば例外を返して再実行に委ねる（途中失敗は再実行で収束）。退会は本人セッションのユーザー ID のみを対象とし、他ユーザーには波及しない（dev 実地検証で 1 PK スコープを確認）。
- **匿名化 = SafetyEvent の re-key**。`TransactWrite` で `PK=USER#ANON#<ulid>` へ移し、`UserID` を **不可逆なランダム匿名トークン**へ置換する。ユーザー ID から決定論的に導出する擬似匿名化（pseudonymization）は採らない —— 横断グルーピングの利便より「個人識別子を切り離す」真の匿名化を優先したため。`InputText`/`ResponseText` は開発者防御の証跡として保持し、`GSI2PK`/`GSI2SK` を維持して横断レビュー（ADR-2.22 / Issue #3580）に残す。
- **退会後の遷移**。サインアウトは Cookie 発行元の auth サービスに集約しており、livetalk は `/api/auth/signout` への POST を受け付けない。そのため `next-auth/react` の `signOut` は使わず、ヘッダーのサインアウトと同じく auth サービスのサインアウト URL へ遷移し、callbackUrl に公開オリジンを渡してトップへ戻す。

### 2.22 セーフティイベントの横断レビューは sparse GSI + 管理画面（ADR / Issue #3532）

**背景・問題**

requirements 3.2 はセーフティ検出ログを「別領域・人間レビュー可能」と定めるが、実態は同一テーブル・ユーザー PK 配下の `SAFETY#` SK プレフィックス分離（論理分離）にとどまる。SafetyEventRepository は `create` と `getById`（EventID 既知前提の単件取得・主にテスト用）しかなく、**運営が全ユーザー横断で最近の検出を一覧する手段が物理的に存在しない**。「ログは取っているが誰も見られない」状態で、「人間レビュー可能」要件が実態として未達。

**決定**

- **sparse GSI（GSI2）で全 SafetyEvent を横断 Query** する。ADR-2.19（Profile 列挙の sparse GSI）と同じパターンで一貫させる。
  - `GSI2PK='SAFETY'` を SafetyEvent item にのみ付与（sparse）。`GSI2SK` = 検出時刻ベースの ULID（時系列降順で「最近の検出」を取得）。
  - 射影は一覧表示に必要なメタデータを `INCLUDE`。実装で確定した属性は `UserID`（匿名化済みユーザー参照）/ `EventID` / `CharacterID`（キャラ）/ `Trigger`（応答種別）/ `DetectedPattern`（検出パターン）/ `CreatedAt`（検出時刻）。**PII（`InputText` / `ResponseText`）は射影しない**（横断レビューはメタデータのみ。フル本文が要る場合だけベーステーブルの `getById` 経由）。なお `CharacterID` は本対応で SafetyEvent に追加した（既存レコードには無いため optional）。
- **`livetalk:admin` 権限の管理画面**で時系列一覧を提供する。SCR-009（ステータス画面）の拡張とし、新規ページは増やさない。
- ユーザーが在籍中は SafetyEvent にユーザー ID を保持し、退会時に匿名化する（ADR-2.21）。GSI2 はどちらの状態でも横断 Query できる。

**根拠・トレードオフ**

- ✅ 既存の sparse GSI パターンに揃い、全件 Scan を避けて横断 Query できる / admin 画面は既存の `livetalk:admin` 基盤に乗る
- ⚠️ GSI 追加は CDK / インフラ変更を伴う（DynamoDB の GSI 増設）。**増設しただけでは Query できない**: その GSI を Query する各ロールは、テーブルを `fromTableArn` ではなく `fromTableAttributes` + `globalIndexes` でインポートしないと grant に `table/.../index/*` が含まれず `dynamodb:Query` が `AccessDenied` になる（batch ロール=#3527、web の status 画面ロール=#3580 で 2 度顕在化）。GSI を増やすときは「テーブル定義・各ロールの import/grant・Query 実装」をセットで更新する

### 2.23 親密度は累積接触量として保持するが、現状は体験へ未反映（ADR / Issue #3532）

**背景・問題**

ADR-005 は「親密度は上昇のみ」を決めたが、**値がどの体験（第一声・口調・通知文面）に、どの閾値で効くのかがどのドキュメントにも無い**。実装を読むと、`AffectionLevel` は会話完了時（`calculateAffectionDelta`）と日次バッチ（`calculateBidirectionalityDelta`）で計算・加算・保存されるが、**読み出して体験へ反映している箇所はゼロ**（`summarize.prompt.ts` が文言で曖昧に触れるのみ）。つまり現状は「溜まるだけで使われない死蔵データ」で、これは法務・安全の穴ではなく体験未完成（スペック負債）。

**決定（現状の明文化）**

- 親密度の現状は「**累積接触量（情報開示量・時間継続・双方向性の 3 軸）として計算・無期限保持しているが、第一声・口調・通知のいずれにも未反映**」であることを正式仕様として明記する。これにより「実装を読まないと分からない」状態を解消する。
- **値→体験のマッピング（閾値設計）と活用実装は、公開フェーズの体験完成に合わせて別途行う**（roadmap に将来課題として記載）。今回は閾値を確定しない。
- 値域は現状の生値（青天井の累積量）のまま据え置く。活用時にステージ正規化を検討する。

**根拠・トレードオフ**

- ✅ ①退会・③横断レビュー（公開前に塞ぐべき法務・安全）とスコープを分離し、緊急度に応じて優先度を付けられる
- ✅ 死蔵状態をドキュメントに固定することで、活用時の設計起点が明確になる
- ⚠️ 値が体験に効かないまま蓄積し続ける（活用着手まで「上昇のみ」の意味は演出に現れない）

### 2.24 知識・記憶を Topic 中心モデルに再設計する（ADR / Issue #3696）

今の挙動は[Topic](../../specs/livetalk/term/topic.md)、[SELF fact](../../specs/livetalk/term/self-fact.md)、[WEB fact](../../specs/livetalk/term/web-fact.md)、[care](../../specs/livetalk/term/care.md)、[集約バッチ](../../specs/livetalk/batch/consolidate-conversations.md)を参照。

**背景・問題**

ADR-007 で作った「Memory Tier A–D ＋信頼度＋cooldown ＋関連度フィルタ」と、勉強成果を貯める Knowledge / 興味を表す InterestCategory / 勉強候補の StudyTopic は、運用してみると差別化価値（「同じ時間軸で生きているキャラ」）を不安定にしていた。

- **線形増加・非集約**: 勉強成果が生のまま永続追記され、同一話題が繰り返し再調査・重複保存される（dev 実測で同一トピックが十数件に膨張）。
- **非リンク・非抽象化**: 同じ話題について「ユーザーが話したこと（記憶）」と「キャラが調べたこと（知識）」が別サイロに分断され、繋がらない・抽象化されない。
- **陳腐化の粒度を扱えない**: 揮発情報（在庫・価格・順位）と安定情報（作品の事実等）を区別せず一律間隔で再調査し、陳腐な再要約を量産する。
- **忘却・想起の機構が過剰**: Tier ＋信頼度 ＋cooldown は、目的（誤情報の忘却 / 些細情報の連呼防止）に対して複雑すぎ、かつ「削除しても LLM が言い続ける」問題（ADR-007）を根本解決していない。

**決定**

知識・記憶の単位を **Topic（話題）** に置き直す。Topic は 1 レコードではなく、Topic ヘッダと、その配下の **SELF fact（会話由来・削除単位）**・**WEB fact（勉強由来・鮮度単位）** を束ねた集約体とする。これにより「話したこと」と「調べたこと」が同一話題で自動的にリンクする。

- **集約（consolidation）**: 未集約の元データ（会話ログ・Web 取得生）を毎時バッチで Topic に畳む。書き込みは元データへの append のみで、畳み込みはバッチに寄せ、会話ホットパスで集約 LLM を呼ばない。
- **想起は関連度 only**: 会話時は発話の埋め込み類似度で関連 Topic のみを文脈に注入する。Tier・cooldown・嗜好の常時注入を廃止し、関係ない話題が湧く “コーヒー病” を構造で回避する。素性（名前・制約）以外のコアプロフィール常時注入はせず、care も想起の下駄にしない。
- **忘却は決定的削除 ＋ 即時要約再生成**: SELF fact を物理削除し、その場で当該 Topic の要約を作り直す。LLM の「言うな」抑制に依存しない（ADR-007 の前向き整合の延長）。畳み済みの生ログが復活しないことは、前進のみのカーソルが担保する。
- **鮮度追随は揮発 WEB fact 単位**: 揮発性の高い WEB fact だけに再確認の期限を持たせ、安定 fact は再確認しない。再確認の期限は fact ごとに持つが、**再取得は Topic 単位に束ねる**(同じ Topic で期限切れの fact が複数あっても Web 検索は 1 回とし、それらの期限をまとめて前進させる)。検索クエリは Topic から作られるため fact 単位で取ると同じ検索を重ねるだけになり、dev 実測では鮮度切れ再取得の約 3 割が同一実行内の重複検索だった。なお、再確認を起こす契機は当初の「期限到来時の走査」から「Topic が使われたとき」へ変わった (ADR-2.26)。
- **ノートは Topic からのギフト生成**: 「なぜ調べたか（SELF フック）＋調べた内容（WEB）」を合成した共有ログを、キャラの proactive なギフトとして記録する。ユーザーが会話で依頼した調べ物の結果は会話で返し、ノートには倒さない。
- **優先度は care に一元化**: 自発リサーチの選定と能動通知の閾値を、Topic の注目度 `care`（回数ベースの興味強度・情動重み付けなし）で駆動する。
- **旧資産の撤去**: Memory Tier / MemorySummary / InterestCategory / 旧 Knowledge・Note / 知識蓄積用途の StudyTopic を廃止する。通知の escalation 信号も InterestCategory.Weight から care へ差し替える。撤去は「新想起が dev で機能確認できてから旧経路を外す」順序で行い、中間の記憶喪失状態を作らない。

**根拠・トレードオフ**

- ✅ 集約により勉強成果が無限に溜まらず、同一話題で SELF/WEB が融合した応答（「二郎系好きだったよね、新店できたよ」）ができる。揮発情報だけ賢く追随し、安定情報の無駄な再調査をやめられる。
- ✅ 忘却が構造的に確実になり（削除＝即再生成）、想起も関連度 only で「湧いてくる」副作用を断てる。
- ⚠️ **Topic ルーティング / マージ品質が律速**。近い素材を 1 つの Topic に畳みきれず割れる（過分割）リスクがあるため、生断片の provenance を保持して誤マージを可逆化し、条件付き書込・人手削除を最優先の是正手段とする。
- ⚠️ **旧データは一回性マイグレーションで畳み直した**（クリーンスタートではない）。移行は dev・prod とも完了し、旧スキーマのアイテムも削除済みのため、移行用のコードと Lambda は撤去した。
- ⚠️ care はユーザー起点でのみ上げる（下記）。この分岐が無いと自己強化ループに陥る。
- ⚠️ グラフ DB・ベクトル DB は導入しない。関連は事前計算せず、想起時に埋め込み近傍でその場算出する。

**care 上昇ポリシー（ユーザー起点でのみ上げる・レバー1）**

care は「ユーザーがその話題をどれだけ気にしているか」の信号であるべきなので、**care を上げてよいのはユーザーが会話で触れた fold だけ**とし、キャラの自発リサーチ（Web 取得のみ）を畳んだ fold では上げない。集約時にその fold が生んだ SELF fact の有無を代理信号にして分岐する（SELF fact＝ユーザーが会話で触れた）。

この分岐が無いと、ユーザーが一言も足していない話題でもキャラが自発リサーチを畳むだけで care が育ち、「高 care → もっと自発リサーチ → もっと care」の自己強化ループになる（dev 実測: キャラ自身のパーソナ Topic が育ち、キャラが自分自身を通知した）。一過性の「◯◯調べて」だけで SELF fact が出ない依頼は興味とみなさず care に載せない、という割り切りを取る。

**既知の制約（静観・後回しの判断）**

以下は本再設計で「実害が積み上がるまで静観」と判断した事項。判断がセッションの継ぎ目をまたぐため永続化する。

- **所見C: ルーティング / マージ品質（過分割）**: consolidation の埋め込み近傍 ＋ LLM のマージ判断が近似重複を吸収しきれず、近い話題が複数 Topic に割れることがある（dev 実測。冗長な旧データほど顕在化し care も分散する）。移行固有ではなく consolidation 本体の性質。prod は旧データが小さく影響は軽い見込みで、現状は静観。将来はルーティング/マージ閾値の改善、または近似 Topic の merge/dedup パスで対処する。
- **所見D: 想起が汎用発話に弱い**: 現状の想起は「今の 1 発話だけ」を埋め込み、care を使わない（関連度 only）。そのため「いいゲームないかな」のような汎用発話は具体名の Topic と類似度が閾値に届かず想起されない（語が一致する「ラーメン食べたい」等は想起される）。前者は要件（発話＋直近文脈を埋め込む）との実装乖離＝直せるギャップ、care 不使用は “コーヒー病” 回避のための意図的な選択。将来は「想起クエリに直近数ターンを含める」／「類似度がニアミス帯のときだけ care で後押しする」で改善余地があるが、過剰想起の再来に注意し現状は静観。
- **所見E (解消済み): 鮮度追随の「変化時のみ更新」が実質機能していない**: 変化判定は既存の WEB fact 1 件 (狭い単一の主張) と、再取得した Topic 全体の要約を比べていたため、ほぼ常に「変化あり」になっていた (dev 実測で 9 割超)。加えて consolidation は WEB fact を追記するだけで置き換えなかったため、fact は減らずに増え続け、期限ごとの走査による再確認のバックログに処理が追いつかなかった。2026 年 10 月の prod ではリサーチ約 2,000 回のうち 1,829 回がこの再取得だった。モデルや推論設定では直らず、判定と集約の構造に起因していたため、再確認の契機を「使われたとき」に変え、集約が新しい事実を既存の事実と見比べて件数に上限を持つ形にして解消した (ADR-2.26)。

**将来拡張（レバー2・未実装）: care を「累計回数」から「最近のユーザー興味」へ**

現状 care は累計回数で単調増加し、明示的な減衰を持たない。将来的には care を「最近ユーザーが触れたか（最近性）」に再定義し、明示的な減衰 cron を持たずに通知・ノート・自発リサーチの候補を並べることで、古い話題が希少な通知枠を占め続けるのを自然に防げる。会話での想起は既に関連度 only で自然に薄れているため、優先度側にも最近性を効かせるのが筋。本対応（レバー1）では実装せず、拡張余地として記録に留める。

### 2.25 勉強は利用者単位の 1 日の回数で上限を持ち、離れた利用者では止める (ADR / Issue #4607)

今の上限と挙動は[勉強バッチ](../../specs/livetalk/batch/acquire.md)を参照。

**背景・問題**

勉強 (Web リサーチ) の上限は「キャラクターごと・1 回の実行ごと」にしかなく、利用者単位・全体の上限がなかった。利用者 1 人の原価が、話すキャラクターの数だけ増える。さらに、勉強の対象は lifecycle のある (利用者 × キャラクター) の組で、一度作られると退会まで消えないため、話さなくなった利用者のためにも勉強が続いた。費用の約 7 割は Web 検索で、リサーチ 1 回で何回検索するかはモデル任せのまま、回数も記録されていなかった。

**決定**

- **上限は利用者単位で、回数で数える**。会話からの依頼・鮮度の確認・自発リサーチを同じ枠で数える。値は 1 日 20 回の仮の値で、1 か所の定数にまとめる。区分 (プラン) ごとに値を変える仕組みは作らない。
- **期間は日本時間の暦日**。月で数えると、月の初めに使い切って残りの期間ずっと勉強が止まりうる。上限いっぱいで月約 1,200 円 (リサーチ 1 回約 2 円)。
- **枠は勉強中のキャラクターで等分する**。勉強中とは、後述の 3 日ルールで止まっていないキャラクター。就寝中のキャラクターも配分には含める。日の途中で勉強中のキャラクターが増えたときは偏ってよい (あとから入ったキャラクターが、その日は 0 回になることがある)。
- **キャラクター別と利用者合計の両方を数える**。勉強中の人数が日の途中で減ると、キャラクター別の枠だけでは合計が利用者の上限を超えるため。合計だけが断った場合は、キャラクター別の加算を戻す。
- **失敗したリサーチも、1 回の実行の予算に数える**。試した時点で成否にかかわらず予算を減らす。
- **カウンターの障害時は、その組の勉強を止める**。止めた利用者はバッチの失敗として報告する。
- **最後に話してから 3 日たったキャラクターは勉強の対象から外す**。「話した」はユーザーの発話だけで、通知のタップは含めない。最後の発話の時刻は、平常通知の周期と同じく発話の履歴から求める。外れる条件と再開の仕方は[勉強の停止](../../specs/livetalk/term/study-pause.md)を参照。
- **Web 検索の回数をリサーチごとにログへ出し、バッチの完了ログに合計を載せる**。外部の検索 API への切り替えはしない (今の OpenAI の Web 検索のまま)。
- 数える仕組みのうち、条件付きの加算と戻し (DynamoDB) は `@nagiyu/aws`、日本時間の日・月のキーと TTL の計算は `@nagiyu/common` の共通部品とし、Quick Clip の利用回数と共有する ([shared-libraries.md](../../development/shared-libraries.md))。

**根拠・トレードオフ**

- ✅ 利用者 1 人の勉強の原価に上限が付き、キャラクターを増やしても増えない。Web 検索の回数が追えるので、上限の値を実測で直せる
- ✅ 3 日ルールで、離れた利用者のためにリサーチ費用をかけない
- ✅ 重要通知も同じ条件で止める (ADR-2.27)
- **カウンターの障害時は止める側に倒す**。数えられないまま勉強すると、原価の上限を守れないため。Quick Clip の利用回数と ADR-2.20 のチャットのガードは、障害時に通す側に倒しており、ここは逆になる
- 利用者の区分と課金は扱わない。本番での使用感を見てから別に進める
- ⚠️ 上限の値は仮。1 回の重さのばらつきは小さいので回数で数えるが、Web 検索の回数はモデル任せで、1 回あたりの原価は変わりうる
- ⚠️ 等分のため、1 人のキャラクターだけが活発でも、勉強中のキャラクターが多いとそのキャラクターの枠は小さい

### 2.26 鮮度は使われたときだけ確認し、WEB fact は区分ごとの件数で保つ (ADR / Issue #4607)

今の挙動は[鮮度確認の依頼](../../specs/livetalk/term/freshness-check-request.md)、[WEB fact](../../specs/livetalk/term/web-fact.md)、[集約バッチ](../../specs/livetalk/batch/consolidate-conversations.md)を参照。

**背景・問題**

ADR-2.24 の鮮度追随は、期限の来た揮発 WEB fact を走査して再取得していた。会話に出てこない Topic まで期限ごとに調べ直すため、勉強の枠の大半がここに使われた。また変化の判定が実質機能せず (所見E)、集約は WEB fact を置き換えずに足すので、Topic の WEB fact は増え続けた (dev では 1 Topic に 100 件ほど)。会話は想起した Topic の WEB fact を全件プロンプトに入れるため、事実が増えるほど原価が増え、古い事実と新しい事実が混ざって伝わった。

**決定**

- **鮮度の確認は、Topic が使われそうになったときだけ依頼する**。「使われた」とは、会話の想起で発話に直接近い Topic (direct) として選ばれたとき、および通知のバッチで重要通知の判定の候補や平常通知のネタになったとき。周辺の Topic (related) は含めない。その Topic に再確認の期限切れの WEB fact があれば確認の依頼を記録し、取得バッチが調べ直す。会話中にその場では調べない。
- **取得バッチの処理順は、会話からの依頼、確認の依頼、自発リサーチ**。確認の依頼は利用者の 1 日の枠を使う。依頼は最初のものを残し、上書きで処理順を後ろへ回さない。枠や予算で後回しになり続けた依頼は TTL で消える。消えても、その Topic が次に使われたとき再び依頼される。
- **鮮度掃引用の GSI は廃止した**。再確認の期限は確認が要るかの判定に使うため WEB fact に残す。
- **集約は、新しい WEB fact を統合先 Topic の既存の WEB fact と見比べ、追加・置き換え・重複のいずれかにする**。
    - 置き換えは「古いものを消して新しい事実を作る」。作成日時が新しくなるので、ノートの再評価の条件 (ADR-2.29) に乗る。再確認の期限は、新しい事実の揮発性と集約時刻から付け直す
    - 重複は新しい事実を保存せず、元の事実の観測日時と再確認の期限を集約時刻で更新する。自発リサーチの間隔の判定が最新の観測日時を見ているため、更新しないと同じ Topic を毎回調べ直す
- **Topic あたりの WEB fact に、揮発性の区分ごとの上限を置く**。stable 以外 (low / medium / high) をひとまとめ、stable を別に数える (件数は仮の値)。観測日時の古いものから消す。上限の適用に失敗しても、集約とカーソルの前進は止めない。
- **読む側は区分を問わず観測日時の新しい順に N 件だけ使う**。用途ごとの件数は[WEB fact](../../specs/livetalk/term/web-fact.md)を参照。有無や増加の判定は全件で行う。
- **すでに溜まっている Topic に専用の掃除は作らない**。使われる Topic は、会話 (鮮度の確認) や自発リサーチを経て必ず集約を通り、そこで上限まで減る。集約を通るまでの間も、読む側が新しい側の上限までしか取らないので原価は膨らまない。使われない Topic は溜まった件数のまま残るが、害は保存量だけ。

**根拠・トレードオフ**

- ✅ 会話に出ない Topic を調べ直さなくなり、勉強の枠を新しい情報の探索に回せる。会話の原価が WEB fact の総数に比例しなくなる
- **区分ごとに上限を分けた理由**: 合計で数えると、stable だけで上限が埋まった Topic では、新しく調べた stable 以外の事実 (ライブの日程など) が足したそばから消え、新しい情報が残らず、自発リサーチの間隔の判定も効かず毎回調べ直す。stable を数から外すだけにしなかったのは、stable が集約の LLM の付ける区分で、付け間違えると上限なしで溜まるため
- **置き換えた古い事実は残さず消す**: 残すと件数の上限を圧迫し、古い事実と新しい事実が混ざる原因に戻る
- **見比べの方法**: 振り分けの判断基準の文言は変えず、候補 Topic ごとの既存の WEB fact を番号付きで渡し、新しい事実ごとに追加 / 置き換え (番号) / 重複 (番号) を返させる
- ⚠️ 確認の依頼は次の取得バッチまで処理されないため、使われた直後の会話は期限切れの事実を含みうる (会話中にその場では調べない判断)
- ⚠️ 期限切れの WEB fact がある Topic は、確認が済むまで重要通知を出さない (ADR-2.27)。確認が枠で後回しになれば、その分通知も遅れる

### 2.27 重要通知は同じ話題・同じ予定を 1 度だけ送り、勉強が止まったら止める (ADR / Issue #4607)

今の挙動は[通知バッチ](../../specs/livetalk/batch/notify.md)を参照。

**背景・問題**

重要通知 (ADR-2.11 のクリティカル escalation) には、同じ話題を続けて送らないための抑止がなかった。また、勉強が止まった (ADR-2.25) 後も重要通知を出し続けると、情報が更新されないまま、延期や中止を拾えずに「もうすぐある」と通知しうる。平常通知の文面は「見つけたよ」「調べておいたよ」と勉強したことを前提にしている。

**決定**

- **同じ話題・同じ予定の重要通知は 1 度だけ送る**。通知の記録に重要通知の予定の日付を残し、送り済みの話題・予定を判定から外す。予定の日付が変われば新しい予定として改めて送る。日付が記録に無い旧データは、話題ごと送り済みとして扱う。
- **期限切れの WEB fact がある Topic は、確認が済むまで重要通知を出さない**。通知の候補になった時点で確認を依頼する (ADR-2.26)。古い情報で通知しないため。
- **重要通知も、最後の発話から 3 日で止める**。条件は勉強と同じ (ADR-2.25)。
- **平常通知の周期は今のまま**(無視されるたびに間隔が延び、約 1 か月で止まる)。ただし勉強が止まっている間は、話題名を入れない文面だけを使う。

**根拠・トレードオフ**

- ✅ 同じ通知の繰り返しと、古い情報による誤った通知を避けられる
- ✅ 平常通知は止めずに文面だけ変えるので、離れた利用者への「追わない」スタンス (ADR-2.11) を保ったまま、勉強していない事実を言わずに済む
- ⚠️ 予定の日付を取れなかった旧データは、話題ごと 1 度きりになる

### 2.28 自発リサーチは、利用者の興味から角度を広げる探索にする (ADR / Issue #4607)

今の挙動は[勉強バッチ](../../specs/livetalk/batch/acquire.md)と[探索の記録](../../specs/livetalk/term/exploration.md)を参照。

**背景・問題**

自発リサーチのクエリは常に「{話題名} 最新情報」で、興味から角度を広げる段がなかった。「ボカロが好き」と話しても、ライブの情報のような周辺の話題は出てこず、同じ話題の最新情報を繰り返し取ってくるだけだった。

**決定**

- **起点の Topic から、軽い LLM で検索の角度 (クエリ) を 1 つ作り、リサーチ 1 回で探索する**。検索の回数は増やさない (利用者の 1 日の枠、ADR-2.25)。角度の生成に失敗したときは、従来の「最新情報」のクエリに落とす。
- **起点にするのは care 1 以上の Topic に限る**。care は利用者が会話で触れたときにだけ上がる (ADR-2.24) ので、1 以上は利用者の興味を表す。探索の結果として集約された care 0 の Topic まで起点にすると、利用者の興味から離れた探索が連鎖する。
- **外れた情報が混ざってもよい**。会話のネタになればよいため、利用者がまだ知らなさそうな周辺 (関連するイベント・新作・関わる人物など) を選ばせる。すでに知っている事実と最近探索した角度に重ならないようにする。センシティブな内容には踏み込まず、趣味・関心の範囲で広げる。
- **起点が気分・体調・悩み (憂鬱、眠気、疲れなど) のときは、解決策や公的な情報には広げず、気分転換になる軽い話題へ広げる**。説教っぽくならないようにするため。
- **探索の記録 (起点ごとの最後の探索時刻と最近の角度) を、Topic とは別のアイテムで持つ**。探索の結果は別の Topic に集約されうるため、起点の WEB fact の観測日時が進まず、観測日時だけでは間隔を空けられずに起点を毎回探索してしまう (dev では、同じ起点を毎時 10 回調べていた)。Topic のヘッダに足さないのは、ヘッダを集約が楽観ロックで書き換えるため。ノートの見送りの記録 (ADR-2.29) と同じ置き方にした。
- **探索の結果の出し先は会話だけとし、ノート・通知・想起の範囲は変えない**。探索で得た情報は care 0 の Topic に集約されることが多く、care を閾値にするノートや通知には出ない。会話では、発話が調べた Topic に直接近いときだけ想起される (「ボカロのイベント行きたい」には出るが、「ボカロばっか聴いてる」には出ない)。想起を広げて何でも引っ張ってくるのも望ましくないため、出し方は本番での様子を見てから決める。
- 探索は、事実の整理 (ADR-2.26) の後に行う。古い事実が混ざったままでは、探索の質を判断できないため。

**根拠・トレードオフ**

- ✅ 検索の回数を増やさずに、周辺の新しい情報が会話のネタとして集まる
- ✅ 起点を care 1 以上に限ることで、探索が利用者の興味から離れて連鎖しない
- ⚠️ 角度の質は LLM 任せで外れることがある (許容)。外れた情報でも、会話以外には出ない
- ⚠️ 角度の生成に LLM を 1 回足す (軽いモデルで足りる)

### 2.29 ノート生成の「生成しない」判断を記録し、WEB fact が増えるまで評価し直さない (ADR / Issue #4607)

今の挙動は[集約バッチ](../../specs/livetalk/batch/consolidate-conversations.md)と[ノート](../../specs/livetalk/term/note.md)を参照。

**背景・問題**

ノートの生成は、生成しないと判断した結果を覚えておらず、毎時同じ候補を LLM に評価させ直していた。

**決定**

生成しないと判断した時刻を、Topic ごとに別のアイテムで記録する。その後に Topic へ新しい WEB fact が増えたとき (作成日時が判断より新しい) だけ評価し直す。

**根拠・トレードオフ**

- ✅ 評価の入力が変わっていないのに LLM を呼ぶ無駄がなくなる
- 判断の基準を「新しい WEB fact が増えたか」にしたのは、ノートが SELF フックと WEB fact の合成で、評価の入力のうち変わりうるのが WEB fact だから。集約の置き換え (ADR-2.26) も新しい事実を作るので、この条件に乗る
- ⚠️ SELF fact だけが増えた場合は評価し直さない

## 3. データモデル概要

DynamoDB Single Table（`nagiyu-livetalk-dynamodb-{env}`）。

- PK = `USER#<userId>`
- SK 階層パターン（例）:
  - `PROFILE`
  - `CHAR#<charId>#STATE` / `#LIFECYCLE` / `#AFFECTION`
  - `CHAR#<charId>#MSG#<ulid>`（Message、TTL 90 日。集約の元データを兼ねる）
  - 知識・記憶は Topic 中心（ADR-2.24）。1 Topic は「ヘッダ ＋ SELF fact ×N ＋ WEB fact ×N」を SK プレフィックスで束ねた集約体で、`begins_with(TOPIC#<topicId>#)` で一括取得する:
      - Topic ヘッダ `CHAR#<charId>#TOPIC#<topicId>#META`（subject・要約・category・care・想起用の embedding を同居。恒久・集約でのみ更新）
      - SELF fact `CHAR#<charId>#TOPIC#<topicId>#SELF#<ulid>`（会話由来・ユーザー削除単位）
      - WEB fact `CHAR#<charId>#TOPIC#<topicId>#WEB#<ulid>`（勉強由来・鮮度単位。揮発 fact のみ再確認期限を持つ）
  - `CHAR#<charId>#NOTE#<ulid>`（共有ログ Note。Topic を参照するギフト記録、恒久）
  - `CHAR#<charId>#WEBRAW#<ulid>`（Web 取得生。未集約の元データ、TTL 90 日）
  - `CHAR#<charId>#CURSOR`（集約カーソル。会話生・Web 取得生のストリーム別に、どこまで畳んだかを条件付きで前進させる状態）
  - Topic の束 (`TOPIC#<topicId>#`) の外に置くアイテム。Topic を一括取得する `begins_with` に混ざらないようにするため:
      - `CHAR#<charId>#FRESHCHECK#<topicId>` (鮮度確認の依頼。使われた Topic の期限切れ WEB fact を取得バッチに知らせる、TTL 7 日、ADR-2.26)
      - `CHAR#<charId>#NOTESKIP#<topicId>` (ノートを生成しないと判断した時刻、恒久、ADR-2.29)
      - `CHAR#<charId>#EXPLORE#<topicId>` (自発リサーチの起点ごとの最後の探索時刻と最近の角度、恒久、ADR-2.28)
  - `STUDYUSAGE#<YYYYMMDD>` (勉強の 1 日の回数。日本時間の暦日ごとに 1 item で、キャラクター別と利用者合計の回数を属性に持つ。TTL は日が終わった翌日、ADR-2.25)
  - `SAFETY#<ulid>`（SafetyEvent、TTL 3 年。退会時も削除せず匿名化して残し、期限は引き継ぐ、ADR-2.21 / 2.22）
  - `NOTIF#<ulid>`（NotificationEvent、TTL 30 日）/ `PUSH_SUBSCRIPTION#<id>`
  - `RATELIMIT#<window>#<bucket>`（チャットのレート制限カウンタ。window=`1m`/`1h`、`Count` を上限付きで加算・TTL で自動掃除、ADR-2.20）
  - `CHATLOCK`（チャットの in-flight ロック。実行中のみ存在し `OwnerToken` / `ExpiresAt` / `TTL` 付き、ADR-2.20）
- GSI1（Profile 列挙用 sparse GSI、ADR-2.19）:
  - `GSI1PK='PROFILE'` を Profile item にのみ付与（sparse）/ `GSI1SK` = 生の `UserID` / 射影は `KEYS_ONLY`
  - バッチのユーザー列挙（`ProfileRepository.listAllUserIds`）が全件 Scan を避けてこの GSI を Query する
- GSI2（SafetyEvent 横断レビュー用 sparse GSI、ADR-2.22）:
  - `GSI2PK='SAFETY'` を SafetyEvent item にのみ付与（sparse）/ `GSI2SK` = 検出時刻ベースの ULID（`EventID` をそのまま使用。時系列降順で最近の検出を取得）/ 射影は `INCLUDE`（`UserID` / `EventID` / `CharacterID` / `Trigger` / `DetectedPattern` / `CreatedAt`。PII の `InputText` / `ResponseText` は射影しない）
  - `livetalk:admin` の管理画面が全ユーザー横断で SafetyEvent を Query する（全件 Scan を避ける）
  - ⚠️ GSI を Query するロールは、テーブルを `fromTableAttributes` + `globalIndexes` でインポートして `index/*` を grant する必要がある（`fromTableArn` だと `AccessDenied`。ADR-2.22 の根拠・トレードオフ参照）
- Topic 中心モデル（ADR-2.24）が追加する sparse GSI（既存 GSI1/GSI2 と衝突しない名前で増設）:
  - **Topic 列挙用 GSI**: Topic ヘッダのみを索引化する。`#META` が SK の接尾辞のため `begins_with` ではヘッダだけを列挙できないことへの対応。想起用の embedding と care を射影し、想起（全 Topic の座標だけを読んで自前で cosine 計算）と自発リサーチ（care 降順の選定）の双方を、Topic 本体を全読みせずに賄う
  - 鮮度掃引用の GSI は、鮮度の確認を「使われたとき」の依頼に変えたため削除した (ADR-2.26)。WEB fact の再確認期限は、確認が要るかの判定のために残す
  - ⚠️ 増設した GSI を Query する各ロールにも、GSI2 と同じく `fromTableAttributes` + `globalIndexes` の grant が要る（ADR-2.22 の教訓）

**保持・削除ポリシー (ADR-2.21 / 2.24)**: 元データ (Message・Web 取得生) は TTL 90 日、通知履歴 (NotificationEvent) と勉強の依頼 (StudyTopic) は TTL 30 日、鮮度確認の依頼は TTL 7 日、勉強の 1 日の回数は日が終わった翌日まで、ノートの見送りと探索の記録は恒久、Topic 配下 (ヘッダ・SELF fact・WEB fact) と共有ログ Note は恒久、Affection は在籍中は無期限。退会時は `PK=USER#<userId>` 配下を即時ハード削除するが、SafetyEvent のみ匿名化 (個人識別子を切り離す) して保持する (保持期限は検出から 3 年の TTL で、匿名化しても引き継ぐ。暫定で、法務レビューで確定)。SELF fact のユーザー削除は物理削除で、当該 Topic 要約を即時再生成する (決定的忘却、ADR-2.24)。削除は「消す → 要約を再生成する」の順で行うため、再生成だけが失敗しても押し直しで直せるようにしてある。挙動は[記憶 API](../../specs/livetalk/api/memory.md)を参照。

詳細な SK 定義・属性は実装（`services/livetalk/core/src/mappers/keys.ts`、`entities/`）を参照。概念モデルは [external-design.md](./external-design.md) を参照。

## 4. インフラ構成

### 4.1 ECS Cluster / ALB 戦略

**ECS Cluster はプラットフォーム共通、ALB はサービスごとに個別** とする。

- 既存 `nagiyu-root-cluster-{env}` は Portal（root ドメイン）専用のため流用しない
- ECS Cluster は共有（`nagiyu-shared-cluster-{env}`）— Cluster 自体は無料、共有の副作用なし
- ALB は個別（`nagiyu-livetalk-alb-{env}`）— アイドルタイムアウト・TLS をサービス単位でチューニングできる方が望ましい。特に LiveTalk の LLM ストリーミングは長めのアイドルタイムアウトが必要。既存 Portal も個別 ALB のためパターン一貫
- Target Group / Listener Rule / Task Definition / Service も個別

配置: `infra/shared/lib/ecs-cluster-stack.ts`（共通 Cluster）、`infra/livetalk/`（ALB / Service / CloudFront / DynamoDB / Batch 等）。

### 4.2 利用する AWS サービス

| AWS サービス                   | 用途                                                                      |
| ------------------------------ | ------------------------------------------------------------------------- |
| ECS Fargate                    | Next.js + VOICEVOX の 2 コンテナ Task                                     |
| Application Load Balancer      | サービス専用 ALB（LLM ストリーミング用に長めの timeout）                  |
| CloudFront                     | エッジ配信、ALB をオリジンとする（OriginReadTimeout 延長）                |
| DynamoDB                       | Single Table、PITR、Message は TTL 90 日                                  |
| Lambda + EventBridge Scheduler | バッチ（Topic 集約 / Web 取得 / 通知 / 活動時間学習）、各 Lambda 独立 + DLQ |
| ECR                            | Next.js / VOICEVOX / batch のイメージ                                     |
| Secrets Manager                | OpenAI API キー等                                                         |
| S3                             | モデル / 音声 / 静的ファイル                                              |
| Web Push（既存基盤）           | プッシュ通知配信                                                          |
| CloudWatch Alarms（→ admin）   | バッチ / ALB / DynamoDB の障害検知、admin 本流アラーム基盤へ接続（§2.18） |

リージョンは us-east-1 固定（`infra/bin/nagiyu-platform.ts`）。AZ は us-east-1a + us-east-1b。

### 4.3 バッチ構成

各バッチは独立 Lambda（障害切り分け・権限最小化のため DLQ / IAM Role も個別）。スケジュールと処理は、バッチごとの仕様カードを参照する。

| バッチ | 仕様カード |
| ------ | ---------- |
| consolidate (旧 compress を発展) | [集約バッチ](../../specs/livetalk/batch/consolidate-conversations.md) |
| acquire (旧 study を発展) | [勉強バッチ](../../specs/livetalk/batch/acquire.md) |
| learn-user-activity | [活動時間学習バッチ](../../specs/livetalk/batch/learn-user-activity.md) |
| notify | [通知バッチ](../../specs/livetalk/batch/notify.md) |

集約（畳み）と取得（Web アクセス）を別バッチに分けるのは、取得の失敗・レイテンシと畳みの整合性（カーソル前進）を独立に扱うため。時刻判定のため Web Task / 関連 Lambda には `TZ=Asia/Tokyo` を設定。

## 5. 技術スタック

| カテゴリ       | 技術                                                 | 選定理由                                                               |
| -------------- | ---------------------------------------------------- | ---------------------------------------------------------------------- |
| Live2D 描画    | pixi-live2d-display-lipsyncpatch（MIT）              | クライアント描画、リップシンク対応、OSS 実績                           |
| TTS            | VOICEVOX（セルフホスト）                             | 無料、日本語品質、ライセンス緩い、CPU で動く                           |
| LLM            | OpenAI gpt-5.6-luna                                  | 会話・要約・分類・リサーチを単一モデルに統一し、用途の差は推論量（reasoning effort）で付ける。推論トークンは出力として課金されるため、構造化抽出のような推論不要の用途では推論を切る |
| Web 検索       | OpenAI Web Search（`responses` + `web_search` tool） | Stock Tracker に実績、検索→要約→構造化が 1 API、抽象化で将来差し替え可 |
| 構造化出力     | Structured Outputs（zodTextFormat）                  | 型保証、silent failure 解消                                            |
| embedding      | OpenAI text-embedding-3-small                        | 記憶 retrieval の類似検索                                              |
| フロント / API | Next.js + Lambda Web Adapter                         | プラットフォーム標準、ECS Fargate で稼働                               |
| データ         | DynamoDB Single Table                                | プラットフォーム標準、TTL / PITR                                       |

プラットフォーム共通の技術選定（認証 NextAuth、CDK、Material-UI 等）は各共通ドキュメントを参照。
