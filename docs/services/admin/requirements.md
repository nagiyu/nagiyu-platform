# Admin サービス 要件定義書

この文書は、満たすべきこと (要件) を書く。今どう動くか (画面・API・バッチ・通知の経路・用語) は[仕様カード](../../specs/README.md)にある。このサービスの分は `docs/specs/admin/`。

---

## 1. ビジネス要件

### 1.1 背景・目的

nagiyu プラットフォームの管理機能を提供する Web アプリケーションとして、Admin サービスを開発します。

**Phase 1 の目的**:
- Auth サービスとの **SSO（シングルサインオン）連携動作確認**
- JWT ベースの認証基盤の実地検証
- ロールベースアクセス制御（RBAC）の動作確認

Phase 1 は最小限の実装（MVP）とし、早期にデプロイ・動作検証することで、認証基盤の信頼性を確保します。

### 1.2 対象ユーザー

**プライマリーユーザー**: プラットフォーム管理者
- Auth サービスで `admin` ロールを付与されたユーザー
- プラットフォーム全体の管理権限を持つ

**セカンダリーユーザー**: ユーザー管理者（Phase 2 以降）
- `user-manager` ロールを持つユーザー
- ユーザー管理機能にのみアクセス可能

### 1.3 ビジネスゴール

#### Phase 1 (MVP)
1. **SSO 連携の動作検証**: Auth サービスで発行された JWT クッキーを検証し、シームレスなログイン体験を提供
2. **RBAC の動作確認**: ロールベースでのアクセス制御が正常に機能することを確認
3. **早期デプロイ**: CI/CD パイプラインを先行構築し、開発環境へのデプロイを実現

#### Phase 2 以降
- CloudWatch Logs 閲覧機能の提供
- ユーザー管理 UI の実装
- プラットフォーム統計ダッシュボードの提供

## 2. 機能要件

### 2.1 ユースケース

各ユースケースの手順と例外の扱いは、右列のカードにある。ここには満たすべきことだけを書く。

| ID | ユースケース | 満たすべきこと | 今の挙動 |
|---|---|---|---|
| UC-001 | SSO によるログイン | Auth サービスで認証済みの管理者が、再ログインなしで Admin を使える。JWT がない、または無効なら Auth サービスのサインインへ誘導する | [システム系の API](../../specs/admin/api/system.md)、[ダッシュボード画面](../../specs/admin/screen/dashboard.md) |
| UC-002 | ユーザー情報の表示 | ダッシュボードで、ログイン中のユーザーの名前、メールアドレス、保有ロール一覧、JWT の有効期限、SSO 連携の動作確認メッセージを見られる。名前と JWT の有効期限は、現状は表示していない (#4690) | [ダッシュボード画面](../../specs/admin/screen/dashboard.md) |
| UC-003 | ロールベースアクセス制御 (RBAC) | ロールに応じて使える機能を制限し、`admin` は全機能を使える。必要なロールがなければ 403 を返す。ダッシュボードは `admin` または `user-manager` だけが開ける。現状はログインしていれば開ける (#4692) | [権限とロール](../../specs/admin/term/permission.md) |
| UC-004 | SNS 通知の受信とプッシュ通知の送信 (自己監視専用) | 新しいエラー通知の仕組み自身 (alarm-ingest・stream-handler・DLQ・error-events テーブル) が障害でも、管理者に Push が届くよう、本流とは独立した経路を持つ。履歴には残さず、Push だけ送る | [SNS 受信 API](../../specs/admin/api/notify-sns.md) |
| UC-005 | 管理者端末のプッシュ通知の購読 | `admin` ロールの管理者が、ダッシュボードから通知を有効にできる。権限のない利用者は登録できない | [Push 購読の経路](../../specs/admin/flow/push-subscription.md)、[Push 購読 API](../../specs/admin/api/notify.md) |
| UC-006 | プッシュ通知の受信 | CloudWatch Alarm の発火など、エラーが記録されたとき、ブラウザ (またはホーム画面に追加した Admin PWA) にプッシュ通知が届く | [エラー通知の経路](../../specs/admin/flow/error-notification.md)、[stream-handler](../../specs/admin/batch/stream-handler.md) |
| UC-007 | CloudWatch Alarm 由来のエラーの永続化 | 各サービスの CloudWatch Alarm の内容を ErrorEvent として共通のエラーストアに保存し、購読者へ Push を送る。保存に失敗しても、Push の配信に失敗しても、運用者が気づける | [alarm-ingest](../../specs/admin/batch/alarm-ingest.md)、[エラー通知の経路](../../specs/admin/flow/error-notification.md) |
| UC-008 | エラー履歴の一覧の閲覧 | `errors:read` を持つ運用者が、過去のエラーを時系列の降順で、サービスと期間で絞って見られる。権限がなければ、その旨を表示する | [エラー履歴一覧画面](../../specs/admin/screen/errors.md)、[エラー履歴 API](../../specs/admin/api/errors.md) |
| UC-009 | エラー詳細の閲覧 | `errors:read` を持つ運用者が、1 件のエラーのメタ情報・本文・コンテキストを見られる。期限が過ぎて消えたもの、該当のないものは Not Found を表示する | [エラー詳細画面](../../specs/admin/screen/error-detail.md) |
| UC-010 | 通知のタップで詳細ページへ遷移 | 受信した Push 通知をタップすると、対応するエラーの詳細ページがダッシュボードを介さずに開く | [stream-handler](../../specs/admin/batch/stream-handler.md)、[エラー詳細のキー](../../specs/admin/term/error-event-key.md) |

## 3. 非機能要件

### 3.1 パフォーマンス要件

| 項目                          | 要件                       |
| ----------------------------- | -------------------------- |
| 初回表示速度                  | < 2秒 (グローバル平均)     |
| Time to Interactive (TTI)     | < 3秒                      |
| Lambda コールドスタート        | < 1秒                      |

### 3.2 セキュリティ要件

#### 認証・認可
- **JWT 検証**: Auth サービスと共有する秘密鍵（または公開鍵）で署名を検証
- **有効期限チェック**: `exp` クレームを確認し、期限切れトークンを拒否
- **発行者検証**: `iss` クレームが `auth.nagiyu.com` であることを確認
- **RBAC**: 権限に応じたアクセス制御、権限不足時は 403 Forbidden ([権限とロール](../../specs/admin/term/permission.md))

#### クッキーセキュリティ
- **読み取り専用**: Admin サービスは JWT クッキーを発行せず、検証のみ実施
- **SameSite=Lax**: CSRF 保護
- **Secure フラグ**: HTTPS 通信でのみ送信
- **Domain**: `.nagiyu.com` で Auth サービスとクッキーを共有

#### 通信セキュリティ
- **HTTPS 強制**: CloudFront で HTTPS リダイレクト設定
- **HSTS ヘッダー**: HTTP Strict Transport Security (HSTS) ヘッダー送信

#### その他のセキュリティ対策
- **レート制限**: AWS WAF でリクエストレート制限
- **最小権限の原則**: Lambda 実行ロールは必要最小限の権限のみ付与
- **SNS 署名検証**: SNS から届く HTTP 通知は必ず AWS 公開鍵で署名を検証し、偽造通知を拒否する
- **VAPID 認証**: Web Push Protocol の VAPID 鍵ペアを使用し、サーバーの正当性を証明する
- **VAPID 秘密鍵管理**: AWS Secrets Manager に保存し、Lambda 環境変数で参照する
- **サブスクリプション操作の認可**: プッシュサブスクリプションの登録・削除は `notifications:write` 権限を持つ認証済みユーザーのみ可能

### 3.3 可用性要件

| 項目                     | 要件                            |
| ------------------------ | ------------------------------- |
| 稼働率                   | 99.9% (月間ダウンタイム < 43分) |
| RTO (復旧目標時間)       | < 30分                          |
| RPO (復旧目標時点)       | 0 (ステートレス)                |
| SNS 通知到達時間         | SNS 発火から Web Push API 送信完了まで 10 秒以内（同時サブスクリプション 100 件以内を想定） |

### 3.4 保守性・拡張性要件

#### 保守性
- **コード品質**: TypeScript strict mode、ESLint、Prettier によるコード品質保証
- **テストカバレッジ**: ビジネスロジック（`lib/`）80%以上
- **ドキュメント**: アーキテクチャ、API 仕様、デプロイ手順のドキュメント整備

#### 拡張性
- **Phase 2 以降の拡張**: CloudWatch Logs 閲覧、ユーザー管理 UI の追加を想定した設計
- **モジュール化**: ビジネスロジック（`lib/`）と UI（`components/`, `app/`）を分離
- **新規アラーム追加**: 将来 CloudWatch Alarms を追加する際は Admin SNS トピックへ接続する設計に統一する
- **既存アラームの段階移行**: 既存 Stock Tracker アラームは既存トピックを維持しつつ Admin トピックへも通知を追加する

### 3.5 その他の非機能要件

#### スケーラビリティ
- Lambda の自動スケーリングにより、同時リクエスト数に応じて拡張
- CloudFront キャッシュにより、静的アセットの配信を高速化

#### 監視・ロギング
| 項目                     | ツール/方法                                                |
| ------------------------ | ---------------------------------------------------------- |
| アプリケーションログ     | CloudWatch Logs (Phase 2 で libs/common logger 統合)      |
| エラー追跡               | CloudWatch Logs Insights                                   |
| メトリクス               | CloudWatch Metrics (Lambda 実行時間、エラー率)            |
| アラート                 | CloudWatch Alarms (エラー率 > 5%, Lambda タイムアウト)    |

## 4. UI/UX 要件

### 4.1 画面一覧

画面と API の今の挙動は、右列のカードにある。

| 画面名 | パス | 説明 | 優先度 | 今の挙動 |
| ------ | ---- | ---- | ------ | -------- |
| ダッシュボード | `/dashboard` | ログイン済みユーザーの情報表示、通知の有効化、エラー履歴への入口 | 高 | [ダッシュボード画面](../../specs/admin/screen/dashboard.md) |
| エラー履歴一覧 | `/errors` | 永続化されたエラーを時系列降順で一覧する | 高 | [エラー履歴一覧画面](../../specs/admin/screen/errors.md) |
| エラー詳細 | `/errors/{eventId}` | 1 件のエラーのメタ情報・本文・コンテキストを表示する | 高 | [エラー詳細画面](../../specs/admin/screen/error-detail.md) |
| ヘルスチェック API | `/api/health` | サービス稼働状態を返す公開エンドポイント (認証不要) | 中 | [システム系の API](../../specs/admin/api/system.md) |

### 4.2 ダッシュボードの要件

ダッシュボードは、次を満たす。

- ログイン中のユーザーの名前、メールアドレス、保有ロールの一覧を表示する。名前は現状は表示していない (#4690)
- JWT の有効期限と、SSO 連携が動作している旨のメッセージを表示する。有効期限は現状は表示していない (#4690)
- `admin` ロールの利用者には、プッシュ通知を有効にする操作と無効にする操作を出す。現状は有効にする操作だけで、無効にする操作はない (#4691)
- `admin` または `user-manager` ロールを持つ利用者だけが開ける。現状はログインしていれば開ける (#4692)
- JWT の有効期限が切れたときは、Auth サービスへ自動でリダイレクトする
- ヘッダーとフッターは `@nagiyu/ui` の共通コンポーネントを使う。ヘッダーのアカウントメニューからログアウトできる

画面の要素・状態・操作の今の挙動は[ダッシュボード画面](../../specs/admin/screen/dashboard.md)にある。

### 4.3 レスポンシブ対応要件

| デバイス     | 対応要件                                                     |
| ------------ | ------------------------------------------------------------ |
| デスクトップ | 1920x1080 を基準、Material-UI の Grid で柔軟なレイアウト    |
| タブレット   | 768px 以上でデスクトップと同等のレイアウト                   |
| モバイル     | 375px を基準（スマホファースト）、縦積みレイアウト           |

### 4.4 アクセシビリティ要件

- **WCAG 準拠レベル**: AA
- **キーボード操作**: Tab キーでフォーカス移動、Enter キーでボタン操作
- **スクリーンリーダー対応**: ARIA ラベルの適切な設定
- **カラーコントラスト**: WCAG AA 準拠（4.5:1 以上）

### 4.5 UI/UX ガイドライン

- **デザインシステム**: Material-UI (MUI) v7.x、共通 UI ライブラリ `@nagiyu/ui`
- **カラーパレット**: Material-UI のデフォルトテーマ
- **タイポグラフィ**: Material-UI のデフォルトフォント（システムフォント）
- **スペーシング**: Material-UI の spacing システム（8px グリッド）

- ❌ CloudWatch Logs 閲覧機能（Phase 2）
- ❌ ユーザー管理 UI（Phase 2）
- ❌ ロール割り当て UI（Phase 2）
- ❌ プラットフォーム統計ダッシュボード（Phase 2）
- ❌ リアルタイムログストリーム表示（Phase 2）
- ❌ 外部 API の提供（Phase 2 以降で検討）
- ❌ Admin サービス以外のサービスへのプッシュ通知
- ❌ 通知履歴の閲覧 UI

## 6. 用語集

| 用語    | 定義                                                                          |
| ------- | ----------------------------------------------------------------------------- |
| SSO     | Single Sign-On。一度のログインで複数サービスにアクセス可能にする仕組み       |
| JWT     | JSON Web Token。認証情報を含む署名付きトークン                               |
| RBAC    | Role-Based Access Control。ロールベースアクセス制御                           |
| MVP     | Minimum Viable Product。最小限の機能を持つ実用可能な製品                      |
| Phase 1 | SSO 連携動作確認を主目的とした最小限のダッシュボード実装フェーズ              |
| Phase 2 | CloudWatch Logs 閲覧、ユーザー管理 UI などの本格的な管理機能の実装フェーズ   |
| Web Push | W3C 標準のブラウザプッシュ通知プロトコル。サービスワーカー経由で動作する    |
| VAPID   | Voluntary Application Server Identification。Web Push サーバー認証の仕組み    |
| PushSubscription | [Web Push の購読](../../specs/admin/term/push-subscription.md)を参照 |
| SNS サブスクリプション | SNS トピックの配信先として登録された HTTP/HTTPS エンドポイントまたはメールアドレス |
