# 要件定義

この文書は、何を満たすべきか (目的・対象利用者・要件・非機能の目標) を書く。今どう動くかは[仕様カード](../../specs/README.md)にあり、各節からリンクする。

## サービス概要

### 目的

動画ファイルのコーデック変換を**ブラウザのみで**簡単に行えるWebサービスを提供する。

### ターゲットユーザー

- 個人利用の一般ユーザー
- 動画のコーデック変換が必要だが、専門知識がない
- 専門ツール（FFmpegなど）のインストールが面倒

### 提供価値

- ✅ ブラウザだけで完結（ソフトウェアインストール不要）
- ✅ 匿名で利用可能（アカウント登録不要）
- ✅ 無料（Phase 1では課金機能なし）

## MVP範囲の定義

### MVPで実装する機能

**最小限の動作フロー**:
```
ユーザーがMP4をアップロード
    → コーデック選択（H.264/VP9/AV1）
    → 変換処理（AWS Batch）
    → 変換完了後にダウンロード
```

今の流れは[変換の経路](../../specs/codec-converter/flow/conversion.md)を参照する。

**含まれる機能**:
1. ✅ 動画アップロード（MP4のみ、500MB上限）
2. ✅ コーデック変換（H.264/VP9/AV1への変換）
3. ✅ ジョブステータス確認（PENDING/PROCESSING/COMPLETED/FAILED）
4. ✅ 変換済みファイルのダウンロード
5. ✅ CloudFront配信（カスタムドメイン、CDN）

**含まれない機能** (後述のスコープ外を参照):
- ❌ ジョブ一覧表示（ローカルストレージ管理）
- ❌ 複数ファイルの同時アップロード
- ❌ 進捗表示（パーセンテージ）
- ❌ ユーザー認証

### MVP判定基準

次のシナリオが完全に動作すれば、MVPとして成功:

```
シナリオ: 基本的な変換フロー
1. ブラウザでサービスにアクセスし、100MB以下のMP4ファイルを「H.264」で変換開始する
2. ステータスが「PENDING」→「PROCESSING」→「COMPLETED」と遷移する
3. 「ダウンロード」で変換済みファイルを取得し、正常に再生できる
```

## 機能要件

### FR-1: 動画アップロード機能

**説明**: ユーザーがブラウザから動画ファイルをアップロードできる

**要件**:
- **入力形式**: MP4のみ（MIMEタイプ: `video/mp4`）
- **ファイルサイズ上限**: 500MB
- 形式とサイズは、ブラウザ側とサーバー側の両方で検証する
- 動画は、Next.js/Lambda を経由せず、ブラウザから S3 へ直接アップロードする
- 検証に外れたときは、理由を示してアップロードを中止する

今の画面は[アップロード画面](../../specs/codec-converter/screen/upload.md)、API は[ジョブ API](../../specs/codec-converter/api/jobs.md)を参照する。

**制約**:
- ウイルススキャンは実施しない（Phase 1）
- アップロード中断時の再開機能なし（ユーザーが再度アップロード）

---

### FR-2: コーデック変換機能

**説明**: アップロードされた動画を指定したコーデックに変換する

**要件**:
- **入力**: MP4コンテナ（内部コーデックは問わない）
- **出力コーデック**: H.264（MP4）、VP9（WebM）、AV1（WebM）。音声はコンテナに合わせて再エンコードする。値は[出力コーデック](../../specs/codec-converter/term/output-codec.md)を参照する
- 解像度・ビットレート・フレームレートは元動画を維持する
- エンコードは 1-pass とする（処理時間を優先）
- **処理基盤**: AWS Batch（Fargate）と FFmpeg
- **タイムアウト**: 2時間（7200秒）

処理の手順は[変換バッチ](../../specs/codec-converter/batch/convert.md)を参照する。

**エラーハンドリング**:
- **FFmpegエラー**:
    - システム管理者向け: FFmpegのexit codeとstderrを`errorMessage`に記録（DynamoDB）
    - ユーザー向け: 「変換処理に失敗しました」と表示（技術的詳細は非表示）
    - ステータスを `FAILED` に設定
- **リトライ戦略**:
    - 失敗した変換は AWS Batch が自動で再試行する（計2回試行）
    - 再試行しても失敗した場合は `FAILED` に設定
- **中間ファイルの扱い**:
    - FFmpegが途中でクラッシュした場合、中間ファイルは廃棄（S3から削除）
    - 最終的に保持するのは元動画と変換後動画のみ
- **タイムアウト**: 2時間を超えた場合、ステータスを `FAILED` に設定

---

### FR-3: ジョブ管理機能

**説明**: 変換ジョブの状態を管理・追跡する

**要件**:
- **ジョブID**: UUID v4（推測困難）
- ジョブは `PENDING`、`PROCESSING`、`COMPLETED`、`FAILED` のステータスを持つ。意味と変える主体は[ジョブとステータス](../../specs/codec-converter/term/job.md)を参照する
- ジョブ情報は DynamoDB に保存する
- ジョブ作成から24時間後に自動削除する（TTL）
- ユーザーが手動でステータスを確認できる（自動ポーリングはしない）
- 失敗したときは、失敗したことと理由をユーザーに示す

今の画面は[ジョブ詳細画面](../../specs/codec-converter/screen/job-detail.md)、API は[ジョブ API](../../specs/codec-converter/api/jobs.md)を参照する。

---

### FR-4: ダウンロード機能

**説明**: 変換済みファイルをダウンロードする

**要件**:
- **ダウンロード方法**: S3 Presigned URL経由
- **有効期限**: Presigned URLは24時間有効
- **ファイル保持期間**: 変換完了後24時間（S3 Lifecycle Policyで自動削除）
- **ダウンロード回数制限**: なし（有効期限内であれば何度でも可能）
- ダウンロードできるのは、変換が完了したジョブだけ

今の画面は[ジョブ詳細画面](../../specs/codec-converter/screen/job-detail.md)、API は[ジョブ API](../../specs/codec-converter/api/jobs.md)を参照する。

---

### FR-5: 認証機能

**説明**: 認証機能は提供しない（匿名利用）

**要件**:
- アカウント登録・ログインは不要
- アクセス制御: ジョブIDを知っている人のみアクセス可能
    - ジョブIDはUUID v4（128ビット）なので推測困難

**セキュリティ考慮**:
- ジョブIDの漏洩リスクはユーザー責任
- Phase 1では認証なしで実装（Phase 2以降で検討）

## 非機能要件

### NFR-1: パフォーマンス

- **同時に動かす量**: AWS Batch の Compute Environment の最大 vCPU で制御し、超えた分はキューで待機する（ジョブ数そのものは制御しない）
- **変換処理時間の目安**:
    - H.264: 実時間の 0.3-0.5倍（30分動画 → 9-15分）
    - VP9: 実時間の 0.5-1.0倍（30分動画 → 15-30分）
    - AV1: 実時間の 1.0-2.0倍（30分動画 → 30-60分）
    - ※インスタンスタイプや動画の複雑さにより変動
- **アップロード/ダウンロード速度**: ユーザーのネットワーク環境に依存

### NFR-2: スケーラビリティ

- **想定同時ユーザー数**: Phase 1では小規模想定（具体的な数値は設定しない）
- **フロントエンド**: Lambda（自動スケール）
- **処理キュー**: AWS Batch（デフォルトスケジューリング）

### NFR-3: セキュリティ

- **データ暗号化**:
    - 転送時: HTTPS（すべての通信）
    - 保存時: S3 SSE-S3（サーバー側暗号化）、DynamoDB暗号化（デフォルト有効）
- **アクセス制御**:
    - S3バケット: 非公開（Presigned URLのみでアクセス）
    - DynamoDB: IAMロールベースのアクセス制御
- **ウイルススキャン**: Phase 1では実施しない

### NFR-4: 可用性

- **稼働率目標**: 設定しない（ベストエフォート）
- **バックアップ**: 実施しない（一時的なデータのため）

### NFR-5: コスト

- **想定月間処理量**: Phase 1では制限なし（実験的運用）
- **コスト最適化策**:
    - ファイル24時間自動削除
    - Lambdaは実行時のみ課金
    - Batchは処理時のみ課金（Fargate Spot未使用時）

### NFR-6: 動的リソース配分

ジョブの特性に応じて最適なリソースを動的に割り当てることで、コスト効率と処理時間を最適化する。設計の理由は [architecture.md](./architecture.md#動的リソース配分) を参照する。

#### リソース選択の自動化

- **要件**: ファイルサイズと出力コーデックに基づいて、最適な vCPU とメモリを自動選択
- **目的**:
    - 軽量な処理には低スペックリソースを使用してコストを削減
    - 重量な処理には高スペックリソースを使用して処理時間を短縮
    - 同時実行可能なジョブ数を最大化してキュー滞留を削減
- 選び方は[ジョブ定義のサイズ](../../specs/codec-converter/term/job-definition-size.md)を参照する

#### コスト最適化

- **要件**: リソース構成の異なる複数のジョブ定義を用意し、適切に使い分ける
- **目標**:
    - 小さいファイル + H.264 には小さいリソースを、大きいファイル + AV1 には最大のリソースを割り当てる
    - 中間的なケースは適切なリソースを選択
- **効果測定**: AWS Cost Explorer でリソース最適化前後のコストを比較

#### 処理時間の最適化

- **要件**: 重量な処理には高性能リソースを割り当てることで処理時間を短縮
- **目標**:
    - AV1 変換の処理時間を 20-30% 短縮（4 vCPU 使用時）
    - VP9 変換の処理時間を 10-20% 短縮（4 vCPU 使用時）
- **測定方法**: CloudWatch Logs でジョブ実行時間を記録・比較

#### キャパシティ管理

- **要件**: Compute Environment の最大 vCPU を、多様なリソース構成のジョブを同時実行できる大きさにする
- **例**: 最大 16 vCPU なら、1 vCPU を 4 ジョブと 4 vCPU を 3 ジョブを同時に動かせる

#### 後方互換性

- **要件**: 既存のジョブが失敗しないように、既定のジョブ定義（medium）を引き続き利用可能にする
- **実装方針**: リソース選択に失敗したとき、または不正なファイルサイズ・コーデック指定時は、既定の定義にフォールバックする

#### モニタリング

- **要件**: 各リソースパターンの使用状況を CloudWatch Logs で確認可能にする
- **実装**:
    - ジョブ定義名と使用リソース（vCPU、メモリ）を起動時にログへ出力

#### テストカバレッジ

- **要件**: リソース決定ロジックのユニットテストでカバレッジ 80% 以上を達成
- **テスト項目**:
    - 各ファイルサイズ × コーデックの組み合わせで正しいジョブ定義が選択されるか
    - 境界値テスト（100MB、300MB）
    - 不正な入力のエラーハンドリング
    - デフォルトへのフォールバック動作

## 制約事項

### 技術的制約

1. **ファイルサイズ**: 500MB上限
2. **ファイル形式**: MP4のみ（入力）
3. **変換タイムアウト**: 2時間
4. **対応コーデック**: FFmpegで処理可能なもののみ
5. **Lambda実行時間**: 15分（APIのみ、変換処理はBatch）

### ビジネス制約

1. **匿名利用のみ**: ユーザー認証なし
2. **無料提供**: 課金機能なし（Phase 1）
3. **ファイル保持期間**: 24時間のみ

## スコープ外

以下の機能はPhase 1では実装しない:

### Phase 1でスコープ外の機能

1. **ジョブ一覧表示**（ローカルストレージでの管理）
    - 理由: MVP範囲を最小化するため
    - Phase 2で実装予定

2. **進捗表示**（パーセンテージ）
    - 理由: FFmpegからのプログレス取得が複雑
    - Phase 2で実装予定

3. **複数ファイル対応**
    - AVI, MOV, MKVなどの入力形式
    - H.265/HEVCなどの出力コーデック

4. **変換オプション**
    - 解像度変更
    - ビットレート指定
    - フレームレート変更

5. **ユーザー認証・アカウント管理**

6. **ウイルススキャン**

7. **PWA対応**
    - 理由: サービスの特性上、オフライン機能のメリットが薄い（アップロード/変換/ダウンロードは全てオンライン必須）
    - 頻繁に使うツールではない（ブックマークで十分）
    - Service Workerのキャッシュ管理が複雑化する
    - Phase 2以降で必要性を再検討

## 成功基準

### MVP成功基準

以下をすべて満たせば、MVPとして成功:

1. **SC-1: 基本フロー成功率**
    - 100MB以下のMP4ファイルをアップロード → H.264変換 → ダウンロード
    - 成功率: 95%以上（典型的なテストセット）

2. **SC-2: 同時処理**
    - 最大 vCPU の範囲で並列実行できる
    - 超えた分はキューで待機する（処理が滞留しない）

3. **SC-3: タイムアウト**
    - 2時間を超えるジョブは `FAILED` ステータスになる

4. **SC-4: ダウンロード**
    - 変換完了後、Presigned URLからファイルをダウンロード可能
    - ダウンロードしたファイルが正常に再生できる

5. **SC-5: データ削除**
    - ジョブ作成から24時間後にS3オブジェクトとDynamoDBレコードが削除される

### 受け入れテスト

以下のシナリオをすべてパスすること:

1. **正常系（H.264変換）**: 50MBのMP4を「H.264」で変換開始し、ステータスが `PENDING` → `PROCESSING` → `COMPLETED` と遷移して、ダウンロードしたファイルを再生できる
2. **ファイルサイズ超過**: 600MBのMP4を選ぶと、「ファイルサイズは500MB以下である必要があります」が表示され、アップロードが実行されない
3. **FFmpeg失敗**: FFmpegで処理できないMP4をアップロードすると、ジョブが `FAILED` になり、エラーメッセージが記録される
