# Claude セッション運用の実測と制約

大規模対応では、Phase ごとに新しいマスターセッションへ再帰する（→ [`CLAUDE.md`](../../CLAUDE.md)）。本ドキュメントは、そのときに**親子セッション間で何が届き、何が届かないか**を実測ベースで記録する。

運用ルールそのものは `CLAUDE.md` にある。ここは**その根拠となる事実**を置く場所であり、運用のたびに追記されていく台帳として扱う。

> **注意**: 記載の多くは Claude Code on the web / Routines の現時点の挙動であり、公式に *research preview* とされている領域を含む。仕様は変わりうる。値が古いと感じたら**再測定して更新する**。
>
> 初版の計測日: 2026-08-24 / Claude Code `2.1.241`

---

## なぜここを気にするのか

セッションを分ける目的は **意思決定が人と交わる地点を分散させること**であって、親が子を監視することではない（理由は [`CLAUDE.md`](../../CLAUDE.md) の「なぜセッションを分けるのか」）。

したがって以下の制約は、**設計上の不都合ではない**。親が子の詳細を受け取れてしまうと、コンテキストを分散させた意味が消える。制約と設計意図が一致している。

問題になるのは 1 点だけ。**親から子へ渡せるのは起動時の一度きり**であること。ここだけは設計上も気をつける必要がある。

## セッションとサブエージェントの使い分け

| | サブエージェント | セッション |
|---|---|---|
| 人の介入 | **できない**（走り出したら止まるまで待つ） | **できる**（人がそのセッションで対話する） |
| コンテキスト | 親から隔離。結果は戻り値で親に返る | 完全に独立。親には要約しか返らない |
| 用途 | 実装・レビューなど、**判断が確定済み**の作業 | **判断そのものを分散**したい場合 |
| 起動コスト | 小 | 1 本あたり最低 $0.4 程度 |

**物量だけが理由ならサブエージェントで足りる。** セッションを分けるのは、そこで人の判断が要るときである。

## 親から子へ届くもの

| 手段 | 可否 | 備考 |
|---|---|---|
| `create_session` の `prompt` | ✅ | **実質唯一のチャネル** |
| `SendMessage` | ❌ | クラウド → クラウドは `ListAgents` に載らず名前解決できない |
| Routine（`create_trigger` + `run_once_at` + `persistent_session_id`） | ⚠️ | 同一会話として継続する。ただし **3〜10 分の遅延**（stagger） |
| `fire_trigger`（手動即時発火） | ❌ | 後述（使ってはいけない） |

`SendMessage` が届かないのは、クラウドセッションが相手の一覧に載る条件が「**送信側が Remote Control に接続していること**」だから。クラウドセッション自身は Remote Control 接続を持たないため、クラウド → クラウドが塞がる。ローカル端末からクラウドセッションへは届く。

Routine 経由は同一会話の継続として成立する（前ターンのコンテキストを読み直したうえで応答する）。コンテナがアイドルで切断されていても、起こしたうえで配信される。ただし遅延は避けられないため、**対話のテンポでは使えない**。

> **設計上の含意**: 子が親に質問する設計は破綻する（往復に 20 分かかる）。子は**人に**聞く。これは分散設計の意図とも一致する。

## 子から親へ届くもの

親が取得できるのは `get_session` / `list_sessions` が返す **`post_turn_summary` の 1 行だけ**。

```
post_turn_summary:
  status_category: review_ready
  status_detail:   "<1 行の状態ラベル>"
  needs_action:    ""
```

- 会話本文・ツール出力・最終応答は**取得できない**
- **プロンプトから内容を制御できない**。ハーネスが生成するセッション単位のラベルであり、「要約に詳しく書け」と指示しても反映されない

実測では、子が 6,750 トークンの説明を書いたにもかかわらず、返った要約に当該内容は一切含まれなかった。

**したがって、成果物の受け渡しは Issue / PR / ブランチを経由するしかない。** `CLAUDE.md` の継ぎ目モデルが Issue コメントを媒体と定めているのは、思想である以前に技術的必然である。

なお `post_turn_summary` 以外に、親から見える有用な情報もある。

| 項目 | 内容 |
|---|---|
| `current_branches` | 子が作業しているブランチ |
| `usage` / `cost_usd` | トークン消費とコスト |
| `session_status` / `connection_status` | 稼働状態 |
| `needs_action` | 人の対応が要るかどうか |

「どのブランチで何をしていて、いくらかかったか」までは追える。

### 人は全文を読める

制約があるのは**エージェントから見た場合**だけ。人は以下で全文を読める。

- claude.ai/code でセッションを開く
- ローカル端末で `claude --teleport <session-id>`（会話履歴ごと手元に引き込む）

## 実行環境の実測値

| 項目 | 実測 |
|---|---|
| 起動 〜 応答完了 | 約 11 秒 |
| コスト（空のセッション） | 約 $0.40 |
| コスト（リポジトリ clone 込み） | 約 $0.71 |
| アイドルによる切断 | 約 12 分で `disconnected`（Routine で復帰可能） |
| Routine の発火遅延（stagger） | 実測 3 分 49 秒。公式記載は「数分」、Routine ごとに一定 |
| レートリミット | `five_hour` 枠を**親子で共有** |

コストの大半は初期の `cache_write`（システムプロンプト等）。**空のセッションを立てるだけで $0.4 かかる**ため、並列に多数立てる設計ではこれが下限として効く。

### 親から継承されるもの / されないもの

| | 挙動 |
|---|---|
| モデル | 継承される |
| `permission_mode` | 継承される。**親より緩くはできない** |
| `environment_id` | 継承される |
| `extra_allowed_tools` | 親が持たない許可は**黙って落とされる** |
| リポジトリ | **継承されない**。`source_url` / `source_revision` の明示が必要 |

`permission_mode: 'plan'` は人の承認待ちでブロックするため、**自律実行する子セッションには使えない**。

## 使ってはいけない手段

### `fire_trigger`（Routine の手動即時発火）

`persistent_session_id` を指定していても**無視して新しいセッションを作る**。

- `origin` が `force_run_trigger` になり、親子関係が付かない
- モデルが継承されない（実測では Sonnet に落ちた）
- 生成されたセッションは `archive_session` で片付けられない（`resource not found`）

追い指示には `run_once_at` を指定したスケジュール発火を使う。

## 未検証の項目

運用で当たりうるが、まだ測っていないもの。判明したら追記する。

- 子が長時間（数十分〜）走った場合の挙動
