# Issue の分類

## 目的

Issue を後から絞り込めるようにする。主な用途は、リリースのときに「どのサービスに何が入るか」を確認することである。

## 軸の振り分け

Issue を分類する軸は 3 つあり、軸ごとに表す場所を 1 つに決める。

| 軸 | 表す場所 | 付ける人 |
|---|---|---|
| 種別 (バグ・機能追加など) | タイトルのプレフィックス | 起票者 |
| サービス | ラベル | 起票者 |
| リリース | マイルストーン | 人 |

同じ情報を 2 か所に書かない。2 か所に書くと、片方だけ直されて食い違う。

ラベルはサービス専用にする。リリース対象の確認ではサービス単位の絞り込みが最もよく効くためである。種別までラベルにすると、ラベルが複数の軸の混在になり、どれを付けるべきか迷って付け忘れの原因になる。

## タイトル

`[種別] 内容` の形で書く。種別は次のいずれかとする。

| プレフィックス | 種別 |
|---|---|
| `[Feature]` | 新規機能 |
| `[Bug]` | バグ修正 |
| `[Refactor]` | リファクタリング |
| `[Docs]` | ドキュメント更新 |
| `[CI]` | CI/CD 更新 |
| `[Infra]` | インフラ更新 |
| `[Chore]` | その他 |

- 区分は PR テンプレートの「変更種別」とそろえる。Issue と PR を同じ分類で追えるようにするためである。
- 内容は「何が起きているか」または「何をするか」を文で書く。
- 連番やシリーズ名は、プレフィックスではなく内容の側に書く。
    - 例: `[Refactor] 共通化 C1: DynamoDB エラーの扱いを共通化する`

## サービスラベル

- サービスごとに 1 つ用意し、名前はサービスのディレクトリ名と同じにする (`stock-tracker`、`livetalk` など)。
- どのサービスにも属さないもの (共通ライブラリ、共通インフラ、CI、ドキュメント、開発運用) には `platform` を付ける。
- 複数のサービスにまたがる場合は、該当するラベルをすべて付ける。
- 起票者が起票時に付ける。どのサービスかは判断を要さずに決まる。後から付けることにすると、付け忘れた Issue が絞り込みから漏れる。

## マイルストーン

- リリースの版 (`vX.Y.Z`) と、リリース先が未定のもの (`Backlogs`) を使う。
- 人が付ける。どのリリースに入れるかは判断を伴うためである。

## サブ Issue

サブ Issue にはラベルもマイルストーンも付けない。分類は親 Issue だけで行う。

- リリース対象の確認は親 Issue を見れば足りる。
- 付けるものと付けないものが混ざると、絞り込みの結果が中途半端になる。付けないことで統一する。

## PR

PR にはラベル・マイルストーン・種別プレフィックスを付けない。分類は関連 Issue で行う。

- PR の種別は PR テンプレートの「変更種別」で表している。タイトルにも書くと同じ情報が 2 か所になる。
- タイトルは「何を変えるか」を文で書く。

## 対象外

定期実行のワークフローが起票する Issue のラベル (`weekly-check` など) は、ワークフローごとの識別に使うものであり、本規約の対象外とする。
