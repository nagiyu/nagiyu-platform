# はじめに

nagiyu-platform は、AWS 上で動く個人開発のサービス群と、それらが共有するライブラリ・インフラをまとめたモノレポです。このサイトでは、各サービスが何をするか、今どう動くか、なぜそう作ったかを読めます。

サイトは https://nagiyu.github.io/nagiyu-platform/ で公開しています。develop に取り込まれた内容が反映されます。

## 読み方

左のメニューは 3 つの章に分かれています。

| 章 | 中身 |
|---|---|
| サービス | サービスごとに、今の挙動 (画面・API・バッチ・処理の流れ・用語) と設計資料 |
| 共通基盤 | サービスをまたいで使う用語、共通ライブラリ、インフラ |
| 開発の進め方 | コーディング規約、テスト戦略、ブランチ戦略など、開発する人向けの文書 |

サービスの中のページは、知りたいことで読み分けます。

| 知りたいこと | 読むページ |
|---|---|
| 今どう動くか | 画面・API・バッチ・処理の流れ・用語 |
| 何を満たすべきか、なぜそう作ったか | 設計資料 (要件定義、外部設計、アーキテクチャなど) |

今の挙動のページはコードから作っていて、コードが変わると CI が作り直しを求めます。設計資料には、コードからはわからない理由と、捨てた案を残しています。

## ドキュメントの方針

### ドキュメント駆動開発

本プロジェクトは**ドキュメント駆動開発**を採用しています。

- **理由**: AI 主体の開発では、詳細なドキュメントが正確な実装を生成するための明確な指示書となる
- **アプローチ**: 要件定義 → 基本設計 → 実装の順で、各フェーズで 1 つのドキュメントに情報を集約
- **メリット**: 設計の一貫性を保ち、AI への指示が明確になる

### なぜと今の挙動を分ける

docs は 2 種類に分かれる。

| 種類 | 中身 | 鮮度の保ち方 |
|---|---|---|
| なぜ (ADR・設計判断) | コードからわからないこと | 人が書き、追記していく |
| 今の挙動 ([仕様カード](specs/README.md)) | コードからわかること | コードから作り直し、CI で検査する |

コードからわかることを、手で書いて保守しない。書くなら、鮮度を機械的に検査できる写し (仕様カード) として書く。

### 最小限のルール

本プロジェクトは**最小限のルール**を原則としています。

- **理由**: 過度な制約は開発の柔軟性を損ない、変化への対応を困難にする
- **アプローチ**: 必須事項のみを定め、実装の詳細は各サービスの特性に応じて判断
- **メリット**: サービスごとの最適な設計を可能にし、プラットフォーム全体の進化を促進

### docs/ の外へリンクしない

docs は、docs/ だけを公開する先 (GitHub Pages など) でも読める。そのため docs/ の中から docs/ の外へリンクを張らない。docs/ の外のファイル (`CLAUDE.md` など) に触れるときは、リンクにせずコード表記のパスで書く。CI のリンク検査が検出する。

サイトの章立ては設定 (`docs-site/src/site-structure.ts`) で決めている。どの章にも載らないページは、ビルドで検出する。
