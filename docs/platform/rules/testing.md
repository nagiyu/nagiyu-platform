# テストの規約

テストの層ごとの責務、置き場所、ユニットテストとカバレッジ、契約テストの規則と、その理由。強制している設定はパッケージごとの `jest.config.ts` のカバレッジ閾値だけで、残りはレビューで守らせる。E2E の規則は [E2E の規約](./e2e.md)、バリデーションのテストは [バリデーションの規約](./validation.md) にある。

## 層ごとの責務

### 各層は、その事象を検知できる最も安い層に責務を持たせる

上位の層は、下位の層で捕まえられないものだけを担う。「テストが green であること」が「実際に動くこと」を意味する状態を保つためである。

| 層 | 担保すること | 担保しないこと | 実行環境 |
|---|---|---|---|
| ユニットテスト | ビジネスロジック、データアクセス層の契約、抽出したコンポーネントの描画 | 実アプリの配線、実インフラ | Jest |
| E2E テスト | 各ユースケースの成立 (配線と画面遷移を含む) | 組合せの網羅、実 AWS の挙動 | Playwright と InMemory |
| dev 結合環境 | 実インフラの差分 (実 DynamoDB、実 auth、IAM、デプロイと起動) | ユニットと E2E で担保済みの内部ロジック | 実 AWS |

### dev 結合環境はテストの階層ではなく、デプロイ先として扱う

「結合テスト」と「結合環境」は別の軸である。結合テストは V 字モデル上の自動テストの階層で、本プラットフォームでは画面遷移と連携の多くを E2E が、データアクセス層の等価性を契約テストが受け持つ。結合環境は実 AWS にデプロイして確かめる場所で、テストの階層ではない。

ユニットの網羅、E2E のユースケース担保、契約テストによる等価性が保たれていれば、dev での確認は反映確認まで縮められる。dev で内部ロジックの確認をやり直しているなら、下位の層の責務漏れである。

## 置き場所

### テストコードは `tests/` 配下に置き、`src/` と分ける

実装とテストを分けると、ビルド成果物とカバレッジの対象にテストが混ざらない。

| ディレクトリ | 内容 |
|---|---|
| `tests/unit/` | ユニットテスト。`src/` と同じ構造で置く |
| `tests/e2e/` | E2E テスト (サービスの web のみ) |
| `tests/contract/` | 契約テスト (データアクセス層を持つ core) |
| `tests/integration/` | サービスが必要なときだけ置く。Jest の対象から外して別のスクリプト (`test:integration`) で流すものがある |
| `tests/helpers/` | テスト間で共有する補助。サービスが必要なときだけ置く |
| `tests/setup.ts` | ブラウザ API のモックなど、全テストに共通のセットアップが要るときだけ置く |

例外として、tools の一部は `src/**/__tests__` に、infra の codec-converter は `test/` にテストを置いている。

### ライブラリは E2E テストを持たない

ライブラリの責務は再利用できる部品の提供であり、ユーザーフローを持たない。ユーザーフローの E2E は使う側のサービスが持ち、ライブラリはユニットテストで担保する。

## ユニットテスト

### ビジネスロジックと、状態や条件分岐を持つ部品を対象にする

純粋関数、データ変換、バリデーション、エラーの扱いなどを重点的に書く。UI は、状態管理や条件分岐を持つコンポーネントを対象にし、E2E が通る部分は省いてよい。フレームワークは Jest を使い、React コンポーネントは Testing Library で描画する。

### 純粋関数はモックせず、副作用のある処理だけをモックする

純粋関数をモックすると、実装を通らないテストになる。モックするのは、ブラウザ API (`navigator.clipboard`、`localStorage` など)、外部への HTTP リクエスト、ファイルシステム、データベース、Next.js のルーティングである。

## カバレッジ

### カバレッジの閾値は、パッケージごとの `jest.config.ts` の `coverageThreshold` で決める

共通の土台はなく、各パッケージが自分の設定に書く。既定は `global` で branches、functions、lines、statements とも 80% で、下回ると `test:coverage` が非ゼロで終わる。

例外は次のとおり。

- `libs/ui` は lines と statements を 90% にしている
- `services/stock-tracker/web` は、対象を、テストで担保すると決めたファイルに絞って `global` を 100% とし、ディレクトリごとに 80% の閾値を足している
- `services/niconico-mylist-assistant/batch` は閾値も `test:coverage` も持たない。中心の処理が実ブラウザを操作し、Jest では再現できないため、`tests/integration` の Playwright で確かめる

### 新しいパッケージには `test:coverage` と閾値を揃える

CI のカバレッジの検査は `test:coverage` を持つパッケージにだけかかる。スクリプトがなければ流れず、CI も赤くならない。しかも検査が流れるのは `develop` 向けの PR だけである。振る舞いは [サービスの PR 検証](../specs/ci/service-verify.md) にある。

## 契約テスト

### データアクセス層の等価性は、DynamoDB Local に対する契約テストで担保する

E2E は決定性と速度のために InMemory のリポジトリで動く。InMemory は DynamoDB の近似であり、GSI の射影、ソート順、条件式などで乖離しうる。乖離はコードの構造では防げないため、実装に依存しない振る舞いの仕様を InMemory と DynamoDB Local の両方で流し、片方でしか通らない差分を検知する。本番に載る DynamoDB の実装自体も DynamoDB Local に対して検証する。DynamoDB Local はトランザクションの競合例外など一部の挙動を再現しないので、そこはモックで補う。

InMemory を使う設計は [データアクセス層の規約](./data-access.md) にある。

### 契約テストは `test:contract` で通常のテストから隔離し、接続できなければ落とす

通常の `npm test` に混ぜると、DynamoDB Local がない環境で壊れる。接続できないときに自分でスキップすると、契約が一度も流れないまま green になる。落とすことで、検査が流れていないことに気づける。

`test:contract` スクリプトを持つワークスペースは、CI が DynamoDB Local を立てて流す。契約テストを足すときは、スクリプトを用意すればよく、ワークフローの変更は要らない。DynamoDB Local の起動は、手元と Claude on the web で手順が違う ([Claude の実行環境](./claude-environment.md))。テスト補助の関数は [DynamoDB Local のテスト補助](../specs/lib/aws/testing.md) にある。

### 契約には、実 DynamoDB が仕様として保証していることだけを書く

近似実装は決定的に振る舞うので、観測できた挙動をそのまま契約にすると、実 DynamoDB が保証していない順序まで固定してしまう。全件走査の結果の順序が典型である。メソッドごとに絞り込み条件が違うことも多く、「他のメソッドと揃っているはず」という前提で契約を書くと、書き手の思い込みを固定する。契約にする前に、両実装の振る舞いをメソッド単位で確かめる。

両実装で通るテストにも価値はあるが、乖離の検知ではない。射影と復元の整合を守るテストのように、将来どちらか片方だけが落ちるためのものである。テストにその意図を書いておく。

### フィクスチャは、境界の値そのものを狙う

乖離は境界にしか現れないことが多く、件数を多めに積むだけでは足りない。既定ページサイズが 50 件のメソッドに 130 件のフィクスチャを用意しても、「ちょうど 50 件で終わる」境界が抜けていた。

境界の値は、そのメソッドの既定ページサイズから決める。既定値は共通のストアとリポジトリの実装の二段にあり、一致しているとは限らないので、実装を読んで確かめる。

追加した契約は、修正前の実装に対して落ちることを実測する。全テストが通っている状態は、契約に回帰を検知する力があることを示さない。

### 乖離を見つけたら、近似実装を実 DynamoDB に寄せる

実 DynamoDB が正である。逆向きに揃えると、乖離を仕様として追認する。どちらを直すかが設計判断になるときは、独断で決めず人に聞く。

等価性を揃えると、呼び出し元の不具合が初めて現れることがある。近似実装が実 DynamoDB より多く返していたため、本番で起きている打ち切りが E2E では再現していなかった、という形である。等価性の修正と呼び出し元の修正は、切り分けて扱う。
