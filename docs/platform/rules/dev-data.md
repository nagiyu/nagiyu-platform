# dev 環境のデータ

dev 環境を日常利用の場にする方針と、そのために dev のデータをどう扱うかの規則と理由。強制している設定ファイルはなく、サービスを足すときの判断で守らせるため、出典は持たない。

## 環境の使い方

### dev を日常利用の場にし、prod は壊さない場所にする

運営者自身がプラットフォームの利用者でもあるため、dev を日常に使う。prod は壊さない場所として温存する。

- 実際に使うことで、回帰が常に見える。
- 壊れたら自分が困る。この当事者性が、品質を保つ動機になる。

dev は、prod から写したデータに後勝ちで上書きされることを許す。

### 個人データを生むバッチも dev で動かす

アラートの評価のように、個人データを生むバッチは dev でも動かす。dev で当事者として通知を受けることが、dev を日常利用の場にする目的そのものだからである。prod の動作の焼き直しではない。

## データの出自

### データを出自で分類し、扱いを決める

サービスごとにデータの出自が異なり、一律には写せない。出自で 4 つに分け、正の所在と dev での扱いを決める。

| クラス | 正の所在 | dev での扱い |
|---|---|---|
| 外部 API 由来 | 外部サービス | dev が自前で再取得・再構築する。写さない |
| コード / 設定由来 | git | デプロイで dev と prod が自動的に一致する。写さない |
| 派生・エフェメラル (安価・再生成可) | なし | 使い捨て。写さない |
| 共有マスタ / 個人資産 / 高コスト派生 | prod | prod が正で、dev はコピーする |

写すのは最後のクラスだけである。

### 派生データでも、再生成が高コストか過去分が非可逆なら prod からコピーする

派生データは、再生成が安価なら dev で作り直す。再生成が高コスト (外部 API の課金など) なもの、過去分を作り直せないものは、dev で作り直さず prod からコピーする。dev でも作ると、二重に課金され、二重に負荷がかかるためである。

### 個人データのうち、dev で独立に運用したいものは写さない

保有・アラート・ユーザー設定などの個人データは、dev で動作確認のために自分で作り、dev で独立に運用したいため、写さない。

## 写し方

### 写すときは dev-sync を使う

prod から dev へ写すデータは、dev-sync で写す。どの範囲をどう写すかは [同期](../../services/dev-sync/requirements/functional/sync.md) に、対象の足し方は [同期の対象を足す](../../services/dev-sync/requirements/use-cases/add-sync-target.md) にある。
