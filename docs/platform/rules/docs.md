# docs の書き方

`docs/` の文書の分類・配置・frontmatter・理由の書き方の規約。配置と frontmatter は検査が強制する。

## 分類と配置

文書は要件・仕様・規約の 3 つに分ける。

| 分類 | 何を書くか | 出典 |
|---|---|---|
| 要件 | 何を満たすべきか。やらないと決めたことと、その理由 | 常になし |
| 仕様 | 今のコードがどう動くか、何がどこにあるか | あり。ただし正しい内容がリポジトリの外にあるものはなし |
| 規約 | 守る規則と、その理由 | 設定で強制していればその設定ファイル。なければなし |

```
docs/
├── services/
│   ├── _template/                サービス 1 つ分の雛形
│   └── <service>/
│       ├── requirements/
│       │   ├── purpose.md        目的
│       │   ├── domain-model.md   ドメインモデル
│       │   ├── use-cases/        ユースケース
│       │   ├── functional/       機能要件
│       │   └── non-functional/   非機能要件
│       └── specs/
│           ├── screen/ api/ batch/ flow/ term/
│           ├── deploy.md         デプロイ先
│           ├── resource/         リソース
│           └── data/             データ
└── platform/
    ├── specs/
    │   ├── lib/<package>/  ci/  term/
    │   └── deploy.md  resource/  data/      shared のインフラ
    └── rules/                    規約
```

正確な配置は `docs/layout.json` の `patterns` が定義する。文書をここに当たらない場所に置くと、検査が止まる。配置を 1 つの定義に集めるのは、公開サイトのサイドバーと検査が同じ定義を読み、食い違わないようにするためである。

## サービスと platform の線

コードの置き場所で引く。`services/<name>/` にあるものは `docs/services/<name>/`、それ以外 (`libs/`、`infra/shared/`、`infra/common/`、`configs/`、`.github/`) は `docs/platform/` に置く。意味や規模で線を引くと、同じものが人によって別の場所に置かれ、探せなくなるためである。

## 分け方

一緒に変わるものを 1 つの文書にする。同じ内容をほかの文書に書かず、リンクする。2 か所に書くと、片方だけが古くなる。

README・目次・ドキュメント一覧は手で書かない。公開サイトのサイドバーが `docs/layout.json` から作る。手で書いた一覧は、文書を足すたびに直し漏れが出るためである。

## 種別と単位

### 要件

| 種別 | 単位 | 書くこと |
|---|---|---|
| 目的 | サービスに 1 本 | サービスが解決すること。サービスとして扱わない範囲も書く |
| ドメインモデル | サービスに 1 本 | 概念の名前と関係だけ。属性・キー・テーブルは仕様に書く |
| ユースケース | 1 件 1 本 | 誰が何のために何をするか |
| 機能要件 | 機能 1 つにつき 1 本 | 満たすこと。その機能でやらないことも書く |
| 非機能要件 | テーマ 1 つにつき 1 本 | 測れる水準。全サービス共通の水準は規約に書く |

機能一覧の表、用語集、想定画面の概要は要件に書かない。用語と画面は仕様に書く。要件に置くと、仕様が変わるたびに要件も直すことになるためである。

### 仕様

| 種別 | 単位 | 書くこと |
|---|---|---|
| 画面 | 1 画面 1 本 | 入口、表示、操作 |
| API | リソース単位で 1 本 | エンドポイント、入出力、エラー |
| バッチ | 1 つにつき 1 本 | 起点、処理、失敗したとき |
| 経路 | 流れ 1 つにつき 1 本 | 通知経路など、サービスをまたぐ流れ |
| 用語 | 1 つにつき 1 本 | 定義と説明 |
| デプロイ先 | 各サービスと shared に 1 本 | ホスト名、スタックの一覧、デプロイの流れ |
| リソース | 役割 1 つにつき 1 本 | リソースの名前、設定値、環境変数、権限 |
| データ | テーブル 1 つにつき 1 本 | テーブル、キー設計、項目 |
| ライブラリ (platform) | 機能 1 つにつき 1 本 | 機能と使い方 |
| CI (platform) | 一緒に変わるワークフロー・composite action・イメージの群 1 つにつき 1 本 | 検証、デプロイ、定期の起票、CI 共通イメージ、共通の action の挙動 |

- リソースの単位は、スタックではなく役割 (実行環境、シークレット、監視など) にする。スタックは実装の都合で分かれ、読む人が知りたい単位とは一致しないためである。
- 書くことが少ないリソース (ECR など) は文書を作らず、デプロイ先のスタックの一覧に載せる。
- どの仕様も、最後に任意の「理由」と「手順」の節を置ける。手順は独立した文書にせず、その手順が触る対象の仕様に書く。手順だけの文書は、対象が変わっても残って古くなるためである。

### 規約

テーマ 1 つにつき 1 本。規則とその理由を書く。設定で強制しているものは、その設定ファイルを出典にする。

## 本文の型

見出しの型は、サービスの種別なら `docs/services/_template/` の同じ位置の雛形が定義する。雛形は必須の節と任意の節を区別している。platform にしかない種別 (規約・ライブラリ・CI) の型は docs-write スキルにある。型をコードで強制しないのは、節の有無が内容によって正当に変わるためで、検査は本文の見出しを見ない。

## frontmatter

全文書が次の 3 項目だけを持つ。

| 項目 | 内容 |
|---|---|
| `sources` | 出典になるリポジトリ内のファイルのパス。なければ `[]` |
| `sources_hash` | 出典があるときだけ書く。`docs-structure.mjs update` が計算して書き、手では書かない |
| `unimplemented` | 未実装のときだけ `true` を書く |

- 出典は、その文書の挙動を決めるファイルだけにする。リポジトリルートからのパスで、ファイルだけを書く (glob は不可)。関係のないファイルを入れると、無関係な変更のたびに文書の確認が要るためである。
- `sources_hash` は、`sources` をパスでソートし、各ファイルの「パス + 改行 + 中身」を連結した sha256 である。CRLF は LF にそろえて計算する。生成日時のような、作り直すたびに変わる値は入れない。差分のノイズになるためである。
- 出典のある文書は、出典のハッシュで鮮度を検査する。出典のファイルが変わると、本文が今のコードと合っているかを確かめるまで検査が止まる。ハッシュだけを更新して通さない。通すためだけの更新は、文書を嘘にする。
- 要件の出典は常になしにする。要件はコードの写しではなく、決めたことだからである。
- 正しい内容がリポジトリの外にある文書は、出典なしにして参照先を本文に書く。コンソールや API の中にある設定 (SCP、GitHub の Variables など) は写しを持たず、理由と実物を見る方法だけを書く。写しは、外の変更に気づけず古くなる。
- 実装の前に決まった仕様は、`unimplemented: true` を付けて `docs/` に直接書く。実装とともに出典を埋め、`unimplemented` を消す。未実装の文書は develop / master に入れない。入れると、実装されていないことが今の挙動として読まれるためである。

## 理由の書き方

理由は、説明する対象の文書の中に、今の状態として現在形で書く。理由だけを集めた文書は作らない。決定の記録を積み上げると、今の採用理由がどれかを読み解く必要が生じるためである。

- 決定が変わったら、追記せず書き換える。
- 残すのは、今の採用理由である。採らない案とその理由、判断の根拠になった実測値を含める。
- 時系列の経緯と、置き換えられた決定は残さない。git の履歴にある。
- 複数の仕様にまたがる理由は、共有しているものの仕様に書く。サービスをまたぐなら platform の仕様か規約、1 サービスの中なら用語や経路の仕様に書く。
- やらないと決めたことは、要件に理由を添えて書く。
- Issue / PR 番号・Phase 名は書かない。それを見に行かないとわからない状態を作らないためである。

## 検査

`node .github/workflows/scripts/docs-structure.mjs check` が次を確かめる。

| 検査 | 対象 |
|---|---|
| frontmatter に `sources` がある | 全文書 |
| `sources` のファイルが存在し、ハッシュが一致する | 出典がある文書 |
| 決めた配置のどこかに置かれている | 全文書 |
| `unimplemented: true` がない | develop / master 向けの PR (`--forbid-unimplemented`) |
| リンク切れと docs の外へのリンクがない (`python3 .github/workflows/scripts/check-doc-links.py`) | 全文書 |

本文の見出しが型に合っているかは検査しない。docs の外のファイルへはリンクを張らず、コード表記のパスで書く。docs だけを公開する先でリンクが壊れないようにするためである。

## 旧配置の文書

まだ新しい配置へ移していない文書は、`docs/layout.json` の `legacy` に挙げてある。`legacy` の文書は移すまで従来どおりの検査だけを受け、新しい配置の規則 (frontmatter の 3 項目など) は求められない。移したら `legacy` から外す。
