# コメントの規約

コードのコメント (JSDoc を含む) を書くときの規則と、その理由。コメントは、コードを読んでも得られない情報を補うためにある。書いた時点の文脈に依存するコメントは、コードが変わるたびに読み手を誤らせる。強制している設定ファイルはなく、レビューで守らせるため、出典は持たない。

## 何を書くか

### WHY を書き、WHAT は書かない

コードを読めばわかる処理内容の言い換えは書かない。書くのは、その実装を選んだ理由、守るべき制約、自明でない前提である。

```ts
// NG: 処理内容の言い換え
// ユーザー ID でキャッシュを削除する
cache.delete(userId);

// OK: 理由
// 権限の変更を次のリクエストから反映させるため、TTL を待たずに破棄する
cache.delete(userId);
```

### 経緯は、今後の開発に効く制約としてだけ、現在形で書く

「以前はこうだったが今はこう」という変更履歴や備忘は書かない。過去の失敗が今後の変更で再発しうるときに限り、「こうすると壊れる」という制約として書く。

```ts
// NG: 変更履歴
// 以前は command で引数を渡していたが、環境変数に変更した

// OK: 現在形の制約
// Docker の CMD の上書きで引数が消えるため、command ではなく環境変数で渡す
```

### Issue や PR の番号と Phase 名を書かない

番号を書くと、経緯を知るために Issue や PR を見に行かなければならなくなる。Phase は開発中だけの区切りで、完了したら意味を失う。変更の経緯は Git の履歴と PR が持つ。コメントに残す必要のある内容は、要点をコメントそのものに書く。

### リポジトリ内のファイルや文書への参照に、説明を任せない

ファイルのパス、文書、節の番号を指して説明を済ませない。参照先の変更や削除にコメントが追従できず、リンクが切れる。必要な情報はコメントに書く。外部の仕様 (AWS のドキュメント、RFC など) の URL は書いてよい。

```ts
// NG
// 詳細は docs/services/xxx/api-spec.md の 5.1 を参照

// OK: 必要な制約をその場で書く
// ページングのトークンは DynamoDB の LastEvaluatedKey をそのまま返すため、呼び出し側で中身を解釈しない
```

## JSDoc

### 関数・クラス・型には、原則として JSDoc を書く。名前・型・実装から自明なものは省く

省略の判断は、JSDoc 全体にも、個々の `@param` と `@returns` にも同じように当てはめる。名前と型の言い換えは、読む手間を増やすだけである。自明でない振る舞いだけを書く。

```ts
// NG: 名前と型の言い換え
/**
 * ユーザーを取得する
 *
 * @param id - ユーザー ID
 * @returns ユーザー
 */

// OK: 自明でない振る舞いだけ
/**
 * @returns 退会済みのユーザーは null を返す (例外は投げない)
 */
public async getUserById(id: string): Promise<User | null>
```

## 表記

### 記号とスペースは、表記の規約に従う

記号を半角にし、スペースを記号の役割で決める。コメントの表記も同じ規約に従う。詳細は [表記の規約](./writing-style.md) にある。
