# インフラの参照名

CDK で、スタックをまたいで参照する SSM パラメータの名前と Secrets Manager のシークレットの名前の決め方。強制する設定はなく、レビューで守る。

## 規則

### SSM パラメータの名前は `SSM_PARAMETERS` に 1 か所で定義する

名前は `infra/common` (`@nagiyu/infra-common`) の `SSM_PARAMETERS` だけが持つ。書くスタックも読むスタックも、これを import して使う。名前の文字列を各スタックに直接書かない。

パラメータは、作るスタック (たいていは shared) が書き、各サービスのスタックが読む。名前を双方が別々に持つと、片方だけ変えたときにずれる。ずれた読み取り側は、デプロイするまで気づけない。同じ定数を使えば、変更がコンパイルで見つかる。

shared のデプロイが走る条件は[デプロイ先](../specs/deploy.md)にある。

- キーを足すときは infra-common に足す。shared やサービスのスタックに写しを作らない

### シークレットの名前は `SECRET_NAMES` に 1 か所で定義する

Secrets Manager のシークレットの名前も、infra-common の `SECRET_NAMES` だけが持つ。作るサービスと別のサービスが読むシークレットは、必ずここに置く。

たとえば Auth のシークレットは、認証を使う各サービスが読む。名前を作る側と読む側が別々に持つと、作る側が名前を変えても、読む側はコンパイルエラーにならず、タスクの起動時に初めて壊れる。型でも lint でも見つからない。

### シークレットの名前を変えない

`SECRET_NAMES` の文字列を変えると、シークレットの `Name` が変わり、CloudFormation がリソースを置き換える。新しいシークレットはプレースホルダーの値で作られ、実際の値は引き継がれない。値を手で入れ直すまで、アプリが壊れる。コンテナはプレースホルダーでも起動するので、CI は通り、実際の API 呼び出しで初めて失敗する。

- 名前の形がそろっていなくても、変えない。得られるのは見た目の一貫性だけで、費用に見合わない
- 新しいシークレットの名前は `nagiyu-{サービス名}-{用途}-{env}` の形にする

## パラメータの一覧

名前の一覧は、ここに書かない。各リソースの仕様が、そのリソースが書く名前を持つ。たとえば[共有 VPC](../specs/resource/vpc.md)と[共有 ECS クラスター](../specs/resource/ecs-cluster.md)。
