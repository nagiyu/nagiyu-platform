# E2E の規約

サービスの web の Playwright E2E テストを書くときの規則と、その理由。デバイスの構成と、実行時の既定値 (リトライ、ワーカー数、タイムアウト) は `configs/playwright.config.base.ts` が決める。テスト全体の層の分担は [テストの規約](./testing.md) にある。

## E2E の定義

### E2E はユースケースが満たされることを担保し、組合せは網羅しない

メインのフローだけでなく、権限の拒否、入力のエラー、not found、空の状態といった、仕様にある主要な例外フローも対象にする。各フローは代表のケースで通しで証明し、バリデーションやロールと状態の組合せの網羅は、ユニットテストに任せる。

### テストは決定的に書き、1 テスト = 1 結末にする

実行結果が一意に決まるよう、固定のデータ (InMemory) と、テストごとに用意したロールと状態を前提にする。

実行時の分岐で複数の結末を許すテスト (「表示されれば A、されなければ B」を検証する) は書かない。どちらに転んでも成功するテストは、壊れても落ちないので、E2E の価値がない。例外フローは分岐で吸収せず、ロールと状態を固定した独立のテストにする。

結末が 1 つなら、操作の手順を実行時の状態で変えてよい。端末幅で畳まれたメニューを、見えているときだけ開いてからリンクを押す、といった分岐である。どちらの場合も同じ結果を assert するため、分岐しても壊れて通ることがない。

### 期待する状態がないとき、テストは自分でスキップしない

スキップしてよいのは、ブラウザがその API を持たないといった静的な条件のときだけである。実行時に状態を調べてスキップすると、前提が壊れても green のままになる。

### テストは互いに状態を共有しない

テストは `configs/playwright.config.base.ts` の `fullyParallel: true` により、同じファイルの中でも並列に流れうる。順序は保証されない。ほかのテストが用意したデータや実行順に依存すると、結果が揺れる。必要なデータは自分で用意する。リセットを使うときの注意は、後述の「リセットはストアの広い範囲に及ぶので〜」の節にある。

### 不安定なテストは、直すか消す

CI は失敗したテストを再試行する (`retries`) ので、不安定なテストは再試行で通り、不安定なまま残る。

## フィクスチャ

### ロールはフィクスチャの `role` オプションで宣言し、全リクエストのヘッダで渡す

web サーバーは起動時の環境変数 `TEST_USER_ROLES` でロールが固定されるため、テストごとにロールを変えられない。固定のままだと、「admin なら表示、それ以外はリダイレクト」を 1 つのテストで両方受ける分岐が生まれる。

テストは `test.use({ role: [...] })` でロールを宣言する。フィクスチャが、ページ遷移と `request` の全 HTTP リクエストに `x-test-user-roles` ヘッダを付ける。サーバーは `SKIP_AUTH_CHECK=true` のときだけヘッダを読み、権限の判定を実際に評価したうえで結果を固定できる。ヘッダ名と解決の規則は [セッション取得](../specs/lib/nextjs/session.md) にある。

### `createSessionGetter` と `createClientSessionGetHandler` には同じ `defaultRoles` を渡す

サーバー側 (API ルートと Server Component) とクライアント側 (`useSession()` が呼ぶ `/api/auth/session`) は、別の口でヘッダを解釈する。`defaultRoles` が食い違うと、ロールを宣言しないテストで、サーバーとクライアントの既定のロールがずれる。例外として share-together は、`createClientSessionGetHandler` を使わず、どちらにも `defaultRoles` を渡していない。

### 否定の assert の前に、セッションの取得を待つ

「ボタンが表示されないこと」は、クライアントのセッションが届く前なら無条件に通る。壊れても落ちない状態で、一部の環境でだけ落ちる不安定なテストの原因になる。

否定を assert する前に、次の 2 つを待つ。時間待ちでは置き換えない。

1. `/api/auth/session` のレスポンスが期待のロールであること。`page.waitForResponse` を `goto` より前に待ち受ける
2. セッションに依存して描画される肯定の要素 (ヘッダのアカウントメニューなど) が見えること。レスポンスを受け取っても、React への反映が済んだとは限らないため

### 初期状態は、`USE_IN_MEMORY_DB=true` のときだけ有効なテスト用エンドポイントで用意する

テストのプロセスは web サーバーと別なので、InMemory の状態は HTTP でしか操作できない。リセットと seed は、`USE_IN_MEMORY_DB=true` のときだけ有効で、それ以外では 404 を返す `/api/test/*` のエンドポイントで行う。インターネットから届く環境では `USE_IN_MEMORY_DB=true` にしない。

seed はリポジトリの `create` の経路で入れる。not found や空の状態といった例外フローを、決定的な初期状態から確かめられる。

### リセットはストアの広い範囲に及ぶので、使うファイルは直列にし、必要なデータは自分で seed する

リセットは、InMemory の共有ストアを広く空にする (stock-tracker と share-together はサービス全体、niconico は呼び出したテストユーザーの動画で、ユーザーが固定のため実質同じ)。ファイル間も並列に流れる (`fullyParallel: true`) ので、あるファイルのリセットが、別のファイルが用意したデータを消す。

- リセットを使うファイルは `test.describe.configure({ mode: 'serial' })` で直列にする。防げるのはファイル内の競合だけで、ファイル間は防げない。例外として、share-together はリセットを使う全ファイルで、niconico は `test-setup.spec.ts` で直列にしていない
- ファイル間の安全は、CI がワーカー 1 本で流すことに依存している (`configs/playwright.config.base.ts`)。ローカルで流すときは `--workers=1` を付ける。付けないと、リセットを使わない別のファイルが巻き添えで落ちる
- 実行順に依存して溜まったデータを前提にしない。必要なデータは自分で seed し、自分が seed したものだけを検証する

### テストデータのクリアと seed の失敗は握り潰さず、例外にする

クリアや seed の失敗を警告のログだけで済ませて続けると、クリアが一度も成功しないままテストが green になる。前提の破綻は、テスト本体の失敗より先に、はっきり落として気づけるようにする。

## デバイス

### スマホファーストで書き、デスクトップは補助にする

デバイスは `chromium-desktop`、`chromium-mobile`、`webkit-mobile` の 3 つで、構成は `configs/playwright.config.base.ts` にある。どのデバイスをどの CI で流すかは [E2E](../specs/ci/e2e.md) にある。

## ブラウザ固有の落とし穴

### Service Worker を使うアプリでは、モックや API 応答に依存するテストで Service Worker を無効化する

Service Worker を経由したリクエストは、Playwright から捕まえられない。モックしたつもりの応答が素通りして実サービスへ向かったり、Service Worker がキャッシュした古い応答が画面に出たり、画面遷移が妨げられたりする。症状が多様で、Chromium では起きないことがあるため、原因に辿り着きにくい。`libs/react` の `ServiceWorkerRegistration` が Service Worker を登録する。これを layout に置いているサービス (livetalk、niconico-mylist-assistant、share-together、stock-tracker) が対象になる。

共通の設定で Service Worker をブロックしているのは `chromium-mobile` だけである。そのためテストファイルで `test.use({ serviceWorkers: 'block' })` と明示する。

### hydration の完了を待ってから入力する

サーバーで描画された直後の入力欄は、まだ JavaScript が結び付いていない。この状態で入力すると、DOM の値だけが変わり、アプリの状態は更新されない。値が入っているのにボタンが有効にならない、という分かりにくい失敗になる。WebKit は Chromium より hydration が遅く、起きやすい。

画面遷移のあと、最初の操作の前に読み込みを待つ。入力から「操作対象が有効になる」までを、冪等に再試行する書き方も有効である。期待の状態に達しなければタイムアウトで落ちるので、1 テスト = 1 結末は崩れない。

### ロケーターは位置関係ではなく、要素を一意に決める属性で指定する

「ある文字列を含む要素の親をたどって最初の入力欄を取る」といった指定は、同じ文字列が別の場所 (ボタンのラベルなど) にも出ると、ブラウザや描画のタイミングで掴む要素が変わる。プレースホルダーやアクセシビリティ上の名前で指定する。

### 完了の判断は、サービス全体の実行で行う

ファイル単体で green でも、全体では落ちることがある。全体の実行のほうが負荷が高く hydration が遅れやすいこと、直列にしていないファイルの間でデータが干渉することが理由である。修正の確認は対象のファイルだけで素早く流してよいが、完了の判断はサービス全体の実行で行う。

### WebKit では `Notification` と `PushManager` をスタブする

Playwright 同梱の Linux 版の WebKit には、`window.Notification` と `window.PushManager` がない。アプリが「ブラウザ非対応」として処理を中断するため、保存ボタンを押しても何も起きない、という失敗になる。

Web Push の購読を通すテストは、`addInitScript` で、存在しない場合に限って両方を最小限のスタブにし (`services/stock-tracker/web/tests/e2e/alert-management.spec.ts`)、`page.goto` の前に仕込む。Chromium は両方持つので、既存のグローバルは上書きしない。`context.grantPermissions` による本物の許可の状態を壊さないためである。

Web Push の購読そのものは E2E で担保せず、`libs/browser` と `libs/react` のユニットテストが担保する。
