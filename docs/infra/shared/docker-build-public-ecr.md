# Docker ビルドの public ECR 認証とリトライ

## 概要

Docker ビルドで `public.ecr.aws` のベースイメージを pull する際、レート制限エラー (`toomanyrequests` / `Data limit exceeded`) が発生することがある。対策は次の 2 段構えで、`build-docker-image` action に組み込んでいる。

- **主対策**: public ECR への認証 (後述「public ECR への認証」)
- **保険**: `toomanyrequests` 検知時の自動リトライ (後述「リトライ方針」)

---

## public ECR への認証

ビルド前に `aws ecr-public get-login-password` で public ECR へ `docker login` する。匿名 pull のクォータは送信元 IP 単位で、GitHub-hosted runner の IP は他者と共有されるため、こちらの同時実行数と無関係に枠が消費される。認証するとクォータの単位が送信元 IP から認証済みアカウントに変わり、他者に枠を消費されない。

- **リージョンは us-east-1 固定**: ECR Public の認証トークンは us-east-1 でしか取得できない。呼び出し元の `AWS_REGION` には依存させない
- **ログイン失敗はジョブを失敗させず、警告を出して匿名 pull で続行する**: 必要な IAM 権限 (Container Policy の `ecr-public:GetAuthorizationToken` / `sts:GetServiceBearerToken`) は dev / prod で反映タイミングが異なりうる。ログインの成否でビルド全体が止まるより、匿名 pull で進める方が安全なため
- **待機リトライでは解消しない場合がある**: `Data limit exceeded` は転送量の上限超過であり、短時間の待機では回復しないことが多い。リトライだけに頼らず、認証でクォータの単位を変えている

必要な IAM 権限は Container Policy に含まれ、GitHub Actions の全ロールに付与される ([IAM ポリシー](iam.md) を参照)。

## 同時実行制御を設けない理由

かつては S3 オブジェクトをセマフォとして使い、同時に実行する Docker ビルド数を 3 に制限していた。認証 pull の導入後に実測したところ、レート制限もリトライも発生しない一方で、セマフォ待ちだけが累計で長時間発生していたため撤去した (dev / prod の両方で認証 pull を確認済み)。

- **認証後はレート制限の原因が同時実行数ではなくなる**: クォータが認証済みアカウント単位になり、他者との共有 IP による枠の消費を受けない。同時実行数を絞っても、レート制限の抑止には効いていなかった
- **セマフォは上限を実効できていなかった**: 既存ロック数の確認と自身のロック配置が別操作で非原子的なため、同時にロックを取りに行くと上限を超えて通過する。「厳密でない排他制御」を許容した設計だったが、その結果、待ち時間のコストだけが残った

今後、同時実行制御を足したくなった場合は、次の点を踏まえて判断する。

- 認証 pull が有効な状態でレート制限が再発してから検討する。未然防止のために待ち時間を常態化させない
- 上限を実効させるには、取得を原子的に行える仕組み (GitHub Actions の `concurrency` や条件付き書き込みなど) が必要になる。非原子的な確認 + 配置では上限が守れない

## リトライ方針

### 背景・問題

認証 pull でもアカウント単位のクォータには上限があり、一時的な集中アクセスで `toomanyrequests` が発生しうる。発生するたびに開発者が手動でリランする手間が生じ、CI の安定稼働を妨げる。

### 決定

`toomanyrequests` エラーを検知した場合、自動で待機してリトライする仕組みを `build-docker-image` action に組み込む。

- 最大リトライ回数: 5 回
- 1 回あたりの待機時間: 60 秒
- リトライ対象: `toomanyrequests` のみ (それ以外のエラーは即座に失敗)

### 根拠・トレードオフ

- 認証 pull を補完する保険として位置付ける。認証後の実測ではリトライが発動していないが、クォータ超過の可能性自体は残る
- `toomanyrequests` は一時的なレート制限であり、短時間の待機で解消する性質を持つ
- リトライ対象を `toomanyrequests` のみに限定することで、他のエラー (設定ミスや権限エラーなど) は即座に通知され、誤魔化しにならない
- 最長 5 分 (5 回 × 60 秒) の追加遅延を許容することで、手動リランの運用コストを排除する
