## はじめに

個人で開発しているモノレポには、10 ほどのサービスと、それらが共通で使うライブラリ群 (UI 部品、ブラウザ API の薄いラッパー、AWS SDK まわりなど) が同居している。npm workspaces で 1 つにまとめた、よくある構成だ。

このモノレポを始めたときから、ずっと思っていたことがある。共通ライブラリを、**各サービスが版を指定して呼べたらいいのに**、と。

本記事は、それがやっと叶った話だ。やったこと自体は、共通ライブラリを npmjs.com に公開して、サービスが版で依存するようにしただけである。ただ、そこに辿り着くまでに、自分の中の思い込みを 1 つ外す必要があった。

## 共通ライブラリを触ると、全部が動く

困っていたのは、共通ライブラリを触ったときのことだ。

各サービスのデプロイのワークフローは、パスの条件で発火する。自分のサービスのディレクトリに加えて、共通ライブラリのディレクトリも条件に入れてあった。サービスは共通ライブラリのソースを直接参照していて (`"@nagiyu/ui": "*"` で workspaces のソースにリンクされる)、ライブラリが変わればサービスの成果物も変わるからだ。

その結果、ライブラリを 1 行直すと、**全サービスのデプロイが一斉に走る**。

気持ち悪かったのは、そのサービスには要らない変更まで入ってくることだった。ある画面のためにボタンの部品を直しただけなのに、ボタンを使っていないサービスまで新しいライブラリでビルドされ、デプロイされる。関係ないと分かっていても、ワークフローが動いた以上、動作確認はせざるを得ない。

しかも、動作確認用の環境は 1 つしかない。ライブラリを触る対応がある間は、その環境を占有することになり、ほかのサービスの対応は待たされる。ライブラリの変更が大きいほど、サービスを押さえておく区間が伸びる。

## 「版で管理したいなら、モノレポでは無理」

この気持ち悪さは、モノレポを始めた当初からあった。そのとき調べて出した結論は、**版ごとに管理したいなら、モノレポでは無理**、というものだった。

workspaces に入れたら、全部がひとまとめになる。ライブラリはいつも手元のソースのまま参照され、サービスが古い版に留まるという状態は作れない。版で分けたいなら、ライブラリを別のリポジトリに出すしかない。

npm に公開するやり方も、紹介されてはいた気がする。ただ、当時はまだサービスが育っておらず、「今やるには早い」と割り切った。それ以来、その割り切りを、**変えられない制約として自分の中で思い込んでいた**。

## 壁打ちで、結合を分けて見る

きっかけは、モノレポをやめるかどうかを AI と壁打ちしていたときだった。最初に口にしたのは「共通部品を触るたびにサービスのデプロイを止めるため、開発速度がややネックになっている。モノレポの限界かなとも思う」という愚痴だった。

コードを読ませて整理すると、詰まりの正体はモノレポそのものではなかった。重なっていたのは次の 3 つだ。

- デプロイの発火条件に、共通ライブラリのディレクトリが丸ごと入っている
- サービスが共通ライブラリのソースを直接参照していて、ライブラリが変わった瞬間に全サービスの成果物が変わる
- 動作確認用の環境が 1 つしかなく、ライブラリを触る対応がそれを占有する

選択肢は 5 つ出た。影響を受けるサービスだけをデプロイする、ライブラリだけの変更は環境に出さない、環境を増やす、ライブラリを版付きで公開する、リポジトリを分ける。

AI が最初に推したのは、安く済む前の 2 つだった。でも、自分がしたかったのは将来を見据えた話で、安さは決め手にならない。そう返して、版付きで公開する方向に寄せた。

その中で出てきたのが、**共通ライブラリだけを workspaces から外して、npm に公開してしまえばいい**、という案だった。モノレポはそのままで、リポジトリも分けない。ライブラリのディレクトリを独立した npm プロジェクトにして、サービスからは公開した版で依存する。

これを聞いたとき、めちゃくちゃびっくりした。モノレポのまま、一部分だけを切り出してパッケージにする。たったそれだけのやり方を、当時は思いつかなかった。「モノレポでは無理」と割り切ったのは自分で、無理だったのはモノレポではなく、workspaces に全部を入れたままにすることだった。

## 先に sandbox で実物を見る

案が出ても、実物を見ないと判断できない。そこで本番のリポジトリに手を入れる前に、検証用のリポジトリを 4 つ作って試した。共通の資産を置く親が 1 つ、サービスの雛形が 1 つ、サービスが 2 つ。

確かめたのは、主に次のことだ。

- 親が破壊的な版を出しても、版を上げていないサービスは古い版のまま動き続ける
- 公開先を npmjs.com にすると、どこで `npm ci` しても token なしで取ってこられる
- GitHub Actions から publish するとき、npm の Trusted Publishing (OIDC) が使える

手元に動かせる環境がなかったので、npm の組織を作ったり、publish の通知メールを確かめたりする部分は自分でやり、それ以外の検証は AI に任せた。

ここで一度詰まった。Trusted Publishing で publish すると、403 の `OIDC permission denied for this action` が返ってくる。原因は npmjs.com 側の Trusted Publisher の設定で、許可する操作に「npm publish」を足していなかったことだった。足したら、そのまま通った。

ほかにも、パッケージを初めて publish するときだけは Trusted Publishing が使えず、granular access token が要る、という制約にも当たった。

本番に入る前にこうした落とし穴を踏み終えておけたのは、大きかったと思う。

## 本番で踏んだもの

本番の作業は、2 段階に分けた。先にライブラリを独立したプロジェクトにして初版を公開し、それからサービスを 1 つずつ版での依存に切り替える。

### 公開した版は書き換えられない

切り替えの途中で、サービスの Jest がライブラリを読めなくなった。サービスのテストは CommonJS で動いていて、公開したライブラリは ESM でしか読めない形 (`exports` に `import` しかない) になっていたからだ。

AI が最初に出したのは、サービス側の Jest の設定で吸収する案だった。Jest で CommonJS をやめる手もあるのでは、と聞いたうえで、将来どう広げていくかを聞くと、ライブラリ側で巻き取っておいたほうがいい、という答えが返ってきた。サービスはこれから増えていく。サービスごとに同じ吸収を書かせるより、ライブラリが CommonJS のビルドも一緒に配るほうが筋がいい。そう判断して、ライブラリ側を直した。

ライブラリを直したら、版を上げて出し直すことになる。ここで、自分はまだ publish していないつもりでいた。ところが初版の 0.1.0 は、すでに npmjs.com に出ていた。

npm では、一度公開した版の中身は書き換えられない。同じ番号で出し直すことはできないので、直したものは 0.1.1 として出した。当たり前のことだが、版で管理するというのはこういうことなのだと、ここで実感した。

### publish のワークフローは、既定のブランチにないと手で動かせない

もう 1 つ、GitHub Actions の制約にも当たった。publish は、人が手で起動する (`workflow_dispatch`) ワークフローにしてある。ところが `workflow_dispatch` で起動できるのは、リポジトリの既定のブランチにあるワークフローだけだ。

作業していたのは、既定のブランチに入れる前の作業用のブランチだった。そこで、そのブランチへの push で起動する条件を一時的に足して publish し、出し終えたら外した。

## 1 日で片付いた

方針を詰める壁打ちから、全サービスの切り替えが終わって動作確認用の環境で全部が応答するまで、実際には 1 日だった。

長いこと無理だと思っていたことが、こんなに早く、こんなにうまくいくとは思わなかった。sandbox で先に一通り試してから本番に挑めたのも、大きかったと思う。

終わってみると、変わったのは次のところだ。

- 共通ライブラリを変えても、それだけではどのサービスのデプロイも走らない
- 新しい版を使いたいサービスだけが、自分の依存の版を上げる。上げなければ、古い版のまま動き続ける
- ライブラリの新しい版を出すのは、人が手で publish のワークフローを動かしたときだけ

裏を返せば、ライブラリを触るときは、どのサービスがどの版を使っているか、破壊的な変更なら版をどう上げるかを、今までより考えないといけない。ただ、それは版で管理するなら当たり前のことで、むしろ今まで考えずに済んでいたことのほうが不自然だった。

## おわりに

この件でいちばん大きかったのは、技術的な工夫ではなく、**昔の割り切りを制約だと思い込んでいた**と気づいたことだ。

「版で管理したいなら、モノレポでは無理」は、当時の自分が、当時の規模で出した結論だった。前提が変われば、結論も変わりうる。それなのに、結論だけが制約として残り続けていた。

モノレポで共通部分に振り回されていたら、モノレポをやめる前に、全部を 1 つの workspaces に入れていることのほうを疑ってみるといい。一部分だけを外に出して、版で配るという道もある。
