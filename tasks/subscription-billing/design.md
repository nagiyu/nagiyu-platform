本書は Phase をまたいで守る前提と、Phase 間の取り決めを書く。各 Phase の詳細 (物理設計・画面の細部) は、その Phase で決めて追記する。

## 前提 (調査と準備で分かっていること)

### Stripe の状態

- Stripe のアカウントとサンドボックスは作成済み。dev の検証はサンドボックスで行う。
- 事業者の情報 (公開用の事業者名・サポートの連絡先) は、本番環境を有効化してからでないと設定できない。本番の申請は、全 Phase を本番に出した後に行う。
- Stripe の公式ドキュメントとエージェント向けのスキルがある (`stripe agent setup`)。P2 で使うかはその Phase で判断する。

### Stripe の仕様で設計に効くもの

- **Entitlements**: 商品に「機能」(`lookup_key` を持つ) を紐づけると、契約に応じて有効な機能の一覧を Stripe が管理する。`GET /v1/entitlements/active_entitlements?customer=` で照会でき、変化すると `entitlements.active_entitlement_summary.updated` が通知される。
- **通知の性質**: 配信の順序は保証されず、同じ通知が重複して届くことがある。失敗すると最大 3 日間再送される。署名の検証には、加工していないリクエストの本文が要る。
- **領収書メール**: Stripe が送る領収書には、正式な事業者名 (個人では本名) とサポート用の住所が必ず載る。送信は管理画面の「送信メール → 決済成功時」で切り替えられる。払った本人にだけ見える範囲なので、本名が載ることは許容している。
- **Customer Portal**: 解約 (期間の終わりまで有効)・支払い方法の変更・請求の履歴を Stripe 側で提供する。
- **支払い方法**: 定期課金で使えるのはカード (Apple Pay / Google Pay を含む)。PayPay とコンビニ決済は定期課金に使えない。

### 既存の認証の仕組みで設計に効くもの

- ロールは JWT に載り、`.nagiyu.com` の共有 Cookie で全サービスに伝わる。各サービスは JWT を読むだけで、DB は見ない。
- ロールを DB から読み直すのは auth だけで、契機は 2 つ。auth ドメインへのリクエストで前回から 5 分を超えていたとき、または `/refresh` ページで強制したとき。
- **ロールの剥奪は即時に反映されない**。利用者が auth ドメインを通らない限り、最長でセッションの期限 (30 日) まで古いロールが残る。

### 期限切れの扱い (D1、決定済み)

剥奪が即時に反映されない既存の制約のままだと、解約した人や期限が切れた人が、auth を通らない限り最長 30 日有料ロールを持ち続ける。

**決定: これを許容する。** 期限切れの判定は、auth が有効なロールを算出するとき (ログインとロールの再取得) にだけ行う。JWT に期限を載せて読む側で外す仕組みは作らない。

- 理由: 漏れはおおむね「解約後にもう 1 か月使える」程度に収まる。その程度のために、全サービスが使う共通ライブラリのセッションの扱いを変えるほどではない。
- 漏れが問題になったら、期限を JWT に載せて読む側で外す方式を検討する。

## データモデル

### 論理モデル

```typescript
// 課金の権利。持ち主のユーザーの項目に入るため、userId は持たない
type RoleGrant = {
    grantId: string;
    roleId: string;           // ROLES のキー。有料ロールとしてコードで定義する
    source: 'manual' | 'stripe';
    sourceRef?: string;       // 手動ならメモ、Stripe なら顧客 ID など
    expiresAt?: number;       // 手動では必須
    revokedAt?: number;
    grantedBy?: string;       // 手動で付けた運営者の userId
    createdAt: number;
    updatedAt: number;
};

// 自サービスの利用者と Stripe の顧客の対応 (P2)
type StripeCustomerLink = {
    userId: string;
    stripeCustomerId: string;
};
```

**有効なロール** = 手動ロール ∪ { 取り消されておらず、期限内の課金の権利の `roleId` }

### 物理モデル

Stripe の顧客の対応は P2 で決める。

#### 課金の権利 (D2、決定済み)

**決定: 既存のユーザーの項目に、属性 `RoleGrants` (課金の権利の一覧) を足す。** 別テーブルは作らない。

- 理由:
    - 有効なロールの算出で、読み取りが増えない。ログインと再取得で今読んでいるユーザーの項目 1 件に入っている。
    - develop の版と dev で行き来しても壊れない。古い版の mapper は知らない属性を読み飛ばし、更新は属性ごとの SET なので `RoleGrants` を消さない。別テーブルにすると、develop の版をデプロイするたびにテーブルが消える。
    - インフラを変えずに済み、ユーザーを削除すると権利も一緒に消える。
- 同じテーブルに別の種類の項目を並べる案は採らない。`listUsers` がテーブル全体を Scan して User として読むため、古い版の一覧が壊れる。
- 管理画面と Stripe の通知 (P2) が同時に書いても失われないよう、権利を書き換えるときは読んだときの `UpdatedAt` を条件にして書く (既存の楽観ロック)。失敗したら読み直してやり直す。
- 取り消した権利は消さずに `revokedAt` を付けて残す (管理画面で経緯を読めるようにする)。

決めるときの制約:

- 既存のユーザーのテーブルは `userId` だけをキーに持つ (ソートキーなし)。同じキーで別の種類の項目を並べることはできない。
- 有効なロールの算出は、ログインのたびとロールの再取得のたびに走る。そのときの読み取りの回数を増やしすぎない。
- Stripe の通知は顧客 ID を持ってくる。顧客 ID から `userId` を引けるようにする。
- dev では develop の版と integration の版が上書きし合う (requirements の NFR-COMPAT-1)。dev のテーブルは削除設定 (`DESTROY`) なので、作り直しは許容する。

### P1 の取り決め

- **有効期限**: 手動の権利では必須。管理画面では日付で指定し、その日の終わり (日本時間) まで有効とする。
- **有効な権利**: `revokedAt` がなく、`expiresAt` がないか現在より後のもの。
- **付けられるロール**: 有料ロールの仮の定義は作らず、既存のすべてのロールを権利として付けられる。付けられるのは `roles:assign` を持つ運営者だけで、その人はもともと手動ですべてのロールを付けられるため、権限は広がらない。対象の絞り込みは、プランの単位 (D3) と一緒に P2 で決める。dev の動作確認は既存のロールで行う。
- **期限の変更**: 手動の権利の期限は、新しい期限が現在より後なら、延長・短縮・期限切れからの復活のいずれも許す (日付の入れ間違いを直せ、支援を再開した人を同じ権利で扱えるため)。途切れていた期間は記録に残らない。取り消した権利は変更できない。画面の文言は「期限の変更」とする。
- **本人に見せる範囲**: 本人向けの API (`/api/users/me`) では、権利のメモ (`sourceRef`) と付けた運営者 (`grantedBy`) を外す。
- **同時の書き込み**: 楽観ロックのやり直しの読み取りは、強い整合性にしない。競合は同じユーザーへの書き込みがミリ秒単位で重なったときだけ起き、失敗しても変更は失われず、運営者は再読み込みして保存し直せばよく、Stripe の通知は再送される。やり直しで解けなければ 409 を返す。
- **出どころを足すとき**: 権利の読み取りは厳格にし、知らない出どころの権利があるとユーザーごと読めない。読み飛ばすと、その版で書き換えたときに読めなかった権利が消えるため。出どころを足すときは、まず読めるようにするだけの版 (`ROLE_GRANT_SOURCES` に足すだけ) を develop と本番に出してから、その出どころで書き始める。
- **管理画面 (SCR-002)**: 課金の権利の変更 (追加・期限延長・取り消し) は、手動ロールと一緒に画面下部の「保存」でまとめて送る。Stripe 由来の権利は表示だけにし、API でも変更を拒否する。

### プランと有料ロール (D3、決定済み)

**決定: 有料ロールと契約をサービスごとに持つ。** 利用者はサービスごとに Checkout で申し込み、契約・更新日・解約もサービスごとに独立する。

- 有料ロール (`{service}-premium`、権限は `{service}:premium`):
    - `livetalk-premium` (LiveTalk プレミアム)
    - `quick-clip-premium` (Quick Clip プレミアム)
- 出し分け (どの機能に `{service}:premium` を求めるか) は各サービスの Issue で決める。ここではロールと権限の名前だけを置く。
- 申し込みの判定 (UC-001 の例外フロー) は、同じサービスの有効な契約があるかで行う。
- 価格はコードに持たせず、Stripe の Price で持つ。dev のサンドボックスは仮の価格で確かめ、本番の価格は P3 (料金のページ) までに決める。
- **権利として付けられるロール**: 有料ロールだけに絞る (P1 の取り決めの絞り込み)。絞り込みは付けるとき (API の検証と管理画面の選択肢) にだけ行い、読み取りでは行わない。P1 の dev の確認で付けた有料ロール以外の権利も、読めて有効なロールに載り続ける。

## コンポーネント設計

### パッケージ責務分担

| パッケージ | 責務 |
|----------|------|
| `libs/common` | 有料ロールの定義 (ROLES)。有効なロールの算出が純粋関数で書けるなら置く |
| `libs/ui` | 特定商取引法に基づく表記の中身と表示部品。共通の利用規約とプライバシーポリシーのデータに課金の条項を足す |
| `services/auth/core` | 課金の権利と Stripe の顧客の対応のリポジトリ。Stripe との同期のロジック |
| `services/auth/web` | jwt callback での有効なロールの算出、管理画面、プランの画面、特定商取引法に基づく表記のページ、申し込み・契約の管理・通知の受け口の API |
| `infra/auth` | テーブル、Stripe の鍵の秘密情報、通知の受け口への経路 |

### Phase 間の取り決め

- **P1 → P2**: 課金の権利を書き換える操作は、P1 で `source` を問わず使える形にしておく。P2 は新しい保存先を作らず、`source: 'stripe'` の権利として同じところへ書く。
- **ロール名の一致**: Stripe の Entitlements の `lookup_key` は、有料ロールの ID と同じ文字列にする。対応表を持たずに済み、プランと有料ロールの対応を Stripe の管理画面で変えられる (NFR-EXT-2)。
- **決済直後の反映**: Checkout の成功時の戻り先を、auth の `/refresh?callbackUrl=<元の画面>` にする。新しい仕組みは作らない (F-007)。

### Stripe との同期 (P2)

通知の中身は「この顧客の何かが変わった」という合図としてだけ使い、毎回 Stripe に最新の状態を問い合わせて上書きする。

1. 署名を検証する。
2. 通知から顧客 ID を取り出し、`userId` を引く。
3. その顧客の有効な Entitlements (または契約) を Stripe から取得する。
4. 得られた `lookup_key` の集合に合わせて、`source: 'stripe'` の課金の権利を作る・期限を更新する・取り消す。
5. 成功を返す。

この形なら、重複・順序の入れ替わり・取りこぼし後の再送のいずれでも、最終的に Stripe の状態と一致する。通知の ID を記録して重複を除く仕組みは、原則要らない。

**通知の受け口 (D4、決定済み)**: auth の API (`/api/billing/webhook`) に置く。利用者と課金の権利を持つのは auth であり、通知を受けて権利を書き換えるのも auth の責務だから。

**Stripe 由来の権利の有効期限 (D5、決定済み)**: 契約の現在の請求期間の終わり + 3 日を期限にする。

- 理由: 期限がないと、解約の通知を取りこぼしたとき (Stripe の再送は 3 日まで) 有料ロールが無期限に残り、要件 UC-003 の「最終的に Stripe と一致する」を満たせない。
- 猶予の 3 日は、Stripe の通知の再送期間に合わせる。
- 更新の通知を取りこぼした場合に備え、プランの画面を開いたときにも Stripe から取り直して同期する。

### P2 の取り決め

- **Stripe の顧客の対応**: ユーザーの項目に属性 `StripeCustomerId` を足す (D2 と同じ理由で別テーブルにしない)。顧客を作るときは Stripe の顧客の `metadata.userId` にユーザー ID を入れる。
    - 通知の顧客 ID から `userId` を引くときは、Stripe の顧客の `metadata.userId` を読み、そのユーザーの `StripeCustomerId` が通知の顧客 ID と一致するかを確かめる。顧客 ID の索引 (GSI) は作らない。同期では毎回 Stripe に問い合わせるので、顧客の取得が 1 回増えるだけで済み、テーブルの定義を変えずに済む。
    - 一致しない・ユーザーがいないときは、処理せず成功を返す (再送されても結果は同じため)。
- **同期の中身**: 顧客の契約を Stripe から一覧し、`active` / `trialing` / `past_due` の契約の品目ごとに、商品の Feature の `lookup_key` を有料ロールとして得る。期限は品目の請求期間の終わり + 3 日。
    - 得たロールに有効な Stripe 由来の権利があれば期限と参照を更新し、なければ作る。得たロールにない有効な Stripe 由来の権利は取り消す。
    - `lookup_key` が有料ロールでないものは無視してログに残す。
    - 書き込みは P1 の `updateRolesAndGrants` (楽観ロックとやり直しつき) を使う。
- **鍵の受け渡し**: 秘密情報 `nagiyu-auth-stripe-{env}` (`{"secretKey":"...","webhookSecret":"..."}`) は CDK で作らず、人が手で作る。CDK で作ると、dev で develop の版をデプロイするたびに秘密情報が消え、入れた値が失われるため。デプロイはこの名前で値を読み、既存の秘密情報と同じく CDK の context → Lambda の環境変数で渡す。秘密情報が無い環境では値を空にし、課金の API は使えない旨を返す (本番の鍵を入れるまでの本番もこの状態)。

### API (P2、仮)

| メソッド | パス | 説明 | 認証 |
|---------|------|------|------|
| POST | `/api/billing/checkout` | Checkout Session を作り、その URL を返す。有効な契約があれば作らない | セッション必須 |
| POST | `/api/billing/portal` | Customer Portal のセッションを作り、その URL を返す | セッション必須 |
| POST | `/api/billing/webhook` | Stripe からの通知を受ける | Stripe の署名 |

- Checkout Session には、顧客 (なければ作って対応を保存する)、`client_reference_id` と `metadata` の `userId` を付ける。
- 通知の受け口は、ログインを求めるミドルウェアの対象から外す。

## 実装上の注意点

### 依存関係・前提条件

- P2 は P1 の課金の権利に依存する。P3 は独立して進められる。
- dev の検証には Stripe のサンドボックスの鍵が要る。鍵は人が Stripe の管理画面で発行して、秘密情報に登録する。

### セキュリティ考慮事項

- 課金の権利の手動変更の API は、既存のロール割り当てと同じ権限 (`roles:assign`) で守る。
- Stripe の秘密鍵と通知の署名鍵は、既存の秘密情報と同じ方法 (Secrets Manager → CDK の context → Lambda の環境変数) で扱う。
- 通知の受け口の前にある CloudFront と Lambda の経路で、本文が加工されずに届くか、`Stripe-Signature` ヘッダーが転送されるかを dev で確かめる。
- 削除されずに残る設定で名前が固定のリソース (秘密情報など) は、dev で develop の版と行き来すると、作り直しのときに名前の衝突で失敗しうる。作るときに確かめる。
